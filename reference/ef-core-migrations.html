EF Core, SQLite i migracje

Ściąga do druku. Wszystkie komendy, komunikaty błędów i wygenerowany SQL zweryfikowane na .NET 10.0.400, EF Core 10.0.11, dotnet-ef 10.0.7, Windows 11.

Ćwiczone w lekcji 0009. Powiązane: lifetimes, ProblemDetails, curl.

Instalacja

dotnet add package Microsoft.EntityFrameworkCore.Sqlite
dotnet add package Microsoft.EntityFrameworkCore.Design

dotnet tool install --global dotnet-ef
dotnet tool update  --global dotnet-ef
ElementPo co
…EntityFrameworkCore.Sqliteprovider — tłumaczy LINQ na SQL dialektu SQLite. Dla firmowej bazy: .SqlServer, Npgsql.EntityFrameworkCore.PostgreSQL
…EntityFrameworkCore.Designpotrzebny tylko do generowania migracji; wchodzi jako PrivateAssets="all", więc nie leci do produkcji
dotnet-efnarzędzie CLI (dotnet ef …). Instalowane globalnie, poza projektem

Wersja narzędzia starsza od runtime’u daje ostrzeżenie, nie błąd:
The Entity Framework tools version '10.0.7' is older than that of the runtime '10.0.11'.

Alternatywa dla wiązania po nazwie: dodać prywatny bezparametrowy konstruktor — EF użyje jego i wypełni właściwości setterami.

DbContext — chudy, tylko DbSet-y i jedna linia skanująca

public class HelpdeskDbContext(DbContextOptions<HelpdeskDbContext> options) : DbContext(options)
{
    public DbSet<Ticket> Tickets => Set<Ticket>();

    protected override void OnModelCreating(ModelBuilder modelBuilder) =>
        modelBuilder.ApplyConfigurationsFromAssembly(typeof(HelpdeskDbContext).Assembly);
}

Konfiguracja — jedna encja, jeden plik

public class TicketConfiguration : IEntityTypeConfiguration<Ticket>
{
    public void Configure(EntityTypeBuilder<Ticket> builder)
    {
        builder.HasKey(t => t.Id);
        builder.Property(t => t.Title).IsRequired().HasMaxLength(100);
        builder.HasIndex(t => t.Title).IsUnique();
        builder.HasData(new { Id = 1, Title = "Pierwsze", Priority = "normal" });
    }
}

Gdzie leży plik: Features/Tickets/ przy vertical slices, Infrastructure/Persistence/Configurations/ przy Clean Architecture. ApplyConfigurationsFromAssembly znajdzie go tak czy inaczej — byle był w skanowanym assembly.

Relacje

builder
    .HasOne(t => t.Manufacturer)
    .WithMany()
    .HasForeignKey(t => t.ManufacturerId)
    .OnDelete(DeleteBehavior.Cascade);
FragmentZnaczenie
HasOne(…) / WithMany(…)krotność po obu stronach; WithMany() bez argumentu = nie modelujemy kolekcji po drugiej stronie
HasForeignKey(…)kolumna klucza obcego
OnDelete(Cascade)skasowanie rodzica kasuje dzieci
OnDelete(Restrict)blokuje kasowanie rodzica, dopóki są dzieci
OnDelete(SetNull)zostawia dzieci z NULL w kluczu obcym (wymaga nullowalnego FK)
Dwie pułapki. (1) HasIndex na kolumnie, która już jest kluczem głównym, tworzy drugi, nieunikalny indeks (IX_Tickets_Id obok PK_Tickets) — koszt przy każdym zapisie, zero zysku. (2) Cascade przy wymaganym FK jest domyślne, więc łatwo je odziedziczyć bez decyzji; przy danych o wartości historycznej (zgłoszenia, faktury, logi) zwykle chcesz Restrict.

Nazwa migracji jest dokumentacją. AddTicketAssignee, nie Update2. Migracje wchodzą do gita razem z kodem — bez nich kolega nie odtworzy schematu.

Zapytania — LINQ, który leci do bazy

C#SQL (SQLite)
db.Tickets.ToListAsync(ct)SELECT "t"."Id", … FROM "Tickets" AS "t"
.FirstOrDefaultAsync(t => t.Id == id, ct)… WHERE "t"."Id" = @id LIMIT 1
.AnyAsync(t => t.Title == title, ct)SELECT EXISTS (SELECT 1 FROM "Tickets" …)
.CountAsync(ct)SELECT COUNT(*) …
.Where(…).OrderBy(…).Skip(20).Take(10)… WHERE … ORDER BY … LIMIT 10 OFFSET 20
AsNoTracking() na odczytach. Bez tego EF trzyma kopię każdego wczytanego wiersza, żeby wykryć zmiany przy SaveChangesAsync. Przy GET, gdzie nic nie zapisujesz, to czysty koszt pamięci i czasu. Zasada: query → AsNoTracking(), command → bez.

Zapis

db.Tickets.Add(ticket);        // INSERT … RETURNING "Id"
ticket.Rename("nowy");         // UPDATE … WHERE "Id" = @p — bez żadnego .Update()
db.Tickets.Remove(ticket);     // DELETE FROM …
await db.SaveChangesAsync(ct); // dopiero tu leci SQL, w jednej transakcji

Change tracking: encja wczytana bez AsNoTracking jest obserwowana. Zmiana właściwości wystarczy — SaveChangesAsync sam wygeneruje UPDATE tylko dla zmienionych kolumn. Dlatego encja musi być mutowalna (choćby przez prywatny setter i metodę domenową), a nie niemutowalnym record-em.

Lifetime — jedyna dopuszczalna odpowiedź

DbContext jest Scoped i nie jest thread-safe. AddDbContext rejestruje go jako Scoped automatycznie. Wszystko, co go wstrzykuje, musi być Scoped albo Transient — nigdy Singleton.

Cannot consume scoped service 'HelpdeskDbContext' from singleton 'ITicketStore'.

To ten sam mechanizm captive dependency co w lekcji 0002. Scope = żądanie HTTP, więc jedno żądanie = jeden DbContext = brak wyścigów. Ręczny lock z lekcji 0003 przestaje być potrzebny — o współbieżność dba baza.

Dwa komunikaty z dokumentacji, nieodtwarzane na tej maszynie — warto je kojarzyć, ale nie sprawdzałem ich własnym uruchomieniem:
  • No database provider has been configured for this DbContext — brak UseSqlite(…) albo pusty connection string.
  • A second operation was started on this context instance before a previous operation completed — dwa równoległe await na jednym DbContext, np. przez Task.WhenAll. To dowód, że DbContext nie jest thread-safe.

null czy wyjątek?

Zwraca nullRzuca
FirstOrDefaultAsync, SingleOrDefaultAsync, FindAsyncFirstAsync, SingleAsync

Rozstrzyga nazwa metody, nie miejsce wywołania. Store zna fakt („nie ma wiersza”), wołający zna znaczenie („404” albo „w porządku”). Domyślnie: GetByIdAsync zwraca Ticket?, a ?? throw new DomainException(...) siedzi w handlerze. Gdy powtórzy się w kilku handlerach — dołożyć GetRequiredAsync zwracające Ticket, nie zmieniać zachowania istniejącej metody.

Antywzorzec: store rzuca KeyNotFoundException, handler łapie i zamienia na DomainException — try/catch w roli if-a.
