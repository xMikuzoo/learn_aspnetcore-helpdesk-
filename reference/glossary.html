Reference · Glossary

Słownik pojęć

Terminy po angielsku (tak jak w pracy), wyjaśnienie po polsku, analogia z frontendu gdzie pomaga. Każda lekcja trzyma się tych definicji.

Kolumna „Lekcja” mówi, gdzie pojęcie jest ćwiczone. Puste = jeszcze nie było.

Szkielet aplikacji

Program.cs — punkt startowy
Jedyny plik, który .NET uruchamia jako pierwszy. Dzięki top-level statements nie ma klasy ani Main — kod leci od góry, jak w skrypcie Node. Lekcja 0001.
WebApplicationBuilder — „przepis” na aplikację
Obiekt zwracany przez WebApplication.CreateBuilder(args). Faza konfiguracji: tu rejestrujesz serwisy (builder.Services), czytasz config (builder.Configuration), ustawiasz logowanie. Nic jeszcze nie działa. Lekcja 0001.
WebApplication — zbudowana aplikacja
Wynik builder.Build(). Od tego momentu rejestr serwisów jest zamrożony; teraz definiujesz middleware i endpointy, a na końcu app.Run(). Lekcja 0001.
Endpoint — punkt końcowy HTTP
Para: wzorzec trasy (np. GET /tickets/{id}) + kod, który ją obsługuje. W minimal API tworzysz go przez app.MapGet / MapPost / MapPut / MapDelete. Analogia: app.get('/tickets/:id', handler) w Express. Lekcja 0001.
Route — trasa
Wzorzec URL endpointu. Segmenty w nawiasach klamrowych {id} są parametrami; ASP.NET wiąże je z argumentami handlera po nazwie.
Endpoint handler — funkcja obsługująca trasę
Lambda lub metoda przekazana do MapGet itd. Jej zwrócona wartość jest serializowana do JSON. Nie mylić z command/query handler (niżej) — to inne pojęcie, choć słowo to samo.
Middleware — warstwa pośrednia
Element łańcucha przetwarzającego każde żądanie przed dotarciem do endpointu (i po). Rejestrowany przez app.Use…. Analogia: middleware w Express / Koa. Kolejność ma znaczenie.
Request pipeline — potok żądania
Uporządkowany łańcuch middleware zakończony endpointem. Nie mylić z pipeline behavior (mediator) — to osobny potok, wewnątrz aplikacji.
Minimal API
Styl pisania endpointów bezpośrednio na app, bez klas kontrolerów. Domyślny w tym kursie.
Controller — kontroler
Klasa grupująca endpointy jako metody ([HttpGet]), starszy styl, nadal powszechny w firmowym kodzie. Ta sama maszyneria pod spodem.

Dependency Injection

Rozwinięcie z przykładami i diagnostyką: ściąga — DI: rejestracja i czasy życia. Ćwiczone w lekcji 0002.

Service — serwis
Każdy obiekt, który aplikacja tworzy i wstrzykuje zamiast new-ować ręcznie: repozytorium, klient HTTP, handler, walidator. Nazwa nie mówi nic o roli — mówi tylko „zarządza mną kontener”.
Dependency Injection (DI) — wstrzykiwanie zależności
Klasa deklaruje, czego potrzebuje (parametry konstruktora), a kontener to dostarcza. Klasa nie wie, skąd zależność pochodzi ani jak ją stworzyć. Analogia: provide/inject w Vue, ale obowiązkowe i dla całej aplikacji.
DI container / IServiceProvider — kontener
Rejestr „interfejs → implementacja → lifetime”. Budujesz go przez builder.Services (IServiceCollection), pytasz o obiekty przez IServiceProvider. Zwykle nie pytasz sam — ASP.NET robi to, tworząc handlery.
Lifetime — czas życia serwisu
Jak długo kontener trzyma jedną instancję. Trzy opcje: Singleton (jedna na całą aplikację), Scoped (jedna na żądanie HTTP), Transient (nowa przy każdym wstrzyknięciu).
Captive dependency — „uwięziona” zależność
Błąd: Singleton dostaje wstrzyknięty Scoped/Transient i trzyma go na zawsze. Kontener w trybie Development rzuca wyjątek, żeby to wyłapać.

Architektura

Vertical slice — pionowy wycinek
Organizacja kodu per feature, nie per warstwa: folder Features/Tickets/CreateTicket/ zawiera endpoint, command, handler, validator. Zmiana w jednym feature nie dotyka innych.
Clean Architecture
Organizacja per warstwa z regułą zależności: Domain ← Application ← Infrastructure / Presentation. Wewnętrzne warstwy nie znają zewnętrznych. Slices i Clean Arch można łączyć.
Domain — warstwa domeny
Encje i reguły biznesowe bez zależności od frameworków. „Ticket nie może być zamknięty dwa razy” żyje tutaj.
Application — warstwa aplikacji
Use-case'y: commands, queries, handlery, interfejsy do infrastruktury (np. ITicketRepository). Zna Domain, nie zna bazy danych.
Infrastructure
Implementacje interfejsów z Application: EF Core, e-mail, zewnętrzne API.
Presentation / API
Endpointy / kontrolery. Tłumaczy HTTP na command/query i z powrotem.
Repository — repozytorium
Abstrakcja nad dostępem do danych (GetById, Add…). W wielu projektach zastępuje ją bezpośrednio DbContext.

CQRS i mediator

Command — polecenie
Obiekt opisujący zamiar zmiany stanu: CreateTicketCommand(Title, Priority). Tryb rozkazujący. Zwykle zwraca mało (id) albo nic.
Query — zapytanie
Obiekt opisujący prośbę o dane: GetTicketByIdQuery(Id). Nie zmienia stanu. Zwraca DTO.
Command handler / Query handler
Klasa z jedną metodą Handle(request, ct), która wykonuje dany command/query. Jeden handler na jeden typ requestu. Tu mieszka logika use-case'u.
CQRS — Command Query Responsibility Segregation
Zasada: osobne ścieżki (typy, handlery, czasem modele) dla zapisu i odczytu. W prostym wydaniu = osobne klasy; w skrajnym = osobne bazy.
Mediator / dispatcher
Obiekt, któremu endpoint oddaje command/query (Send(cmd)), a on znajduje właściwy handler w DI i go wywołuje. Endpoint nie zna handlera. Biblioteki: MediatR, Wolverine, Mediator — albo 30 linii własnego kodu.
Pipeline behavior
Middleware mediatora: kod uruchamiany wokół każdego handlera (walidacja, logowanie, transakcje). Sygnatura: dostaje request i next(), jak middleware w Express.
Validator — walidator
Klasa opisująca reguły poprawności requestu, np. RuleFor(x => x.Title).NotEmpty() (FluentValidation). Uruchamiana w pipeline behavior przed handlerem.

Dane

DTO — Data Transfer Object
Płaski obiekt do przenoszenia danych przez granicę (HTTP, warstwa). W C# zwykle record.
Record
Typ C# do niemutowalnych danych z równością po wartości: record CreateTicketCommand(string Title);. Idealny na command/query/DTO.
Entity — encja
Obiekt z tożsamością (Id) i cyklem życia, np. Ticket. Mapowany na tabelę przez EF Core.
DbContext
Główna klasa EF Core: sesja z bazą + zestaw DbSet<T> (tabel). Rejestrowany jako Scoped.
Migration — migracja
Wygenerowany kod opisujący zmianę schematu bazy. dotnet ef migrations add Nazwa, potem dotnet ef database update.
