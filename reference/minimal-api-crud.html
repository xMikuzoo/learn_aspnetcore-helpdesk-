Routing, binding i wyniki HTTP

Ściąga do druku. Oparta na How to create responses in Minimal API apps i Route groups; wszystkie kody statusu zweryfikowane curlem na .NET 10.0.400.

Ćwiczone w lekcji 0003.

Skąd handler bierze parametr

Minimal API rozstrzyga to po typie i nazwie, w tej kolejności:

Atrybuty ([FromRoute], [FromQuery], [FromBody], [FromServices]) są potrzebne tylko wtedy, gdy chcesz nadpisać tę regułę. Kolejność parametrów nie ma znaczenia.

Ograniczenia trasy (route constraints)

app.MapGet("/tickets/{id:int}", …)                // tylko liczby całkowite
app.MapGet("/tickets/{id:int:min(1)}", …)         // i to dodatnie
app.MapGet("/posts/{slug:regex(^[a-z0-9-]+$)}", …) // wzorzec
Ograniczenie zmienia kod odpowiedzi. Bez :int żądanie /tickets/abc pasuje do trasy, ale binding się wywraca → 400 Bad Request. Z :int żądanie w ogóle nie pasuje do żadnej trasy → 404 Not Found. Oba zweryfikowane. Dla API zwykle chcesz 404: „nie ma takiego zasobu” jest prawdziwsze niż „źle sformułowałeś żądanie”.

Grupy tras

var tickets = app.MapGroup("/tickets");

tickets.MapGet("/", …);          // GET  /tickets
tickets.MapGet("/{id:int}", …);  // GET  /tickets/42
tickets.MapPost("/", …);         // POST /tickets

MapGroup zwraca RouteGroupBuilder. Wywołane na nim .RequireAuthorization(), .WithTags("Tickets") czy .AddEndpointFilter(…) dotyczy wszystkich endpointów w grupie. Grupy można zagnieżdżać.

Results vs TypedResults

Results.Ok(x)TypedResults.Ok(x)
Typ zwracanyIResultOk<T> (konkretny)
Metadane OpenAPItrzeba dopisać .Produces<T>(200)automatyczne
Test jednostkowytrzeba rzutowaćAssert.Equal(200, result.StatusCode)
Dwa różne wyniki w jednym handlerzedziała samotrzeba zadeklarować Results<T1, T2>

Docs mówią wprost: „Returning TypedResults is preferred to returning Results”.

Dwa możliwe wyniki — składnia

using Microsoft.AspNetCore.Http.HttpResults;

tickets.MapGet("/{id:int}",
    Results<Ok<Ticket>, NotFound> (int id, ITicketStore store) =>
        store.GetById(id) is { } ticket
            ? TypedResults.Ok(ticket)
            : TypedResults.NotFound());

Typ zwracany stoi przed listą parametrów lambdy — to jedyne miejsce w C#, gdzie zobaczysz taką składnię. Bez tego kompilator nie potrafi znaleźć wspólnego typu dla Ok<Ticket> i NotFound, bo to dwie niepowiązane klasy.

201 vs 200 przy POST. 201 mówi klientowi „powstał nowy zasób i znajdziesz go pod tym adresem” — adres idzie w nagłówku Location, nie w ciele. Frontend może po nim od razu przejść do szczegółów. 200 nie niesie tej informacji.
204 vs 200 przy PUT/DELETE. 204 = „udało się, nie mam ci nic do pokazania”. Ciało musi być puste — fetch() na 204 nie ma czego zdeserializować, więc res.json() po stronie frontendu rzuci wyjątkiem. To najczęstsze zderzenie frontu z backendem przy DELETE.

Stan w singletonie: lock

Serwis Singleton obsługuje żądania równolegle, na różnych wątkach. List<T> i Dictionary<K,V> nie są thread-safe — równoczesny zapis potrafi je fizycznie uszkodzić albo rzucić IndexOutOfRangeException w losowym miejscu.

public class InMemoryTicketStore : ITicketStore
{
    private readonly Lock _gate = new();   // System.Threading.Lock, .NET 9+
    private readonly List<Ticket> _tickets = [ … ];

    public IReadOnlyList<Ticket> GetAll()
    {
        lock (_gate) return _tickets.ToList();   // kopia — patrz niżej
    }
}
  • Osłaniaj też odczyt. Czytanie listy w trakcie cudzego zapisu to wyścig, nie tylko zapis równoległy.
  • Zwracaj kopię (.ToList()). Bez tego oddajesz referencję do żywej listy i wołający iteruje ją poza lock — klasyczne InvalidOperationException: Collection was modified.
  • Sam licznik (_created++) wystarczy opakować w Interlocked.Increment(ref _created) — taniej niż lock.
  • Alternatywa dla całych kolekcji: System.Collections.Concurrent (ConcurrentDictionary).

Przy EF Core (lekcja 0009) problem znika u źródła: DbContext jest Scoped, więc każde żądanie ma własny i nie ma czego blokować.
