DI: rejestracja i czasy życia

Ściąga do druku. Definicje słowo w słowo za Microsoft Learn — Service lifetimes; przykłady zweryfikowane na .NET 10.0.400.

Ćwiczone w lekcji 0002.

Trzy czasy życia

LifetimeKiedy powstaje instancjaKiedy ginieTypowe użycie
AddTransient Za każdym razem, gdy ktoś o nią poprosi — nawet dwa razy w jednym żądaniu. Na końcu żądania (jeśli IDisposable). Lekkie, bezstanowe helpery. Domyślny wybór, gdy nie wiesz.
AddScoped Raz na żądanie HTTP (per client request / connection). Na końcu żądania. DbContext, transakcja, dane bieżącego użytkownika. AddDbContext robi to domyślnie.
AddSingleton Raz na proces, przy pierwszym użyciu (albo od razu, jeśli podasz gotową instancję). Przy zamknięciu aplikacji. Cache, konfiguracja, pule połączeń, stan in-memory. Musi być thread-safe.
Singleton obsługuje wiele żądań równocześnie, na różnych wątkach. Zwykła List<T> w singletonie to bomba z opóźnionym zapłonem — dopóki tylko czytasz, jest dobrze; przy zapisie potrzebujesz lock albo kolekcji z System.Collections.Concurrent. Docs: „Singleton services must be thread safe”.

Składnia rejestracji

// interfejs → implementacja (najczęstsze)
builder.Services.AddSingleton<ITicketStore, InMemoryTicketStore>();

// sama klasa, bez interfejsu
builder.Services.AddScoped<TicketAuditor>();

// gotowa instancja (zawsze singleton)
builder.Services.AddSingleton<IClock>(new SystemClock());

// fabryka — gdy do zbudowania serwisu potrzebujesz innych serwisów
builder.Services.AddScoped<ITicketStore>(sp =>
    new InMemoryTicketStore(sp.GetRequiredService<ILogger<InMemoryTicketStore>>()));

Jak serwis trafia do kodu

// 1. Endpoint minimal API — parametr lambdy, typ znany kontenerowi
app.MapGet("/tickets", (ITicketStore store) => store.GetAll());

// 2. Konstruktor innej klasy (primary constructor, C# 12+)
public class TicketAuditor(ITicketStore store, ILogger<TicketAuditor> log)
{
    public int Count() => store.GetAll().Count;
}

Konstruktor to domyślny i preferowany sposób. Sięganie po IServiceProvider.GetService() w środku metody to service locator — docs wprost odradzają.1

1 DI guidelines, „Avoid using the service locator pattern”.

SingletonScoped / TransientCaptive dependency — wyjątek w Development

Intuicja: instancja trzyma referencję do wstrzykniętej zależności przez całe swoje życie. Singleton żyjący godzinami przytrzymałby DbContext stworzony dla jednego żądania.

Komunikat, który zobaczysz

System.AggregateException: Some services are not able to be constructed
  (Error while validating the service descriptor
   'ServiceType: TicketAuditor Lifetime: Singleton ImplementationType: TicketAuditor':
   Cannot consume scoped service 'IScopedStamp' from singleton 'TicketAuditor'.)
   ...
   at Microsoft.AspNetCore.Builder.WebApplicationBuilder.Build()

Leci z builder.Build() — aplikacja nie wstaje. Tylko w Development: walidacja zakresów jest włączona, gdy środowisko to Development.2 Na produkcji ten sam kod wstanie bez słowa i będzie cicho gubił dane.

2 Scope validation: w Development kontener sprawdza, że scoped nie jest rozwiązywany z roota ani wstrzykiwany do singletonu.

Jak to naprawić — w tej kolejności

  1. Przekaż dane parametrem metody, zamiast wstrzykiwać je w konstruktorze. Konstruktor mówi „potrzebuję tego przez całe swoje życie”; dane jednego żądania (bieżący użytkownik, correlation id, treść requestu) takie nie są. To rozwiązuje większość przypadków.
  2. Sprawdź, czy singleton naprawdę musi być singletonem. Jeśli nie trzyma stanu współdzielonego — zejdź na Scoped i po sprawie.
  3. Dopiero na końcu: twórz scope ręcznie przez IServiceScopeFactory (patrz niżej). Potrzebne głównie w BackgroundService, gdzie nie ma żadnego żądania HTTP.
Anty-odruch: „zmienię singleton na scoped, żeby wyjątek zniknął”. Zniknie — razem z sensem serwisu. Licznik, cache czy pula połączeń tworzone od nowa na każde żądanie kompilują się, uruchamiają, nie rzucają błędem i po prostu nie działają. Ta wersja jest gorsza niż crash, bo nikt jej nie zauważy.

Wyjście awaryjne: własny scope

Singleton naprawdę potrzebujący czegoś scoped (np. background job) tworzy scope ręcznie:

public class Worker(IServiceScopeFactory scopeFactory)
{
    public void Tick()
    {
        using var scope = scopeFactory.CreateScope();
        var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();
        // ... db żyje tylko w tym bloku
    }
}

Reguła kciuka przy wyborze

  1. Serwis trzyma stan współdzielony przez wszystkich (cache, in-memory repo)? → Singleton, i zadbaj o thread-safety.
  2. Serwis trzyma stan jednego żądania (transakcja, DbContext, tożsamość usera)? → Scoped.
  3. Serwis jest bezstanowy? → Transient lub Scoped; różnica to głównie alokacje. Docs odradzają Singleton dla serwisów bez własnego stanu.
