Relacje, klucze obce i indeksy

Ściąga do druku. SQL i komunikaty błędów zweryfikowane na .NET 10.0.400, EF Core 10.0.11, SQLite 3.50.4, Windows 11.

Ćwiczone w lekcji 0011. Powiązane: EF Core + migracje, ProblemDetails, glosariusz.

Relacja jeden-do-wielu

public class Ticket
{
    public int RequesterId { get; private set; }      // foreign key property
    public Requester? Requester { get; private set; } // navigation property
}

builder
    .HasOne(t => t.Requester)
    .WithMany()
    .HasForeignKey(t => t.RequesterId)
    .OnDelete(DeleteBehavior.Restrict);
ElementZnaczenie
HasOne(t => t.Requester)ta encja ma jednego zgłaszającego
WithMany()zgłaszający ma wiele zgłoszeń; kolekcji po jego stronie nie modelujemy
WithMany(r => r.Tickets)to samo, ale z kolekcją w Requester. Dodawaj dopiero, gdy jakiś kod jej używa
HasForeignKey(t => t.RequesterId)która właściwość jest kluczem obcym
FK typu intrelacja wymagana — kolumna NOT NULL
FK typu int?relacja opcjonalna — kolumna NULL dozwolona
nawigacja Requester?nullowalność obiektu w pamięci (bez Include jest null), nie kolumny w bazie

Indeks na kolumnie FK powstaje z konwencji — nie trzeba go dopisywać ręcznie.

OnDelete — co się dzieje z dziećmi

WartośćEfekt przy usuwaniu rodzicaKiedy
Cascadedzieci znikają razem z rodzicemgdy dziecko nie ma sensu bez rodzica (pozycja zamówienia)
Restrictbaza odmawia usunięcia rodzicadane historyczne: zgłoszenia, faktury, logi
SetNullFK dziecka ustawiany na NULLtylko dla FK nullowalnego
Domyślne przy wymaganym FK jest Cascade, przy opcjonalnym ClientSetNull. Kaskadę bardzo łatwo odziedziczyć bez decyzji — jeśli dane mają wartość historyczną, wpisz Restrict jawnie.

Indeksy — cztery poziomy

builder.HasIndex(t => t.Title);                                  // szybciej szukać
builder.HasIndex(t => t.Title).IsUnique();                       // globalny zakaz duplikatu
builder.HasIndex(t => new { t.RequesterId, t.Title }).IsUnique();// unikalna PARA
builder.HasIndex(t => new { t.RequesterId, t.Title })            // unikalna para,
       .IsUnique()                                               // ale tylko wśród
       .HasFilter("\"Status\" <> 'Resolved'");                    // wierszy z warunku
ZasadaSzczegół
klucz złożony = krotkaduplikatem jest powtórzenie całej pary; (1,"X") i (2,"X") współistnieją
kolejność kolumn(A, B) przyspiesza też zapytania po samym A (prefiks), ale nie po samym B
nazwa domyślnaIX_<tabela>_<kolumna>_<kolumna>; zmiana: HasDatabaseName("…")
dwa indeksy na tych samych kolumnachdrugie HasIndex nadpisuje pierwsze; osobny indeks wymaga HasIndex(…, "nazwa")
HasIndex na kluczu głównymbłąd — PK ma już indeks; dostajesz drugi, nieunikalny, płatny przy każdym zapisie
HasFiltersurowy SQL, wklejany do CREATE INDEX … WHERE …. EF go nie parsuje

Cytowanie nazw kolumn w HasFilter

ProviderZapis
SQLite, PostgreSQL"Status" <> 'Resolved' (w C#: "\"Status\" <> 'Resolved'")
SQL Server[Status] <> 'Resolved'

Literówka w nazwie kolumny nie zatrzyma ani kompilacji, ani migrations add — wybucha dopiero database update.

NULL a unikalność

BazaDwa wiersze z NULL w indeksie unikalnym
SQLite, PostgreSQL (standard SQL)przechodzą — NULL nie równa się niczemu
SQL Serverdrugi odpada — NULL-e traktowane jak równe

Provider SQL Servera w EF Core sam dokłada filtr IS NOT NULL dla nullowalnych kolumn indeksu unikalnego; wyłącza się to przez HasFilter(null) (docs). Wniosek praktyczny: unikalność złożoną opieraj na kolumnach wymaganych, a jeśli musisz objąć nullowalną — dopisz warunek świadomie.

enum w bazie

builder.Property(t => t.Status).IsRequired().HasMaxLength(20).HasConversion<string>();

Bez HasConversion w kolumnie ląduje liczba. Tekst wybieramy, bo dane są czytelne, a warunek indeksu (<> 'Resolved') nie zmienia znaczenia po dopisaniu wartości w środek enum-a.

Migracja z relacją na SQLite

dotnet ef migrations add TicketRequester
dotnet ef migrations script InitialCreate TicketRequester   # zobacz SQL, nie ruszając bazy
dotnet ef database update
dotnet ef migrations remove                                 # cofnij OSTATNIĄ niezaaplikowaną

Ostrzeżenie przy dokładaniu kolumny NOT NULL do istniejącej tabeli — to ostrzeżenie, nie błąd:

An operation was scaffolded that may result in the loss of data. Please review the migration for accuracy.

SQLite nie ma ALTER TABLE … ADD CONSTRAINT, więc dodanie klucza obcego generuje przebudowę tabeli:

CREATE TABLE "ef_temp_Tickets" ( … CONSTRAINT "FK_…" FOREIGN KEY … ON DELETE RESTRICT );
INSERT INTO "ef_temp_Tickets" … SELECT … FROM "Tickets";
PRAGMA foreign_keys = 0;
DROP TABLE "Tickets";
ALTER TABLE "ef_temp_Tickets" RENAME TO "Tickets";
PRAGMA foreign_keys = 1;
CREATE UNIQUE INDEX … -- indeksy zakładane ponownie

Na SQL Serverze i Postgresie ta sama migracja to zwykłe ALTER TABLE.

Wymagany FK w niepustej tabeli — data migration

SQLite Error 19: 'FOREIGN KEY constraint failed'

Bierze się stąd, że nowa kolumna NOT NULL dostaje DEFAULT 0, a wygenerowane UpdateData poprawia tylko wiersze znane z HasData. Reszta zostaje z RequesterId = 0 i przy zakładaniu FK nie ma na co wskazywać. Lekarstwo — dopisać do migracji, po InsertData rodziców, a przed FK:

migrationBuilder.Sql("""
    UPDATE Tickets SET RequesterId = 1 WHERE RequesterId = 0;
    """);

migrationBuilder.Sql("""
    UPDATE Tickets SET Status = 'Open' WHERE Status = '';
    """);
PułapkaObjaw
osierocony FK (0)migracja pada od razu — FOREIGN KEY constraint failed
pusty string w kolumnie enum-amigracja przechodzi, wywala się dopiero odczyt encji

Reguła: dodaj kolumnę → uzupełnij dane → nałóż ograniczenie, w tej kolejności, w razie potrzeby w osobnych migracjach. Nieudana migracja cofa się w całości (transakcja) — poza operacjami takimi jak PRAGMA foreign_keys = 0, o których EF ostrzega osobno.
