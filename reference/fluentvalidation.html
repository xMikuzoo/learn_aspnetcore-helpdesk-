FluentValidation i pipeline behavior

Ściąga do druku. API wg dokumentacji FluentValidation; kod i odpowiedzi zweryfikowane na .NET 10.0.400 i FluentValidation 12.1.1.

Ćwiczone w lekcji 0008. Format błędu: ściąga ProblemDetails.

Pakiet

dotnet add package FluentValidation.DependencyInjectionExtensions

FluentValidation.AspNetCore jest porzucony — nie instalować.

Walidator

public class CreateTicketValidator : AbstractValidator<CreateTicketCommand>
{
    public CreateTicketValidator()
    {
        RuleFor(c => c.Title)
            .NotEmpty().WithMessage("Tytuł zgłoszenia nie może być pusty.")
            .MaximumLength(100).WithMessage("Tytuł zgłoszenia może mieć najwyżej 100 znaków.");

        RuleFor(c => c.Priority)
            .NotEmpty().WithMessage("Priorytet jest wymagany.")
            .Must(TicketPriority.IsAllowed).WithMessage("Priorytet musi być jedną z wartości: low, normal, high.");
    }
}

Jeden walidator na jedną komendę, plik obok komendy w slice’ie. Walidujemy command, nie request — bo to command przechodzi przez dispatcher.

Reguły, które się przydają

RegułaSprawdza
NotEmpty()nie null, nie pusty string, nie same białe znaki, nie wartość domyślna
NotNull()tylko null (pusty string przechodzi)
MaximumLength(n) / MinimumLength(n)długość tekstu
GreaterThan(0), InclusiveBetween(a, b)zakresy liczb i dat
EmailAddress(), Matches(regex)format tekstu
Must(predykat)dowolna własna reguła zwracająca bool
MustAsync(...)reguła z I/O — ostrożnie, patrz niżej
When(warunek)reguła obowiązuje tylko w danym przypadku
RuleForEach(c => c.Items)reguły dla każdego elementu kolekcji
Domyślnie łańcuch reguł nie przerywa się po pierwszym błędzie — jedno pole może zwrócić kilka komunikatów. .Cascade(CascadeMode.Stop) zmienia to dla danej reguły.

Pipeline behavior (dekorator ISender)

private async Task ValidateAsync(object message, CancellationToken ct)
{
    var validatorType = typeof(IValidator<>).MakeGenericType(message.GetType());
    var validators = provider.GetServices(validatorType).Cast<IValidator>();
    var context = new ValidationContext<object>(message);

    var failures = new List<ValidationFailure>();

    foreach (var validator in validators)
    {
        failures.AddRange((await validator.ValidateAsync(context, ct)).Errors);
    }

    if (failures.Count > 0)
    {
        throw new ValidationException(failures);
    }
}

W MediatR to samo nazywa się IPipelineBehavior<TRequest, TResponse> z metodą Handle(request, next, ct); next() odpowiada wywołaniu inner.Send(...). Inne typowe behaviory: logowanie, transakcja, pomiar czasu.

Rejestracja

services.AddScoped<Sender>();                          // prawdziwy dispatcher pod własnym typem

services.AddValidatorsFromAssemblyContaining<Program>();  // skan: każdy AbstractValidator<>

services.AddProblemDetails();
services.AddExceptionHandler<ValidationExceptionHandler>();
services.AddExceptionHandler<DomainExceptionHandler>();
GetServices na brak walidatora zwraca pustą listę, nie wyjątek. Zapomniany AddValidation() nie objawia się niczym — API po prostu przyjmuje śmieci ze statusem 201.
