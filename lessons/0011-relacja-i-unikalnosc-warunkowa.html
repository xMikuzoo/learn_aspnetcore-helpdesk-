Lekcja 0011 · ~25 min · projekt Helpdesk

Relacja, klucz obcy i unikalność warunkowa

Cel: zamodelować regułę „ten sam zgłaszający nie może mieć dwóch nierozwiązanych zgłoszeń o tym samym tytule” — i wiedzieć, dlaczego zwykły IsUnique() na Title jest do tego za tępy.

Wymaga: lekcji 0009 (EF Core, migracje), 0007 (DomainException). Ściągi: relacje i indeksy, EF Core + migracje, curl.

Reguła, którą modelujemy

Do tej pory unikalność w Helpdesku była globalna i naiwna: żadne dwa zgłoszenia nie mogą mieć tego samego tytułu. To reguła nie do obrony. „Drukarka nie drukuje” zgłasza pół firmy, i to co miesiąc. Prawdziwa reguła ma dwa wymiary:

Jeden zgłaszający nie może mieć dwóch nierozwiązanych zgłoszeń o tym samym tytule. Inny zgłaszający — może. Ten sam zgłaszający po zamknięciu poprzedniego — też może.

Trzy niezależne rzeczy do zrobienia, każda uczy czegoś innego:

ElementNarzędzieCzego uczy
„zgłaszający” musi istnieć jako bytencja Requester + klucz obcyrelacja, HasOne/WithMany, OnDelete
unikalność w obrębie zgłaszającegoindeks złożony (RequesterId, Title)klucz naturalny z wielu kolumn
„nierozwiązanych”HasFilter(...) — indeks częściowyograniczenie zależne od stanu wiersza
Znasz to z Prismy jako @@unique([requesterId, title]). Czego Prisma nie ma w schemacie: warunku. Trzeci wymiar — „tylko dla wierszy spełniających warunek” — w Prismie robi się surowym SQL-em dopisanym do migracji. Tutaj jest jedną metodą fluent API.

Krok 1 — relacja: Ticket ma zgłaszającego

Features/Requesters/Requester.cs

public class Requester
{
    private Requester(string login, string displayName)
    {
        Login = login;
        DisplayName = displayName;
    }

    public int Id { get; private set; }
    public string Login { get; private set; }
    public string DisplayName { get; private set; }

    public static Requester Create(string login, string displayName) => new(login, displayName);

Login to ta sama wartość, którą HeaderCurrentUser czyta z nagłówka X-User (lekcja 0002). Nagłówek zostaje udawaniem logowania — ale od teraz wskazuje na wiersz w bazie, nie na luźny string.

Features/Tickets/Ticket.cs — nowe pola

public TicketStatus Status { get; private set; }
public int RequesterId { get; private set; }
public Requester? Requester { get; private set; }

public void Resolve() => Status = TicketStatus.Resolved;
ElementPo co
RequesterId — foreign key propertykolumna w tabeli. Po niej filtrujesz i ją wpisujesz przy tworzeniu, bez dociągania drugiej encji
Requester — navigation propertyobiekt po drugiej stronie. Wypełniony tylko wtedy, gdy poprosisz o Include

Features/Tickets/TicketConfiguration.cs

builder
    .HasOne(t => t.Requester)
    .WithMany()
    .HasForeignKey(t => t.RequesterId)
    .OnDelete(DeleteBehavior.Restrict);

WithMany() bez argumentu znaczy: „zgłaszający ma wiele zgłoszeń, ale kolekcji po jego stronie nie modeluję”. Nie dodawaj List<Ticket> Tickets do Requester, dopóki nie masz kodu, który jej używa — kolekcja bez odbiorcy to zaproszenie do przypadkowego wciągnięcia całej tabeli.

Restrict, nie domyślny Cascade. Przy wymaganym kluczu obcym (int, nie int?) EF domyślnie ustawia kaskadę: usunięcie zgłaszającego skasuje wszystkie jego zgłoszenia. Dla danych o wartości historycznej — zgłoszenia, faktury, logi — to prawie zawsze błąd. Restrict sprawia, że baza odmówi usunięcia zgłaszającego, który ma zgłoszenia.

Krok 2 — status jako enum, w bazie jako tekst

public enum TicketStatus { Open, InProgress, Resolved }

builder.Property(t => t.Status).IsRequired().HasMaxLength(20).HasConversion<string>();

Bez HasConversion<string>() EF zapisałby enum jako liczbę i w bazie stałoby 0, 1, 2. Zapisujemy tekst z dwóch powodów: dane dają się czytać bez zaglądania do kodu, a — co ważniejsze za chwilę — warunek indeksu piszesz w SQL-u, więc lepiej, żeby brzmiał <> 'Resolved' niż <> 2. Numer zmieni znaczenie w dniu, w którym ktoś wstawi nową wartość w środek enum-a.

Krok 3 — trzy poziomy „unikalności”

To jest sedno lekcji. Ta sama reguła, trzy różne siły:

ZapisCo zabrania
HasIndex(t => t.Title).IsUnique()dwóch zgłoszeń o tym samym tytule — w całej firmie, na zawsze
HasIndex(t => new { t.RequesterId, t.Title }).IsUnique()dwóch zgłoszeń tego samego zgłaszającego o tym samym tytule — na zawsze
… .IsUnique().HasFilter("…")dwóch nierozwiązanych zgłoszeń tego samego zgłaszającego o tym samym tytule

Indeks złożony to para kolumn traktowana jako jeden klucz. Duplikatem jest dopiero powtórzenie całej pary: (1, "Drukarka") i (2, "Drukarka") to dwie różne wartości, więc oba wiersze przechodzą. Dwa osobne indeksy unikalne dałyby coś zupełnie innego — zakaz dwóch zgłoszeń tego samego zgłaszającego w ogóle i zakaz dwóch o tym samym tytule w ogóle.

Kolejność kolumn nie jest kosmetyką. Indeks (RequesterId, Title) przyspiesza też zapytania filtrujące po samym RequesterId — po prefiksie. Ale nie po samym Title. Gdybyś częściej szukał po tytule niż po zgłaszającym, kolejność powinna być odwrotna; unikalność wyszłaby identyczna. EF Core docs — composite index

Indeks częściowy (filtered / partial index)

HasFilter przyjmuje surowy SQL, wklejany do CREATE INDEX … WHERE …. EF go nie parsuje i nie tłumaczy — nie sprawdzi nawet, czy taka kolumna istnieje. Konsekwencje dwie: składnia zależy od providera ("Status" w SQLite i Postgresie, [Status] w SQL Serverze), a literówka wyjdzie dopiero przy database update.

Wiersz, który nie spełnia warunku, po prostu nie istnieje dla indeksu. Rozwiązanie zgłoszenia usuwa je z indeksu i zwalnia parę — dlatego reguła „dopóki poprzednie nie zostanie rozwiązane” wychodzi tu za darmo, bez żadnego kodu sprzątającego.

Krok 4 — pułapka: NULL w kluczu złożonym

Weź inny wariant tej samej historii: kolumna AssigneeId jest nullowalna, bo świeże zgłoszenie nie ma jeszcze właściciela, a ty robisz na niej indeks złożony (AssigneeId, Title). Sprawdziłem, co robi wtedy SQLite (3.50.4):

CREATE UNIQUE INDEX ix ON t (assignee, title);
INSERT INTO t (assignee, title) VALUES (NULL, 'drukarka');   -- ok
INSERT INTO t (assignee, title) VALUES (NULL, 'drukarka');   -- TEŻ ok. Dwa wiersze.
INSERT INTO t (assignee, title) VALUES (1, 'drukarka');      -- ok
INSERT INTO t (assignee, title) VALUES (1, 'drukarka');      -- UNIQUE constraint failed

W standardzie SQL NULL znaczy „nieznane”, a dwie nieznane wartości nie są sobie równe — więc indeks unikalny ich nie porównuje. Twoja reguła przestaje obowiązywać dokładnie tam, gdzie zwykle jest najbardziej potrzebna: wśród zgłoszeń jeszcze nieprzypisanych.

I to zachowuje się różnie w różnych bazach. SQL Server idzie pod prąd standardu: traktuje NULL-e jako równe i dopuszcza tylko jeden taki wiersz. EF Core to za ciebie łata — „When using the SQL Server provider EF adds an 'IS NOT NULL' filter for all nullable columns that are part of a unique index” (EF Core docs — index filter). Ten sam kod C# daje więc inny SQL i inną regułę na SQLite niż na SQL Serverze. Jeśli w firmowym repo zobaczysz unikalny indeks na nullowalnej kolumnie — warto sprawdzić, czy autor o tym wiedział.

W naszej regule problemu nie ma, bo RequesterId jest wymagany (int). To nie przypadek: unikalność złożona ma sens tylko na kolumnach, które nie bywają puste.

Krok 5 — co robi migracja (i dlaczego straszy)

dotnet ef migrations add TicketRequester
An operation was scaffolded that may result in the loss of data. Please review the migration for accuracy.

To ostrzeżenie, nie błąd. Bierze się stąd, że dokładasz kolumnę NOT NULL do istniejącej tabeli (EF wstawi w starych wierszach defaultValue: 0) i że SQLite musi przebudować tabelę. Zajrzyj w SQL, żeby zobaczyć tę przebudowę:

dotnet ef migrations script InitialCreate TicketRequester
CREATE UNIQUE INDEX "IX_Tickets_RequesterId_Title" ON "Tickets" ("RequesterId", "Title")
    WHERE "Status" <> 'Resolved';

CREATE TABLE "ef_temp_Tickets" ( … CONSTRAINT "FK_Tickets_Requesters_RequesterId"
    FOREIGN KEY ("RequesterId") REFERENCES "Requesters" ("Id") ON DELETE RESTRICT );
INSERT INTO "ef_temp_Tickets" … SELECT … FROM "Tickets";
PRAGMA foreign_keys = 0;
DROP TABLE "Tickets";
ALTER TABLE "ef_temp_Tickets" RENAME TO "Tickets";
PRAGMA foreign_keys = 1;
CREATE UNIQUE INDEX "IX_Tickets_RequesterId_Title" … -- drugi raz, już na nowej tabeli

SQLite nie umie ALTER TABLE … ADD CONSTRAINT, więc EF robi kopię tabeli, przenosi dane, kasuje oryginał, przemianowuje kopię — i zakłada indeksy ponownie. Na SQL Serverze i Postgresie ta sama migracja to zwykłe ALTER TABLE. Zapamiętaj to jako regułę ogólną: migracja jest kodem generowanym pod konkretny dialekt i warto ją przeczytać, zanim pojedzie na produkcję.

Gdy tabela nie jest pusta — data migration

Ta migracja wykłada się na prawdziwej bazie i to jest najcenniejsza rzecz w całej lekcji:

Applying migration '20260908074810_TicketRequester'.
ALTER TABLE "Tickets" ADD "RequesterId" INTEGER NOT NULL DEFAULT 0;
ALTER TABLE "Tickets" ADD "Status" TEXT NOT NULL DEFAULT '';
…
INSERT INTO "ef_temp_Tickets" (…) SELECT … FROM "Tickets";
SQLite Error 19: 'FOREIGN KEY constraint failed'

Prześledź, co się stało. Nowa kolumna NOT NULL musi mieć czym wypełnić istniejące wiersze, więc EF wpisuje im DEFAULT 0. Potem UpdateData poprawia wiersze o identyfikatorach 1 i 2 — bo tylko te zna z HasData. Zgłoszenia, które utworzyłeś sam curlem w lekcji 0009, zostają z RequesterId = 0. Za chwilę pojawia się klucz obcy, przy jego zakładaniu dane są przepisywane do nowej tabeli — i baza pyta: gdzie jest zgłaszający o identyfikatorze 0? Nigdzie.

Dobra wiadomość: nic się nie zepsuło. Cała migracja jechała w transakcji, więc odpadła w całości — w __EFMigrationsHistory dalej jest sam InitialCreate, tabela Tickets jest bez nowych kolumn, ef_temp_Tickets nie istnieje. Poprawiasz i puszczasz jeszcze raz. Wyjątkiem jest PRAGMA foreign_keys = 0, o którym EF ostrzega osobno („cannot be executed in a transaction”) — to jedyny fragment poza transakcją.

Rozwiązanie: domigrowanie danych. Wygenerowaną migrację wolno edytować — dopisz Sql(...) po InsertData ze zgłaszającymi (muszą już istnieć), a przed założeniem klucza obcego:

migrationBuilder.Sql(
    """
    UPDATE Tickets
    SET RequesterId = 1
    WHERE RequesterId = 0;
    """);

migrationBuilder.Sql(
    """
    UPDATE Tickets
    SET Status = 'Open'
    WHERE Status = '';
    """);

Drugi UPDATE jest równie ważny, choć niczego nie wysadza. Domyślną wartością dla Status był pusty string — a "" nie odpowiada żadnej wartości TicketStatus. Bez tej poprawki migracja przechodzi, aplikacja startuje, i dopiero pierwszy GET /tickets wywala się przy materializacji encji. Cicha awaria, odroczona o kilka minut.

To jest cała różnica między nauką a produkcją. Na pustej bazie ta migracja przechodzi bez mrugnięcia — wszystkie wiersze są z HasData, więc UpdateData ogarnia komplet. Prawdziwa baza ma dane, których autor migracji nie zna. Dlatego każde „dodaj wymaganą kolumnę / wymagany klucz obcy” to w istocie trzy kroki: dodaj kolumnę → uzupełnij dane → dopiero potem nałóż ograniczenie. Zespoły często rozbijają to nawet na osobne migracje, żeby dało się wdrażać etapami.

Zostaje pytanie, na które kod nie odpowie: czyje właściwie są osierocone zgłoszenia? Tutaj wpisujemy 1, bo to twoje własne dane testowe. W pracy odpowiedź brzmi zwykle „konto techniczne system/migrated” — i jest decyzją do uzgodnienia z kimś, kto zna dane, nie do zgadnięcia w locie.

db.Tickets.AnyAsync(t =>

Quiz

Indeks (RequesterId, Title) jest unikalny. Wstawiasz (1, "Drukarka"), potem (2, "Drukarka"). Co się dzieje?
Kluczem indeksu jest krotka. (1, "Drukarka") i (2, "Drukarka") to dwie różne wartości klucza. Zakaz dotyczy dopiero drugiego (1, "Drukarka").
Kolumna AssigneeId jest nullowalna i wchodzi w unikalny indeks. Dwa wiersze z NULL i tym samym tytułem — SQLite:
Sprawdzone empirycznie na SQLite 3.50.4: oba wiersze wchodzą. NULL nie jest równy niczemu, także drugiemu NULL-owi. SQL Server robi odwrotnie — i dlatego EF dokłada tam filtr IS NOT NULL.
Po co zostawiać sprawdzenie w handlerze, skoro indeks i tak nie przepuści duplikatu?
Indeks jest gwarancją i łapie też wyścigi oraz zapisy z innych miejsc, ale mówi wyjątkiem bazodanowym. Handler zna kontekst i produkuje sensowną odpowiedź HTTP. Dwie różne role, oba potrzebne.
Wpisujesz w HasFilter nazwę kolumny z literówką. Kiedy się o tym dowiesz?
HasFilter bierze string i wkleja go do CREATE INDEX. EF nie zagląda w środek. Kompilacja przechodzi, migrations add przechodzi, wywala się dopiero baza przy database update.

Zapamiętaj bez zaglądania

Czym różni się indeks złożony od dwóch osobnych indeksów?

Złożony traktuje kolumny jako jeden klucz: unikalna musi być cała para, nie każda kolumna z osobna. Dwa osobne indeksy unikalne zabroniłyby dwóch zgłoszeń tego samego zgłaszającego w ogóle i dwóch o tym samym tytule w ogóle. Przy szukaniu złożony działa też po prefiksie — (A, B) pomaga zapytaniu po samym A, nie po samym B.

Reguła zależna od stanu wiersza — czym ją wyrazić?

HasFilter("…") — indeks częściowy. Wiersze niespełniające warunku nie istnieją dla indeksu, więc zmiana stanu (rozwiązanie zgłoszenia) sama zwalnia parę. Warunek to surowy SQL: "Status" w SQLite i Postgresie, [Status] w SQL Serverze.

Dwa wiersze z NULL w kolumnie objętej indeksem unikalnym — przejdą?

W SQLite i Postgresie tak (NULL ≠ NULL). W SQL Serverze nie — dlatego provider SQL Servera w EF sam dokłada filtr IS NOT NULL dla nullowalnych kolumn indeksu unikalnego. Ten sam kod C#, inna reguła w bazie.

Po co sprawdzenie w handlerze, skoro indeks i tak nie przepuści?

Handler daje 409 z komunikatem, indeks daje 500. Ale handler przepuści wyścig dwóch równoległych żądań i nie obowiązuje zapisów z innych miejsc. Uprzejmość w kodzie, gwarancja w bazie — potrzebne oba.

Dlaczego enum zapisujemy jako tekst, a nie liczbę?

HasConversion<string>(). Warunek indeksu jest surowym SQL-em: <> 'Resolved' przeżyje dopisanie nowej wartości do enum-a, <> 2 zacznie po cichu znaczyć co innego, gdy ktoś wstawi wartość w środek.

Dodajesz wymagany klucz obcy do tabeli, w której już są dane. Co musi się stać po drodze?

Trzy kroki, nie jeden: dodaj kolumnę (z wartością domyślną), uzupełnij istniejące wiersze własnym migrationBuilder.Sql("UPDATE …"), dopiero potem nałóż klucz obcy. Bez środkowego kroku wiersze zostają z 0 i migracja pada na FOREIGN KEY constraint failed. UpdateData wygenerowane przez EF poprawia wyłącznie wiersze z HasData.

WithMany() bez argumentu — co to znaczy?

Że po drugiej stronie relacji jest „wiele”, ale kolekcji w encji nadrzędnej nie modelujemy. Relacja w bazie wychodzi identyczna; różnica jest tylko w tym, czy z kodu da się przejść z Requester do jego zgłoszeń.

Źródło pierwotne

EF Core — Indexes (ok. 10 min; sekcje Composite index, Index uniqueness, Index filter), a potem One-to-many relationships — najgęstsza strona o HasOne/WithMany/HasForeignKey. Dla tła o kaskadach: Cascade delete.
