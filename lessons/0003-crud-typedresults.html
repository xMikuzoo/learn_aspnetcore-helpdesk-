Lekcja 0003 · ~20 min · projekt Helpdesk

Pełny CRUD: ciało żądania, kody statusu, grupy tras

Cel: domknąć /tickets jako prawdziwe API — POST z JSON-em zamiast query stringa, 201 z nagłówkiem Location, 204 przy PUT i DELETE, i jedna grupa tras zamiast powtarzanego prefiksu. Po tej lekcji Program.cs będzie na tyle długi, że zaczniesz chcieć go rozbić — o tym jest lekcja 0004.

Wymaga: lekcji 0002 (ITicketStore w DI). Ściąga: Minimal API — routing, binding, wyniki.

Trzy rzeczy, które są dziś nie tak

Twoje endpointy działają, ale kłamią klientowi. Konkretnie:

TerazProblem
POST /tickets?title=TestDane wejściowe w URL-u. Trafiają do logów serwera i historii przeglądarki, nie da się wysłać zagnieżdżonego obiektu, a znaki specjalne trzeba kodować.
POST zwraca 200 OKKlient nie wie, że powstał nowy zasób ani pod jakim adresem go szukać.
Prefiks /tickets w każdej liniiCztery kopie tego samego stringa. Zmiana na /api/tickets to cztery edycje i jedna szansa na literówkę.

Krok 1: ciało żądania zamiast query stringa

Dodaj plik z dwoma typami — to DTO, obiekty opisujące kształt żądania:

project/Helpdesk/TicketRequests.cs

public record CreateTicketRequest(string Title);
public record UpdateTicketRequest(string Title);

Teraz w handlerze bierzesz je zamiast string title:

app.MapPost("/tickets", (CreateTicketRequest request, ITicketStore store) => …);

Nie musisz nic konfigurować — typ złożony, którego nie ma w kontenerze DI, jest deserializowany z ciała żądania jako JSON. To domyślna reguła bindera, ta sama, która w lekcji 0002 kazała mu sięgnąć do kontenera po ITicketStore. Pełna tabelka źródeł jest w ściądze.

Dlaczego dwa niemal identyczne rekordy? Bo za chwilę zaczną się różnić. CreateTicketRequest nigdy nie dostanie Id (serwer je nadaje), a UpdateTicketRequest prędzej czy później dostanie Status albo AssignedTo. Gdyby oba endpointy przyjmowały Ticket, klient mógłby przysłać własne Id i nadpisać cudze zgłoszenie. Rozdzielanie DTO od encji to nie ceremoniał — to granica zaufania.

Krok 2: TypedResults i prawdziwe kody statusu

Do tej pory używałeś Results.Ok() i Results.NotFound(). Ich typ zwracany to IResult — czyli „coś, co umie zapisać odpowiedź”. TypedResults zwraca konkretne typy: Ok<Ticket>, NotFound, Created<Ticket>. Dokumentacja mówi wprost, że są preferowane.1

1 „Returning TypedResults is preferred to returning Results” — Built-in results. Powody: metadane dla OpenAPI powstają same i da się testować bez rzutowania.

Jest jeden haczyk. To się nie skompiluje:

app.MapGet("/tickets/{id:int}", (int id, ITicketStore store) =>
    store.GetById(id) is { } t ? TypedResults.Ok(t) : TypedResults.NotFound());

Ok<Ticket> i NotFound to dwie niepowiązane klasy — ternary nie ma wspólnego typu do wybrania. Przy Results.* problemu nie było, bo oba zwracały IResult. Rozwiązanie: zadeklaruj typ zwracany lambdy jawnie:

using Microsoft.AspNetCore.Http.HttpResults;   // na górze Program.cs

app.MapGet("/tickets/{id:int}",
    Results<Ok<Ticket>, NotFound> (int id, ITicketStore store) =>
        store.GetById(id) is { } ticket
            ? TypedResults.Ok(ticket)
            : TypedResults.NotFound());

Typ stoi przed nawiasem z parametrami — jedyne miejsce w C#, gdzie zobaczysz taką składnię przy lambdzie. Czyta się to jak sygnaturę: „ten endpoint zwraca albo 200 z Ticket, albo 404”. Frontendowo: to jest Promise<Ticket | null> zapisane w typie, a nie w komentarzu.

is { } ticket to skrót od „nie jest nullem — i nazwij to ticket”. Zastępuje var t = …; if (t is not null).

Krok 3: komplet operacji

Dołóż do ITicketStore dwie metody. Zwracają bool — „udało się / nie było takiego”:

bool Update(int id, string title);
bool Delete(int id);

W InMemoryTicketStore:

public bool Update(int id, string title)
{
    var index = _tickets.FindIndex(t => t.Id == id);
    if (index < 0) return false;
    _tickets[index] = _tickets[index] with { Title = title };
    return true;
}

public bool Delete(int id) => _tickets.RemoveAll(t => t.Id == id) > 0;

_tickets[index] with { Title = title } to with-expression: tworzy kopię rekordu ze zmienionym jednym polem. Dokładnie jak { ...ticket, title } w JS. Rekord jest niezmienny, więc nie da się przypisać do ticket.Title — trzeba podmienić cały obiekt w liście.

Krok 4: grupa tras

Na koniec sprzątanie. Zamiast czterech razy "/tickets…":

var tickets = app.MapGroup("/tickets");

tickets.MapGet("/", (ITicketStore store) => TypedResults.Ok(store.GetAll()));

tickets.MapGet("/{id:int}",
    Results<Ok<Ticket>, NotFound> (int id, ITicketStore store) =>
        store.GetById(id) is { } ticket ? TypedResults.Ok(ticket) : TypedResults.NotFound());

tickets.MapPost("/", (CreateTicketRequest request, ITicketStore store,
                     TicketMetrics metrics, ICurrentUser user) =>
{
    var ticket = store.Add(request.Title);
    metrics.RecordCreated(user);
    return TypedResults.Created($"/tickets/{ticket.Id}", ticket);
});

tickets.MapPut("/{id:int}",
    Results<NoContent, NotFound> (int id, UpdateTicketRequest request, ITicketStore store) =>
        store.Update(id, request.Title) ? TypedResults.NoContent() : TypedResults.NotFound());

tickets.MapDelete("/{id:int}",
    Results<NoContent, NotFound> (int id, ITicketStore store) =>
        store.Delete(id) ? TypedResults.NoContent() : TypedResults.NotFound());

MapGroup zwraca RouteGroupBuilder — obiekt, na którym można ustawić coś dla całej grupy: .RequireAuthorization(), .WithTags("Tickets"), filtry. To ten sam mechanizm, którym w lekcji 0004 rozniesiemy endpointy do osobnych plików.

Co zmienia {id:int}

Dopisanie ograniczenia zmienia zachowanie, które widziałeś w lekcji 0001. Zweryfikowane:

TrasaGET /tickets/abcDlaczego
/tickets/{id}400 Bad Requesttrasa pasuje, binding int się wywraca
/tickets/{id:int}404 Not Foundtrasa w ogóle nie pasuje — routing nie ma dokąd pójść

Dla API zwykle chcesz 404: „nie ma takiego zasobu” jest bliższe prawdy niż „źle sformułowałeś żądanie”.

Krok 5: dług z lekcji 0002 — lock

W lekcji 0002 zostało pytanie bez odpowiedzi: InMemoryTicketStore jest singletonem, obsługuje żądania równolegle na różnych wątkach, a List<T> nie jest thread-safe. Teraz, gdy doszły zapisy i usuwanie, to przestaje być teoretyczne.

public class InMemoryTicketStore : ITicketStore
{
    private readonly Lock _gate = new();
    private readonly List<Ticket> _tickets = [ … ];

    public IReadOnlyList<Ticket> GetAll()
    {
        lock (_gate) return _tickets.ToList();
    }

    public Ticket Add(string title)
    {
        lock (_gate)
        {
            // …
        }
    }
    // tak samo GetById, Update, Delete
}

Trzy rzeczy, które łatwo przeoczyć:

  • Odczyt też trzeba osłonić. Czytanie listy w trakcie cudzego zapisu to wyścig, nie tylko dwa równoczesne zapisy.
  • GetAll zwraca kopię (.ToList()). Bez tego oddajesz referencję do żywej listy, a wołający iteruje ją już poza lock — i dostaje InvalidOperationException: Collection was modified, gdy ktoś w tym czasie doda zgłoszenie.
  • Lock to typ z System.Threading (nowość .NET 9). Starszy kod firmowy blokuje na zwykłym private readonly object _gate = new(); — działa tak samo.

To samo w TicketMetrics, ale taniej

Twój licznik ma teraz jedną linię, która wygląda niewinnie:

private int _created;

public void RecordCreated(ICurrentUser user)
{
    _created++;
}

_created++ to trzy operacje procesora: odczytaj z pamięci, dodaj 1, zapisz z powrotem. Dwa wątki mogą wejść jednocześnie:

Wątek AWątek B_created
czyta 77
czyta 77
zapisuje 88
zapisuje 88

Dwa POST-y, jedno zliczenie. /metrics kłamie. Poprawka to podmiana jednej linii:

Interlocked.Increment(ref _created);

Interlocked (z System.Threading) robi całą trójkę jako jedną niepodzielną instrukcję procesora — nikt się nie wcina w środek. ref znaczy „daj mi adres tego pola, nie kopię wartości” — bez tego metoda dostałaby liczbę i nie miałaby czego zmienić.

Dlaczego nie lock? Bo można, tylko drożej: lock to obiekt synchronizacyjny i potencjalne uśpienie wątku, Interlocked to jedna instrukcja sprzętowa. Dla samego licznika to overkill. Reguła: jedna liczba → Interlocked, cała kolekcja albo kilka pól naraz → lock.

Odczyt public int Created => _created; zostaw jak jest — czytanie int jest atomowe samo z siebie.

W JS tego problemu nie miałeś: event loop jest jednowątkowy, więc między const n = counter a counter = n + 1 nikt ci się nie wcina. ASP.NET Core obsługuje żądania naprawdę równolegle, na puli wątków. To pierwsza rzecz z tego kursu, która nie ma odpowiednika po stronie frontu.

Przy EF Core (lekcja 0009) problem zniknie u źródła: DbContext jest Scoped, każde żądanie ma własny, nie ma czego blokować. To jest właśnie powód, dla którego jest Scoped.

Krok 6: skąd biorą się Id

Zostało jedno miejsce, którego nikt jeszcze nie ruszył. Twój Add nadaje identyfikator tak:

var ticket = new Ticket(_tickets.Count + 1, title);

Do lekcji 0002 to działało, bo zgłoszeń tylko przybywało. W tej lekcji dodałeś Delete — i założenie się rozpadło. Zweryfikowane na działającej aplikacji:

Od tej chwili GET /tickets/3 zwraca pierwsze pasujące zgłoszenie, a DELETE /tickets/3 kasuje oba naraz (RemoveAll). Zasób przestał być jednoznacznie adresowalny — czyli API przestało być REST-owe w najbardziej podstawowym sensie.

Sedno: Count opisuje ile rzeczy jest teraz, a identyfikator musi być pochodną ile rzeczy kiedykolwiek powstało. To dwie różne liczby w każdym systemie, który cokolwiek usuwa. Prawdziwa baza rozwiązuje to sekwencją albo IDENTITY — licznikiem, który nigdy nie cofa się po DELETE.

Sprawdź się

Odpowiedz zanim klikniesz. Zła odpowiedź nie zdradza dobrej — spróbuj jeszcze raz.

Handler ma zwracać Ok<Ticket> albo NotFound. Co jest konieczne?
To dwie niepowiązane klasy, więc ternary nie ma wspólnego typu do wywnioskowania. Results<Ok<Ticket>, NotFound> przed listą parametrów mówi kompilatorowi, jaka jest unia. Przy Results.* problem nie występuje, bo wszystko jest IResult.
Po DELETE zwracającym 204 frontend woła res.json(). Co się stanie?
204 znaczy „bez treści” — ciało jest fizycznie puste, a JSON.parse("") rzuca. Sprawdzaj res.status albo res.ok i nie parsuj. To najczęstsze zderzenie frontu z backendem przy DELETE.
Do czego służy nagłówek Location w odpowiedzi 201?
To adres, pod którym utworzony zasób jest dostępny — u nas /tickets/3. Klient może po nim przejść do szczegółów bez zgadywania URL-a. Przekierowania to 3xx; przy 201 przeglądarka nigdzie nie skacze.
Skąd binder weźmie parametr CreateTicketRequest request?
Typ złożony, którego nie ma w DI, jest deserializowany z body. Gdybyś zarejestrował go w builder.Services, binder wziąłby go z kontenera — dokładnie ta pomyłka daje potem „dlaczego moje pola są puste”.
Dlaczego _created++ w singletonie potrafi zgubić zliczenie?
Trzy operacje, nie jedna. Dwa wątki mogą odczytać tę samą wartość, zanim którykolwiek zdąży zapisać — obydwa zapiszą tę samą liczbę. Interlocked.Increment(ref _created) robi całość jako jedną instrukcję procesora.
Czym różni się TypedResults.Ok(x) od Results.Ok(x)?

Wysyłają identyczną odpowiedź HTTP. Różnica jest w typie zwracanym: Results.Ok daje IResult, TypedResults.Ok daje Ok<T>. Konkretny typ pozwala frameworkowi wygenerować metadane OpenAPI bez .Produces(), a testowi sprawdzić wynik bez rzutowania.

Kiedy 201, kiedy 204, kiedy 200?

201 — POST utworzył nowy zasób; adres idzie w nagłówku Location. 204 — operacja się udała i nie ma nic do zwrócenia (typowo PUT i DELETE). 200 — zwracasz zasób albo kolekcję.

Dlaczego _tickets.Count + 1 to zły sposób nadawania Id?

Count mówi, ile elementów jest teraz. Identyfikator musi wynikać z tego, ile ich kiedykolwiek powstało. Po DELETE te liczby się rozjeżdżają i kolejne Add nadaje Id, które już istnieje.

Dlaczego GetAll() zwraca kopię listy zamiast samej listy?

Bo store jest singletonem. Oddając referencję do żywej listy, pozwalasz wołającemu iterować ją poza lock — a inne żądanie może w tym czasie dodać element i wywołać InvalidOperationException: Collection was modified.
