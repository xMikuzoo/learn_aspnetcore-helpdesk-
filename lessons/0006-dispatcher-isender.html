Lekcja 0006 · ~25 min · projekt Helpdesk

Dispatcher: jeden ISender zamiast dwudziestu handlerów

Cel: napisać własny mediator — trzydzieści linii, po których endpoint przestaje znać typ handlera i mówi tylko sender.Send(command). Po drodze zobaczysz, czym MediatR jest naprawdę, i co dokładnie tracisz, oddając mu wywołanie.

Wymaga: lekcji 0005 (handlery) i struktury Commands/ / Queries/. Ściąga: Dispatcher / ISender.

Problem: endpoint zna handlera po imieniu

Tak wygląda dziś twój endpoint tworzenia zgłoszenia:

private static async Task<Created<TicketDto>> HandleAsync(
    CreateTicketRequest request,
    ICommandHandler<CreateTicketCommand, TicketDto> handler,
    CancellationToken cancellationToken)

Ta druga linia to cały problem. Sześć endpointów — sześć różnych typów wstrzykiwanych w sześciu miejscach; przy dwudziestu przypadkach użycia dwadzieścia. I trzy konkretne bolączki:

  • Zmiana typu wyniku dotyka dwóch plików. Handler zaczyna zwracać Result<TicketDto> zamiast TicketDto — poprawiasz handler i deklarację parametru w endpoincie. Kompilator ci przypomni, ale to robota mechaniczna.
  • Nie ma gdzie wpiąć kodu wspólnego. „Loguj każdy command”, „waliduj każdy command”, „każdy command w transakcji” — nie ma jednego miejsca, przez które przechodzą wszystkie. Trzeba by dopisać to do dwudziestu handlerów.
  • Endpoint zna szczegół implementacyjny. Że istnieje typ ICommandHandler<,>, że ma dwa parametry, że wynik jest tym drugim. Endpoint ma robić HTTP, nie znać architekturę warstwy niżej.

Docelowo chcemy jednej linii:

var ticket = await sender.Send(new CreateTicketCommand(request.Title), cancellationToken);

sender jest zawsze ten sam. Zmienia się tylko obiekt, który mu podajesz — a on sam znajduje handlera. To jest mediator (albo dispatcher: w tym kontekście te słowa znaczą to samo).

Krok 1: skąd Send ma wiedzieć, co zwrócić

Napisz sobie w głowie sygnaturę, którą chcemy:

Task<???> Send(object command);

I od razu widać dziurę: var ticket = await sender.Send(...) ma dać TicketDto, a nie object. Kompilator musi znać typ wyniku w miejscu wywołania. Skąd ma go wziąć? Jedyne, co tam widać, to typ commanda. Czyli typ wyniku musi być zapisany w typie commanda.

Stąd para interfejsów-markerów. Nie mają żadnych metod — niosą wyłącznie informację typu:

project/Helpdesk/Common/Cqrs.cs

namespace Helpdesk.Common;

/// <summary>Operacja zmieniająca stan, zwracająca TResult.</summary>
public interface ICommand<TResult>;

/// <summary>Zapytanie o dane zwracające TResult, bez zmiany stanu.</summary>
public interface IQuery<TResult>;

public interface ICommandHandler<in TCommand, TResult> where TCommand : ICommand<TResult>
{
    Task<TResult> HandleAsync(TCommand command, CancellationToken cancellationToken = default);
}

public interface IQueryHandler<in TQuery, TResult> where TQuery : IQuery<TResult>
{
    Task<TResult> HandleAsync(TQuery query, CancellationToken cancellationToken = default);
}

public interface ICommand<TResult>; — średnik zamiast { }. Interfejs bez składowych; C# pozwala na taki zapis od wersji 12. W TS najbliższym odpowiednikiem byłby phantom type: typ, którego jedynym zadaniem jest przenieść informację przez system typów.

Nowe jest też where TCommand : ICommand<TResult> — ograniczenie parametru typu, odpowiednik extends w generykach TS. Czyta się: „TCommand musi być commandem, którego wynikiem jest TResult”. Bez tego dałoby się napisać handler zwracający bool dla commanda zadeklarowanego jako ICommand<TicketDto>, a dispatcher szukałby wtedy handlera, którego nie ma. Ograniczenie sprawia, że taki kod się nie skompiluje.

Krok 2: kontrakt dispatchera

project/Helpdesk/Common/ISender.cs

namespace Helpdesk.Common;

/// <summary>Oddaje command lub query właściwemu handlerowi; wołający nie zna handlera.</summary>
public interface ISender
{
    Task<TResult> Send<TResult>(ICommand<TResult> command, CancellationToken cancellationToken = default);

    Task<TResult> Send<TResult>(IQuery<TResult> query, CancellationToken cancellationToken = default);
}

Dwie przeciążone metody o tej samej nazwie — kompilator wybierze właściwą po typie argumentu. I najważniejsze: TResult nie jest wpisywane ręcznie. Piszesz sender.Send(new GetTicketQuery(5)), kompilator widzi, że GetTicketQuery : IQuery<TicketDto?>, więc podstawia TResult = TicketDto? i całe wyrażenie ma typ Task<TicketDto?>. To inferencja typu — dokładnie to, co robi TS, wyciągając T z Promise<T> przy await.

Nazwa ISender nie jest przypadkowa — tak samo nazywa się ten interfejs w MediatR. Piszemy własny z tą samą nazwą i tą samą metodą Send, żeby podmiana na bibliotekę była później zmianą using-a, a nie przepisywaniem endpointów.

Krok 3: implementacja — tu się dzieje magia

Sedno problemu: w metodzie Send<TResult> kompilator zna tylko TResult. Konkretny typ commanda (CreateTicketCommand) jest schowany za interfejsem ICommand<TicketDto> — a żeby poprosić kontener o handlera, potrzebujesz obu parametrów: ICommandHandler<CreateTicketCommand, TicketDto>.

KompilacjaRuntime
Typ wynikuTResult — znanyznany
Typ commandatylko ICommand<TResult>command.GetType() — konkretny

Skoro konkretny typ jest dostępny dopiero w runtime, to i typ handlera trzeba złożyć w runtime. Służy do tego refleksja:

var handlerType = typeof(ICommandHandler<,>).MakeGenericType(command.GetType(), typeof(TResult));
  • typeof(ICommandHandler<,>) — otwarty typ generyczny, czyli szablon z niewypełnionymi parametrami. Przecinek bez nazw to poprawna składnia i znaczy „dwa parametry”.
  • MakeGenericType(a, b) — wypełnia szablon i zwraca Type opisujący ICommandHandler<CreateTicketCommand, TicketDto>.
  • Taki Type podajesz kontenerowi: provider.GetRequiredService(handlerType).

Zostaje ostatni kłopot: kontener oddaje object. Rzutowanie ((ICommandHandler<?, TResult>)handler) nie ma jak się skompilować, bo pierwszego parametru nie umiesz wpisać. Rozwiązania są dwa — użyjemy prostszego:

SposóbJakKoszt
dynamicrezygnujesz z kontroli typów w tej jednej linii; metoda wyszukiwana po nazwie w runtimeliterówka wychodzi przy wywołaniu; 3 linie kodu
klasa opakowującaabstrakcyjny Wrapper<TResult> + generyczny potomek, który zna oba typyszybsze i w pełni typowane; ~40 linii — tak robi MediatR

dynamic to słowo kluczowe C#, które wyłącza kontrolę typów dla danego wyrażenia: „sprawdź w czasie wykonania, czy ten obiekt ma metodę HandleAsync”. Czyli zwykły JavaScript, wpuszczony do C# na jedną linię.

To jedyne miejsce w projekcie, gdzie wolno użyć dynamic. Dispatcher z definicji nie zna typów, którymi żongluje. Wszędzie indziej dynamic znaczy „zgubiłem typ i nie chciało mi się go szukać” i słusznie budzi czujność na review.

Gotowy plik

project/Helpdesk/Common/Sender.cs

namespace Helpdesk.Common;

public class Sender(IServiceProvider provider) : ISender
{
    public Task<TResult> Send<TResult>(ICommand<TResult> command, CancellationToken cancellationToken = default) =>
        Dispatch<TResult>(typeof(ICommandHandler<,>), command, cancellationToken);

    public Task<TResult> Send<TResult>(IQuery<TResult> query, CancellationToken cancellationToken = default) =>
        Dispatch<TResult>(typeof(IQueryHandler<,>), query, cancellationToken);

    private Task<TResult> Dispatch<TResult>(Type openHandlerType, object message, CancellationToken cancellationToken)
    {
        var handlerType = openHandlerType.MakeGenericType(message.GetType(), typeof(TResult));
        dynamic handler = provider.GetRequiredService(handlerType);

        return handler.HandleAsync((dynamic)message, cancellationToken);
    }
}

Linia po linii, na przykładzie POST /tickets:

LiniaCo się dzieje
Send(command, ct)endpoint podał CreateTicketCommand; metoda przekazuje dalej szablon ICommandHandler<,> (query dostaje swój szablon — dlatego Dispatch bierze go parametrem, zamiast wpisywać na sztywno)
MakeGenericType(…)z szablonu i dwóch typów powstaje ICommandHandler<CreateTicketCommand, TicketDto>
GetRequiredService(handlerType)kontener oddaje CreateTicketHandler — jako object, bo pytanie było zadane typem z runtime
dynamic handler„nie sprawdzaj typu przy kompilacji, znajdź metodę przy wywołaniu” — bo nazwy tego typu nie da się wpisać w kodzie
handler.HandleAsync(…)wywołanie handlera; (dynamic)message jest po to, żeby wybrać właściwe przeciążenie po prawdziwym typie, a nie po object
Ten plik piszesz raz w życiu. W firmowym projekcie robi to za ciebie MediatR i nikt do tego kodu nie zagląda. Tu jest po to, żeby przestał być magią — a nie po to, żebyś umiał go odtworzyć z pamięci.

Krok 4: oznacz commandy i query

Każdy record musi teraz powiedzieć, co zwraca:

public record CreateTicketCommand(string Title) : ICommand<TicketDto>;
public record UpdateTicketCommand(int Id, string Title) : ICommand<bool>;
public record DeleteTicketCommand(int Id) : ICommand<bool>;

public record GetTicketQuery(int Id) : IQuery<TicketDto?>;
public record ListTicketsQuery : IQuery<IReadOnlyList<TicketDto>>;
public record GetTicketMetricsQuery : IQuery<TicketMetricsDto>;

Uwaga: CreateTicketRequest nie dostaje markera. Request to kontrakt z klientem HTTP i nie ma pojęcia o istnieniu dispatchera — to ta sama granica, którą widać w parze UpdateTicketRequest (tylko Title, z body) i UpdateTicketCommand (Id z trasy + Title z body).

Pliki commandów potrzebują teraz using Helpdesk.Common; — markery mieszkają w innym namespace.

Endpointy chudną

private static async Task<Created<TicketDto>> HandleAsync(
    CreateTicketRequest request,
    ISender sender,
    CancellationToken cancellationToken)
{
    var ticket = await sender.Send(new CreateTicketCommand(request.Title), cancellationToken);
    return TypedResults.Created($"/tickets/{ticket.Id}", ticket);
}

ISender sender zamiast ICommandHandler<CreateTicketCommand, TicketDto> handler — i tak samo w pozostałych pięciu endpointach. Handlery zostają bez zmian: one nadal implementują ICommandHandler<…> i nadal rejestrujesz je po jednej linii.

Rejestracja

project/Helpdesk/Common/CommonServices.cs

public static IServiceCollection AddDispatcher(this IServiceCollection services)
{
    services.AddScoped<ISender, Sender>();

    return services;
}

i w Program.cs: builder.Services.AddDispatcher(); obok AddCurrentUser().

Scoped, nie Singleton — mimo że Sender nie ma żadnego stanu i aż kusi, żeby zrobić z niego Singletona. Powód w sekcji „Diagnostyka”, błąd trzeci: Singleton dostaje korzeniowy provider, z którego nie wolno wyciągać serwisów Scoped. Aplikacja wstanie normalnie i wywali się dopiero przy pierwszym żądaniu.

Diagnostyka: trzy błędy, każdy w innym momencie

1. Zapomniany marker — kompilacja

error CS0311: Nie można użyć typu „CreateTicketCommand” jako parametru typu
„TCommand” w typie ogólnym lub metodzie „ICommandHandler<TCommand, TResult>”.
Brak niejawnej konwersji odwołania z typu „CreateTicketCommand”
na „Helpdesk.Common.ICommand<Helpdesk.Features.Tickets.TicketDto>”.

Ograniczenie where z kroku 1 robi swoją robotę: interfejs handlera już go wymaga, a record jeszcze nie implementuje markera. Dopisz : ICommand<TicketDto>. Ten błąd to dobra wiadomość — złapany przy kompilacji, więc nie ma jak dojechać na produkcję.

2. Brak rejestracji handlera — pierwsze żądanie, 500

System.InvalidOperationException: No service for type
'Helpdesk.Common.ICommandHandler`2[…CreateTicketCommand,…TicketDto]'
has been registered.
   at …GetRequiredService(IServiceProvider provider, Type serviceType)
   at Helpdesk.Common.Sender.Dispatch[TResult](…)

Porównaj z lekcją 0005: tam brak rejestracji dawał komunikat bindera z tabelką i słowem UNKNOWN. Teraz binder jest zadowolony — ISender przecież jest zarejestrowany — a rozczarowanie przychodzi dopiero w środku dispatchera. Nazwa typu w cudzysłowie mówi wprost, której linii AddScoped brakuje.

3. Sender jako Singleton — pierwsze żądanie, 500

System.InvalidOperationException: Cannot resolve scoped service
'Helpdesk.Common.ICommandHandler`2[…CreateTicketCommand,…TicketDto]'
from root provider.

Singleton dostaje w konstruktorze IServiceProvider korzenia aplikacji, a nie ten od bieżącego żądania. Wyciągnięcie z korzenia serwisu Scoped byłoby wyciekiem: handler (a z nim ICurrentUser, docelowo DbContext) żyłby do końca życia procesu. Kontener na to nie pozwala.

Zauważ, czego tu nie ma: walidacja z Build() tego nie wyłapała. W lekcji 0002 captive dependency wysadzała aplikację przy starcie, bo zależność było widać w konstruktorze. Sender deklaruje w konstruktorze tylko IServiceProvider — kontener nie ma pojęcia, że sięgnie po handlera. Wzorzec nazywa się service locator i to jest jego wbudowany koszt: część błędów przenosi się ze startu aplikacji na pierwsze żądanie.

Ostatni wiersz to najczęstszy zarzut wobec mediatorów i wart jest zapamiętania, bo pada na rozmowach: „nawigacja po kodzie przestaje działać”. W IDE ratują cię wtyczki (Rider skacze z commanda do handlera), w code review — konwencja nazw XCommand / XHandler, którą już masz.

Cenę z pierwszego wiersza łagodzi się na dwa sposoby: automatyczną rejestracją handlerów (skan assembly zamiast ręcznych linii — tak działa AddMediatR) albo testem integracyjnym, który dotyka każdej trasy. Do obu wrócimy: skan przy MediatR, testy w lekcji 0011.

MediatR w pięć minut

Napisałeś właśnie mediator. MediatR to ten sam pomysł, dopracowany: cache typów zamiast refleksji przy każdym żądaniu, opakowania zamiast dynamic, do tego notyfikacje i pipeline. Mapowanie nazw jeden do jednego:

Twój kodMediatR
ICommand<TResult>, IQuery<TResult>IRequest<TResponse> — jeden marker na oba
ICommandHandler<TCommand, TResult>IRequestHandler<TRequest, TResponse>
HandleAsync(command, ct)Handle(request, ct)
ISender.Send(command, ct)ISender.Send(request, ct) — ta sama nazwa
ręczne AddScoped per handlerservices.AddMediatR(cfg => cfg.RegisterServicesFromAssemblyContaining<Program>())
—INotification + IPublisher.Publish: zero lub wielu odbiorców
—IPipelineBehavior: kod wokół każdego handlera (dostaje request i next, jak middleware w Express)

Jeden szczegół różni się naprawdę: MediatR ma jeden marker IRequest<T> dla commandów i query. Rozdział na command/query robi się wtedy konwencją nazw albo własnymi interfejsami dziedziczącymi po IRequest<T> — drugie podejście zobaczysz w wielu firmowych repo i teraz wiesz, po co ludzie to piszą.

Sprawdź się

Odpowiedz zanim klikniesz. Zła odpowiedź nie zdradza dobrej — spróbuj jeszcze raz.

Po co commandowi marker ICommand<TicketDto>?
Bez markera await sender.Send(cmd) nie miałoby jak dać TicketDto — kompilator w miejscu wywołania widzi wyłącznie typ argumentu. Marker przenosi typ wyniku przez system typów, a kompilator wyciąga go inferencją. Odróżnianie od query to skutek uboczny, a commandy tworzysz sam przez new, nie przez kontener.
Czemu Dispatch potrzebuje refleksji zamiast zwykłego rzutowania?
W Send<TResult> kompilator widzi argument jako ICommand<TResult>; że to akurat CreateTicketCommand, wiadomo dopiero z command.GetType(). Typ handlera potrzebuje obu parametrów naraz, więc trzeba go złożyć w runtime przez MakeGenericType.
„Cannot resolve scoped service … from root provider” — przyczyna?
Singleton dostaje provider korzenia, a z korzenia nie wolno wyciągać serwisów Scoped — żyłyby wtedy do końca procesu. Brak AddDispatcher dałby inny komunikat, o niezarejestrowanym ISender, a Transient handler rozwiązałby się bez protestu.
Co tracisz, wstawiając dispatcher między endpoint a handler?
Kontener widzi w konstruktorze Sender tylko IServiceProvider, więc nie zweryfikuje przy Build(), że handler istnieje — dowiesz się dopiero przy żądaniu. Handlery testuje się dalej przez zwykłe new, a lifetime nadal ustawiasz przy rejestracji.
Jak z ICommand<TResult> powstaje typ handlera do zapytania kontenera?

typeof(ICommandHandler<,>).MakeGenericType(command.GetType(), typeof(TResult)). Otwarty typ generyczny to szablon; MakeGenericType wypełnia go konkretnym typem commanda (dostępnym tylko w runtime) i typem wyniku (znanym z inferencji w miejscu wywołania).

Czemu Sender musi być Scoped, skoro nie ma stanu?

Bo wstrzyknięty w niego IServiceProvider jest tym od bieżącego żądania tylko wtedy, gdy sam Sender jest Scoped. Jako Singleton dostaje provider korzenia i nie może wyciągnąć z niego handlera, który jest Scoped — 500 przy pierwszym żądaniu.

Trzy błędy z tej lekcji — który wychodzi kiedy?

Zapomniany marker — przy kompilacji (CS0311, dzięki ograniczeniu where). Brak rejestracji handlera i zły lifetime Sendera — dopiero przy pierwszym żądaniu, oba jako 500. To jest cena wzorca service locator.

Co dalej

Twoje handlery komunikują porażkę przez bool i null. To wystarcza na „nie ma takiego zgłoszenia”, ale nie odróżni „nie ma” od „nie wolno” i od „tytuł jest pusty” — a każdy z tych przypadków to inny status HTTP. W lekcji 0007 wchodzi globalna obsługa błędów: własny DomainException, katalog w stylu TicketErrors.NotFound(id) i jeden IExceptionHandler, który zamienia je na odpowiedzi application/problem+json. Endpointy przestaną wtedy zawierać if-y od błędów.
