Lekcja 0007 · ~25 min · projekt Helpdesk

Błędy: jedno miejsce, jeden format, application/problem+json

Cel: przestać zwracać puste 404, w których frontend nie ma czego pokazać. Domena rzuca DomainException z opisanym błędem, jeden handler zamienia go na standardowy JSON, a endpointy przestają rozgałęziać się na if.

Wymaga: lekcji 0006 (ISender). Ściąga: Błędy / ProblemDetails.

Problem: API mówi „nie", ale nie mówi „czemu"

Tak dziś twoje API odpowiada na cztery różne porażki:

ŻądanieOdpowiedźCo dostaje frontend
GET /tickets/99404, brak ciałanic — musi sam wymyślić komunikat
PUT /tickets/99404, brak ciałanic
POST /tickets z pustym tytułem201 — zgłoszenie bez tytułu wjeżdża do bazyfałszywy sukces
cokolwiek rzuci wyjątek500 ze stack tracem (w Development)ścieżki do plików na dysku

Do tego kod. Żeby to 404 w ogóle powstało, informacja „nie ma takiego zgłoszenia" musi przewędrować przez trzy warstwy jako bool albo null:

// store       bool Update(int id, string title);
// handler     return Task.FromResult(store.Update(...));   // przepisuje bool dalej
// endpoint    return updated ? TypedResults.NoContent() : TypedResults.NotFound();
Ten bool to dokładnie ten sam bool, który w lekcji 0006 miał literówkę: updated ? NotFound() : NotFound(). Kompilator nie miał czego złapać — oba ramiona to poprawny typ. Wartość false nie niesie powodu, więc nic nie pilnuje, żebyś obsłużył ją poprawnie.
W Vue robisz const res = await fetch(...) i sprawdzasz res.ok. Puste 404 daje ci tyle, że „coś nie wyszło". Żeby pokazać toast „Zgłoszenie 99 nie istnieje" albo podświetlić pole formularza, potrzebujesz ciała odpowiedzi z kodem błędu — czegoś, na czym można zrobić switch.

Standard, którego nie trzeba wymyślać: RFC 9457

Format ciała błędu jest wystandaryzowany — RFC 9457 Problem Details for HTTP APIs (wcześniej RFC 7807). ASP.NET Core ma go wbudowanego jako ProblemDetails. Wygląda tak:

{
  "type": "https://tools.ietf.org/html/rfc9110#section-15.5.5",
  "title": "Nie znaleziono",
  "status": 404,
  "detail": "Zgłoszenie 99 nie istnieje.",
  "code": "ticket.not_found",
  "traceId": "00-2f9129be428a3154d89b415b28969d6c-38ca5323db86d193-00"
}
PoleDla kogoUwagi

titleczłowiekkrótkie, niezmienne dla danego typu
statusobapowtórzenie kodu HTTP w ciele

Nagłówek to Content-Type: application/problem+json — nie zwykły application/json. Dzięki temu klient odróżnia „ciało z danymi" od „ciała z błędem" bez patrzenia na kod statusu.

Czemu code, skoro jest status? Bo 400 znaczy dwadzieścia różnych rzeczy. Frontend nie może budować logiki na detail (to tekst dla człowieka, zmieni się przy pierwszej korekcie stylistycznej) ani na samym 400. ticket.empty_title jest stabilne i można je zmapować na tłumaczenie i na pole formularza.

Co frontend realnie robi z code

To nie jest pole „na wszelki wypadek". Pięć konkretnych zastosowań, wszystkie z twojego świata:

Przypadek użyciaBez codeZ code
Tłumaczenia. Backend mówi po polsku, aplikacja ma trzy językiwyświetlasz detail po polsku albo prosisz backend o i18nt(`errors.${code}`) — tłumaczenia zostają na froncie, gdzie i tak są
Podświetlenie pola formularzaglobalny toast „coś nie tak"ticket.empty_title → czerwona ramka pod polem Tytuł
Dwa różne 409 na tym samym endpoinciejeden komunikat na obaticket.already_closed → odśwież widok; ticket.assigned_to_other → pokaż przycisk „przejmij”
Interceptor HTTP — ponawiać czy niezgadywanie po statusieswitch w jednym miejscu decyduje: retry, wyloguj, pokaż
Grupowanie w Sentrydetail ma id w środku → tysiąc osobnych „błędów”jedna grupa ticket.not_found z licznikiem

W kodzie wygląda to tak — jeden klient HTTP dla całej aplikacji:

type Problem = { status: number; title: string; detail?: string; code?: string; traceId?: string }

async function api<T>(url: string, init?: RequestInit): Promise<T> {
  const res = await fetch(url, init)
  if (res.ok) return res.json()

  const problem: Problem = res.headers.get('content-type')?.includes('problem+json')
    ? await res.json()
    : { status: res.status, title: res.statusText }

  throw new ApiError(problem)
}
// w komponencie — switch po code, nie po tekście i nie po samym 400
try {
  await createTicket({ title })
} catch (e) {
  if (!(e instanceof ApiError)) throw e

  switch (e.problem.code) {
    case 'ticket.empty_title':
      errors.title = t('errors.ticket.empty_title'); break
    case 'ticket.not_found':
      await router.push('/tickets'); break
    default:
      toast.error(t('errors.generic', { id: e.problem.traceId }))
  }
}

Zwróć uwagę na default: pokazuje traceId. Użytkownik czyta go supportowi, support znajduje po nim wpis w logu z pełnym stosem. To jest cała ścieżka diagnostyczna i dlatego nie musisz wypuszczać stack trace'a na zewnątrz.

Kiedy code jest zbędny. Jeśli jedyne, co robi frontend, to toast.error(detail), to samo detail wystarczy, a code jest ceremonią. Zysk pojawia się dokładnie tam, gdzie status nie wystarcza: przy 400 (które pole?) i 409 (który konflikt?). Przy 404 i 500 to głównie wygoda dla telemetrii.
Czego code nie powie: nasz ErrorType.Forbidden mapuje się na 404 z kodem ticket.not_found — frontend celowo nie odróżni „nie ma” od „nie twoje”. Tak ma być; ta informacja jest wyciekiem.
A gdy błędnych pól jest pięć naraz? Jeden code na odpowiedź wtedy nie wystarczy — formularz rejestracji musi dostać komplet w jednej odpowiedzi, inaczej user poprawia pole, klika, i dostaje błąd o kolejnym. Do tego służy ValidationProblemDetails: ten sam problem+json plus pole errors ze słownikiem pole → tablica komunikatów. Osobna ścieżka, bo DomainException niesie z założenia jeden błąd. Budujemy to w lekcji 0008 razem z FluentValidation.

Krok 1: błąd jako dane, nie jako tekst

project/Helpdesk/Common/Errors/Error.cs

namespace Helpdesk.Common.Errors;

public enum ErrorType
{
    Validation,
    NotFound,
    Conflict,
    Forbidden
}

public record Error(string Code, string Message, ErrorType Type);

Trzy pola i cała pointa lekcji siedzi w rozdzieleniu dwóch z nich:

  • Code — identyfikator. Kontrakt z frontendem, nie zmienia się.
  • Message — zdanie dla człowieka. Może się zmienić, może być tłumaczone.
  • Type — kategoria. Z niej wyliczymy kod HTTP. Domena mówi „to jest konflikt", a nie „to jest 409" — domena nie wie o HTTP.

enum to zamknięty zbiór nazwanych wartości; w TS pisałbyś type ErrorType = "validation" | "notFound" | …. W C# jest to osobny typ, więc funkcja przyjmująca ErrorType nie przyjmie stringa, a switch po nim kompilator umie sprawdzić.

Krok 2: wyjątek, który niesie ten błąd

project/Helpdesk/Common/Errors/DomainException.cs

namespace Helpdesk.Common.Errors;

public class DomainException(Error error) : Exception(error.Message)
{
    public Error Error { get; } = error;
}

Jedna klasa, jedno pole. : Exception(error.Message) woła konstruktor klasy bazowej — dzięki temu w logu i debuggerze widać sensowny komunikat, a nie samą nazwę typu.

Po co w ogóle wyjątek, skoro błąd jest już danymi? Bo wyjątek przeskakuje warstwy bez ich zmieniania. Handler jest siedem ramek stosu poniżej endpointu — z throw nie musi go o niczym informować żaden typ pośredni. Cenę tego rozwiązania rozliczymy na końcu lekcji.

throw new DomainException(...) ≈ throw new AppError(...) w JS. Różnica: w C# łapiemy po typie (is DomainException), a nie po err.name === "AppError". Typ jest nie do podrobienia i nie do zliterówkowania.

Krok 4: jeden handler zamienia wyjątek na odpowiedź

ASP.NET Core ma do tego dedykowany interfejs: IExceptionHandler. Rejestrujesz implementacje, a middleware wyjątków podaje im każdy nieobsłużony wyjątek po kolei.

project/Helpdesk/Common/Errors/DomainExceptionHandler.cs

using Microsoft.AspNetCore.Diagnostics;

namespace Helpdesk.Common.Errors;

public class DomainExceptionHandler(IProblemDetailsService problemDetailsService) : IExceptionHandler
{
    public async ValueTask<bool> TryHandleAsync(
        HttpContext httpContext,
        Exception exception,
        CancellationToken cancellationToken)
    {
        if (exception is not DomainException domainException)
        {
            return false;
        }

        var error = domainException.Error;
        httpContext.Response.StatusCode = StatusFor(error.Type);

        return await problemDetailsService.TryWriteAsync(new ProblemDetailsContext
        {
            HttpContext = httpContext,
            Exception = exception,
            ProblemDetails =
            {
                Title = TitleFor(error.Type),
                Detail = error.Message,
                Status = httpContext.Response.StatusCode,
                Extensions = { ["code"] = error.Code }
            }
        });
    }

    private static int StatusFor(ErrorType type) => type switch
    {
        ErrorType.Validation => StatusCodes.Status400BadRequest,
        ErrorType.NotFound => StatusCodes.Status404NotFound,
        ErrorType.Conflict => StatusCodes.Status409Conflict,
        ErrorType.Forbidden => StatusCodes.Status404NotFound,
        _ => StatusCodes.Status500InternalServerError
    };

    private static string TitleFor(ErrorType type) => type switch
    {
        ErrorType.Validation => "Nieprawidłowe żądanie",
        ErrorType.NotFound => "Nie znaleziono",
        ErrorType.Conflict => "Konflikt stanu",
        ErrorType.Forbidden => "Nie znaleziono",
        _ => "Błąd serwera"
    };
}
LiniaCo robi
is not DomainException … return falsefalse = „to nie mój wyjątek, dawaj następnemu". Handlery idą w kolejności rejestracji; jeśli wszystkie zwrócą false, wchodzi zachowanie domyślne (u nas: generyczne 500 problem+json).
is not X ypattern matching z deklaracją zmiennej: jeśli typ pasuje, y jest już rzutowane. Odpowiednik if (!(e instanceof X)) return, tyle że y ma typ.
Response.StatusCode = …kod HTTP wyliczony z kategorii błędu. Musi być ustawiony przed pisaniem ciała.
TryWriteAsyncpisze ciało w formacie problem+json. Zwraca false, gdy klient prosi o format, którego pisarz nie umie (np. Accept: application/xml) — wtedy dalej działa domyślna obsługa.
Extensions["code"]dokłada nasze własne pole do standardowego JSON-a. RFC 9457 wprost na to pozwala.
ProblemDetails = { … }zagnieżdżony inicjalizator: ustawia pola istniejącego obiektu (kontekst tworzy go sam), nie przypisuje nowego.
Zwrócenie true bez napisania odpowiedzi daje 404. Middleware uzna, że obsłużyłeś wyjątek, a że nikt nic nie napisał — klient dostaje puste 404 i w logu ląduje The exception handler configured on ExceptionHandlerOptions produced a 404 status response. Handler, który zwraca true, musi napisać całą odpowiedź razem ze statusem (docs).

Rejestracja: dwie linijki i jedno miejsce w pipeline

project/Helpdesk/Common/CommonServices.cs

Kolejność w Program.cs jest istotna: UseExceptionHandler() to middleware, a nie rejestracja. Musi stać przed MapTickets(), bo działa jak try/catch owinięty wokół wszystkiego, co jest dalej. Cokolwiek zamapujesz wyżej — nie jest chronione.

Handler jest Singletonem. AddExceptionHandler<T>() rejestruje go jako Singleton (widać to w komunikacie błędu: ServiceType: …IExceptionHandler Lifetime: Singleton). Nie wstrzykniesz w niego ICurrentUser ani żadnego Scoped — to captive dependency z lekcji 0002. Potrzebujesz danych żądania? Bierzesz je z httpContext, który dostajesz parametrem.

Krok 5: co znika z kodu

Teraz kaskada. Skoro handler potrafi opisać porażkę, warstwy pośrednie przestają ją przepisywać.

Handler zamiast bool rzuca

// przed
public Task<bool> HandleAsync(DeleteTicketCommand command, CancellationToken ct = default)
    => Task.FromResult(store.Delete(command.Id));

// po
public Task<Unit> HandleAsync(DeleteTicketCommand command, CancellationToken ct = default)
{
    if (!store.Delete(command.Id))
    {
        throw new DomainException(TicketErrors.NotFound(command.Id));
    }

    return Task.FromResult(Unit.Value);
}

Unit to nowy typ w Common/, bo generyk nie przyjmuje void — nie da się napisać ICommand<void>. To ta sama sztuczka, którą robi MediatR (Unit dla żądań bez wyniku):

public readonly record struct Unit
{
    public static readonly Unit Value = new();
}

Query przestaje być nullowalne

// przed  public record GetTicketQuery(int Id) : IQuery<TicketDto?>;
// po    public record GetTicketQuery(int Id) : IQuery<TicketDto>;

var ticket = store.GetById(query.Id) ?? throw new DomainException(TicketErrors.NotFound(query.Id));

?? to null-coalescing, znane z JS. Nowość: w C# po prawej stronie może stać throw — throw expression. Czyta się jak zdanie: „weź zgłoszenie, a jak go nie ma, rzuć".

Endpoint przestaje rozgałęziać

// przed
private static async Task<Results<NoContent, NotFound>> HandleAsync(...)
{
    var deleted = await sender.Send(new DeleteTicketCommand(id), cancellationToken);
    return deleted ? TypedResults.NoContent() : TypedResults.NotFound();
}

// po
private static async Task<NoContent> HandleAsync(...)
{
    await sender.Send(new DeleteTicketCommand(id), cancellationToken);

    return TypedResults.NoContent();
}

Typ zwrotny zwęził się z Results<NoContent, NotFound> do NoContent. Endpoint mówi teraz tylko o ścieżce sukcesu — to jest ten zysk, dla którego robimy całą lekcję. Ta sama zmiana zaszła w GetTicket (Ok<TicketDto>) i UpdateTicket.

Cena: zwężony typ zwrotny znika też z dokumentacji OpenAPI. Wcześniej Results<Ok<TicketDto>, NotFound> samo ogłaszało, że endpoint może dać 404; teraz trzeba to dopisać ręcznie przez .Produces<ProblemDetails>(404). Wrócimy do tego przy OpenAPI.

Wyjątki czy Result? Uczciwe porównanie

Zrobiliśmy wersję na wyjątkach. Twój zespół — sądząc po stylu Milana Jovanovicia — używa Result pattern: handler zwraca Result<TicketDto>, czyli albo wartość, albo Error, i nikt nic nie rzuca. Warto wiedzieć, czym się różnią, zanim zobaczysz to w firmowym repo.

Wyjątek + IExceptionHandlerResult<T>
Widać w sygnaturze, że może się nie udaćnietak
Da się zignorować porażkęnie (leci w górę)tak (nikt nie każe sprawdzić)
Kod warstw pośrednichnic nie przepisujekażda warstwa musi zdecydować
Koszt wykonaniarzucenie jest drogie (rząd µs)zwykły zwrot wartości
Endpointtylko ścieżka sukcesumapowanie Result → status
Debugger „break on exception"zatrzymuje się na regułach biznesowychcisza

Reguła praktyczna: wyjątek do sytuacji naprawdę wyjątkowych, Result do porażek spodziewanych (walidacja formularza to nie awaria). Duże systemy często mają oba: Result wewnątrz domeny, a IExceptionHandler jako siatka bezpieczeństwa na wszystko, co się przez nią przedostanie. Error i ErrorType, które właśnie napisałeś, przenoszą się do Result jeden do jednego — dlatego zaczęliśmy od nich. Do Result wracamy przy okazji EF Core i testów — najpierw, w lekcji 0008, wyprowadzamy walidację z handlerów.

Handler TryHandleAsync zwraca false. Co się dzieje?
false znaczy „nie mój wyjątek". Handlery idą po kolei; gdy wszystkie odmówią, wchodzi fallback (u nas generyczne problem+json 500). To puste 404 z pierwszej odpowiedzi jest pułapką odwrotną: dostaniesz je, gdy zwrócisz true, nic nie pisząc.
Na czym frontend ma budować obsługę konkretnego błędu?
detail to tekst dla człowieka — zmieni się przy pierwszej korekcie. Sam status HTTP jest za gruby: pod 400 kryje się dwadzieścia różnych powodów. ticket.empty_title jest jedno i to samo zawsze, więc mapuje się na tłumaczenie i na pole formularza.
Czemu ErrorType ma NotFound, a nie Status404?
Ten sam handler może kiedyś obsługiwać kolejkę wiadomości albo gRPC, gdzie 404 nie znaczy nic. Domena mówi „nie znalazłem"; tłumaczenie na protokół to jedno miejsce — StatusFor. Enum w C# jak najbardziej trzyma liczby, a ProblemDetails przyjmuje int.
Gdzie w Program.cs musi stać app.UseExceptionHandler()?
To middleware, czyli warstwa try/catch nałożona na resztę pipeline'u. Endpointy zamapowane wcześniej niż ono nie są chronione. Rejestracje (AddProblemDetails, AddExceptionHandler) idą wcześniej, do builder.Services.

Zapamiętaj bez zaglądania

Co dokładnie wychodzi w odpowiedzi, a co zostaje w logu?

Na zewnątrz: type, title, status, detail, code, traceId. W logu: pełny stack trace z nazwami plików i linii. Łącznikiem jest traceId — użytkownik podaje go supportowi, support znajduje po nim wpis w logu.

Trzy błędy z tej lekcji — który wychodzi kiedy?

Brak AddProblemDetails() i bezargumentowe UseExceptionHandler() bez fallbacku — przy starcie, aplikacja nie wstaje. Zapomniane app.UseExceptionHandler() — dopiero przy żądaniu, jako 500 zamiast 404. Reguła: czego kontener nie może zbudować, to wywala start; czego brakuje w pipelinie, to wychodzi przy ruchu.

Czemu Unit, a nie ICommand<void>?

void nie jest typem, tylko oznaczeniem braku wyniku — nie da się go podstawić pod parametr generyczny. Unit to pusta struktura z jedną wartością Unit.Value, która ten brak reprezentuje. MediatR robi dokładnie to samo.

Źródło pierwotne

Handle errors in ASP.NET Core APIs (ok. 12 min) — czytaj zakładkę Minimal APIs, sekcje Problem details i IExceptionHandler. Dla formatu samego ciała: RFC 9457 — wystarczą sekcje 3 i 3.2 (pola i rozszerzenia).
Coś nie działa albo nie klika? Pytaj — po to tu jestem. Szczególnie warto zapytać, jak twój zespół robi to u siebie: wyjątkami czy Result, i czy mają swój katalog kodów błędów.
