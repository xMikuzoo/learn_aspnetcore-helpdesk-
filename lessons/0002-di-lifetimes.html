Lekcja 0002 · ~20 min · projekt Helpdesk

Dependency Injection: kto tworzy twoje obiekty

Cel: wyciągnąć listę zgłoszeń z Program.cs do serwisu, zarejestrować go w kontenerze i zobaczyć na własne oczy — na wydruku z przeglądarki — czym różni się Singleton od Scoped i Transient.

Wymaga: lekcji 0001 (granica builder.Build()). Ściąga do tej lekcji: DI — rejestracja i czasy życia.

Zacznijmy od tego, co już napisałeś

W lekcji 0001 wylądowało w Program.cs to:

var tickets = new[] { new { Id = 1, Title = "Pierwsze zgłoszenie" }, … };

app.MapGet("/tickets", () => tickets);

To działa. I — przypadkiem — jest już singletonem: lambda domyka (closure) zmienną tickets, więc jedna tablica obsługuje wszystkie żądania przez całe życie procesu. Problem nie w tym, że to singleton. Problem w tym, że nikt tego nie zdecydował. Nie da się tego zmienić bez przepisania endpointu, nie da się podmienić na bazę danych, nie da się przetestować bez startowania serwera.

DI odwraca sytuację: klasa mówi czego potrzebuje, a kontener mówi skąd to wziąć i jak długo ma żyć. Te dwie decyzje przestają być jedną linijką kodu.

provide() / inject() z Vue to ten sam pomysł: komponent deklaruje potrzebę, ktoś wyżej dostarcza. Różnice: w C# kluczem jest typ, nie string, więc kompilator łapie literówki; wstrzykiwanie idzie przez konstruktor, nie przez wywołanie w setupie; i dochodzi wymiar, którego Vue nie ma — czas życia. Bliżej ci do Angulara (@Injectable, providedIn) albo NestJS.

Krok 1: serwis

Trzy nowe pliki obok Program.cs. Nie kopiuj — przepisz.

project/Helpdesk/Ticket.cs

public record Ticket(int Id, string Title);

record to klasa z gotowym konstruktorem, porównywaniem po wartości i czytelnym ToString(). Jedna linia zastępuje twój obiekt anonimowy — z tą różnicą, że ten typ ma nazwę, więc można go zwracać z metody.1

1 Typy anonimowe nie mają nazwy, więc nie da się ich zadeklarować jako typ zwracany. Dlatego przy pierwszym interfejsie musi pojawić się record albo class.

project/Helpdesk/ITicketStore.cs

public interface ITicketStore
{
    IReadOnlyList<Ticket> GetAll();
    Ticket? GetById(int id);
    Ticket Add(string title);
}

Interfejs = interface z TS, tylko że w C# klasa musi go zadeklarować jawnie (: ITicketStore) — nie ma structural typing. Ticket? ze znakiem zapytania to nullable reference type: sygnatura mówi „może zwrócić null, obsłuż to”. Kompilator ostrzeże, jeśli zignorujesz. Włącza to <Nullable>enable</Nullable> w twoim .csproj.

project/Helpdesk/InMemoryTicketStore.cs

public class InMemoryTicketStore : ITicketStore
{
    private readonly List<Ticket> _tickets =
    [
        new Ticket(1, "Pierwsze zgłoszenie"),
        new Ticket(2, "Drugie zgłoszenie!")
    ];

    public IReadOnlyList<Ticket> GetAll() => _tickets;

    public Ticket? GetById(int id) => _tickets.FirstOrDefault(t => t.Id == id);

    public Ticket Add(string title)
    {
        var ticket = new Ticket(_tickets.Count + 1, title);
        _tickets.Add(ticket);
        return ticket;
    }
}
  • _tickets — podkreślenie i camelCase to konwencja dla pól prywatnych; twój .editorconfig tego pilnuje i zgłosi warning, jeśli nazwiesz inaczej.
  • [ … ] to collection expression (C# 12): skrócone new List<Ticket> { … }. Typ bierze z lewej strony.
  • => zamiast { return …; } to expression-bodied member — jednolinijkowe ciało metody.
  • readonly znaczy „referencja się nie zmieni”, nie „lista jest niezmienna”. Do listy nadal można dopisywać — dokładnie jak const arr = [] w JS.

Krok 2: rejestracja i wstrzyknięcie

W Program.cs, przed builder.Build() — pamiętasz granicę z lekcji 0001:

builder.Services.AddSingleton<ITicketStore, InMemoryTicketStore>();

Czytaj to jako: „gdy ktoś poprosi o ITicketStore, daj mu InMemoryTicketStore — zawsze tę samą instancję”. Potem, w endpointach:

app.MapGet("/tickets", (ITicketStore store) => store.GetAll());

app.MapGet("/tickets/{id}", (int id, ITicketStore store) =>
{
    var ticket = store.GetById(id);
    return ticket is null ? Results.NotFound() : Results.Ok(ticket);
});

app.MapPost("/tickets", (string title, ITicketStore store) => Results.Ok(store.Add(title)));

Skąd framework wie, że int id ma wziąć z trasy, string title z query stringa, a ITicketStore store z kontenera? Reguła: jeśli typ parametru jest zarejestrowany w DI, minimal API bierze go z kontenera; typy proste (int, string) idą z trasy lub query.2 Kolejność parametrów nie ma znaczenia.

2 Od .NET 7 nie trzeba już atrybutu [FromServices] — kontener jest sprawdzany automatycznie. W starszym kodzie firmowym ten atrybut jeszcze zobaczysz.

Krok 3: zobacz różnicę na własne oczy

Definicje lifetime'ów da się wykuć i zapomnieć. Lepiej je zobaczyć. Dodaj plik:

project/Helpdesk/Stamp.cs

public interface IStamp { string Id { get; } }
public interface ITransientStamp : IStamp;
public interface IScopedStamp : IStamp;
public interface ISingletonStamp : IStamp;

public class Stamp : ITransientStamp, IScopedStamp, ISingletonStamp
{
    public string Id { get; } = Guid.NewGuid().ToString()[^4..];
}

Jedna klasa, trzy puste interfejsy-znaczniki — tylko po to, żeby ten sam typ dało się zarejestrować trzy razy z trzema różnymi lifetime'ami. Każda instancja dostaje przy tworzeniu losowy 4-znakowy identyfikator.3 [^4..] to range operator: „ostatnie cztery znaki”, odpowiednik str.slice(-4).

3 Ten eksperyment to uproszczona wersja oficjalnego przykładu Microsoftu (IOperationTransient / Scoped / Singleton) z Lifetime and registration options.

Rejestracja i endpoint:

builder.Services.AddTransient<ITransientStamp, Stamp>();
builder.Services.AddScoped<IScopedStamp, Stamp>();
builder.Services.AddSingleton<ISingletonStamp, Stamp>();
app.MapGet("/lifetimes", (
    ITransientStamp t1, ITransientStamp t2,
    IScopedStamp s1, IScopedStamp s2,
    ISingletonStamp g1) => new
    {
        transient1 = t1.Id, transient2 = t2.Id,
        scoped1 = s1.Id, scoped2 = s2.Id,
        singleton = g1.Id
    });

Odśwież /lifetimes trzy razy. Zobaczysz coś takiego (to prawdziwy wynik z tej samej konfiguracji na .NET 10.0.400):

{"transient1":"e4b2","transient2":"32b9","scoped1":"6ee9","scoped2":"6ee9","singleton":"b31f"}
{"transient1":"ee53","transient2":"8f58","scoped1":"de1f","scoped2":"de1f","singleton":"b31f"}
{"transient1":"fb3e","transient2":"849c","scoped1":"2c75","scoped2":"2c75","singleton":"b31f"}

Czytaj to w dwóch osiach — to jest cała lekcja:

W jednym żądaniu (w poziomie)Między żądaniami (w pionie)
Transientróżne — t1 ≠ t2różne
Scopedte same — s1 = s2różne
Singletonta samata sama — b31f aż do restartu

„Scope” w ASP.NET Core to jedno żądanie HTTP. Framework tworzy go, zanim wejdzie do twojego handlera, i wyrzuca po odesłaniu odpowiedzi.

Krok 4: konflikt, który zobaczysz w pracy

Do tej pory każdy serwis miał jeden oczywisty lifetime. Prawdziwe kłopoty zaczynają się, gdy dwa serwisy o różnym czasie życia muszą ze sobą rozmawiać. Zbudujemy dokładnie taką parę — obie klasy mają konkretną robotę.

project/Helpdesk/ICurrentUser.cs — kto wysłał to żądanie

public interface ICurrentUser
{
    string Name { get; }
}

public class HeaderCurrentUser(IHttpContextAccessor accessor) : ICurrentUser
{
    public string Name =>
        accessor.HttpContext?.Request.Headers["X-User"].ToString() is { Length: > 0 } name
            ? name
            : "anonim";
}

Nazwisko użytkownika bieżącego żądania. W prawdziwej aplikacji przyszłoby z tokena albo cookie; tutaj wystarczy nagłówek X-User, żeby dało się to sprawdzić curlem. Musi być Scoped — „bieżący użytkownik” istnieje tylko w kontekście jednego żądania. Rejestracja wymaga jeszcze builder.Services.AddHttpContextAccessor();.

project/Helpdesk/TicketMetrics.cs — ile zgłoszeń powstało od startu

public class TicketMetrics(ICurrentUser user)
{
    private int _created;

    public int Created => _created;

    public void RecordCreated()
    {
        _created++;
        Console.WriteLine($"[metrics] {user.Name} utworzył zgłoszenie; łącznie od startu: {_created}");
    }
}

Licznik dla całej instancji aplikacji, wystawiany przez GET /metrics. Musi być Singletonem — licznik zerujący się co żądanie nie jest licznikiem. Wywołaj metrics.RecordCreated() w endpoincie MapPost("/tickets"), dodaj app.MapGet("/metrics", (TicketMetrics m) => new { created = m.Created }); i zarejestruj: builder.Services.AddSingleton<TicketMetrics>();

Widzisz konflikt? Singleton (TicketMetrics) chce w konstruktorze coś, co żyje jedno żądanie (ICurrentUser). Uruchom:

System.AggregateException: Some services are not able to be constructed
 (Error while validating the service descriptor
  'ServiceType: TicketMetrics Lifetime: Singleton ImplementationType: TicketMetrics':
  Cannot consume scoped service 'ICurrentUser' from singleton 'TicketMetrics'.)
   ...
   at Microsoft.AspNetCore.Builder.WebApplicationBuilder.Build()

To captive dependency: singleton przytrzymałby („uwięziłby”) obiekt stworzony na jedno żądanie i używał go we wszystkich następnych. Twój licznik raportowałby w nieskończoność użytkownika, który akurat trafił jako pierwszy. Zwróć uwagę gdzie to wybucha — w builder.Build(). Ta sama linia, która w lekcji 0001 była granicą dwóch faz, jest też momentem, w którym kontener sprawdza spójność wszystkich rejestracji.

Ta walidacja działa tylko w Development. Ten sam kod na produkcji wstanie bez jednego słowa. Dlatego nigdy nie „naprawiaj” tego wyjątku przez zmianę środowiska — to jedyny moment, w którym framework mówi ci prawdę.

Dwa wyjścia — i tylko jedno jest wyjściem

Droga A: obniż lifetime singletona. AddScoped<TicketMetrics>() — wyjątek znika, aplikacja wstaje. Zrób dwa POST-y i sprawdź /metrics. Prawdziwy wynik:

konsola:  [metrics] wojtek utworzył zgłoszenie; łącznie od startu: 1
konsola:  [metrics] wojtek utworzył zgłoszenie; łącznie od startu: 1
GET /metrics  →  {"created":0}

Licznik dwa razy naliczył „pierwsze” zgłoszenie, a endpoint raportuje zero — bo każde żądanie dostało świeży, wyzerowany TicketMetrics. Kompiluje się, uruchamia, nie rzuca wyjątkiem i jest bezużyteczne. To jest ta sama pułapka co przy ITicketStore jako Scoped, tylko lepiej ukryta. Zapamiętaj to: „zszedłem z lifetime'em, żeby zniknął wyjątek” prawie zawsze znaczy „zepsułem serwis, żeby zniknął wyjątek”.

Droga B: nie wstrzykuj tego, co krótko żyje — podaj to w wywołaniu. Usuń zależność z konstruktora, przyjmij użytkownika jako argument metody:

public class TicketMetrics
{
    private int _created;
    public int Created => _created;

    public void RecordCreated(string user) { … }
}

a ICurrentUser wstrzyknij do endpointu, który i tak żyje jedno żądanie:

app.MapPost("/tickets", (string title, ITicketStore store,
                        TicketMetrics metrics, ICurrentUser user) =>
{
    var ticket = store.Add(title);
    metrics.RecordCreated(user.Name);
    return Results.Ok(ticket);
});

Prawdziwy wynik po trzech POST-ach z różnymi nagłówkami X-User:

konsola:  [metrics] wojtek utworzył zgłoszenie; łącznie od startu: 1
konsola:  [metrics] ania utworzył zgłoszenie; łącznie od startu: 2
konsola:  [metrics] anonim utworzył zgłoszenie; łącznie od startu: 3
GET /metrics  →  {"created":3}

Licznik jest jeden na aplikację, użytkownik prawidłowy przy każdym zapisie. Reguła, którą warto zabrać do pracy: stan długowieczny trzymaj w polu serwisu, dane jednego żądania przekazuj parametrem. Wstrzykiwanie przez konstruktor to deklaracja „potrzebuję tego przez całe swoje życie” — a bieżący użytkownik nigdy taki nie jest.4

4 Trzecia droga, na później: singleton, który naprawdę musi sięgnąć po coś scoped (np. zadanie w tle), wstrzykuje IServiceScopeFactory i tworzy scope ręcznie. Wzorzec jest w ściądze.

Obie klasy pokazują przy okazji primary constructor (C# 12): parametry zapisane po nazwie klasy są dostępne w całym jej ciele, bez pisania pól i przypisań. W firmowym kodzie zobaczysz obie formy — starą i tę.

Sprawdź się

Odpowiedz zanim klikniesz. Zła odpowiedź nie zdradza dobrej — spróbuj jeszcze raz.

Serwis Scoped wstrzyknięty dwa razy do jednego handlera daje:
Scope to jedno żądanie HTTP. W jego obrębie kontener zwraca tę samą instancję, ile razy by o nią nie poproszono — stąd s1 = s2 w wydruku.
Singleton wstrzykuje w konstruktorze serwis Scoped. Co się dzieje?
Kontener waliduje deskryptory w builder.Build(), więc aplikacja nie wstaje. Kompilator nic nie widzi — lifetime to informacja runtime'owa, nie część typu. Na produkcji walidacja jest wyłączona i błąd przechodzi cicho.
Który serwis musi być napisany w sposób thread-safe?
Singleton obsługuje wiele żądań równocześnie, na różnych wątkach. Scoped ma jedną instancję na żądanie, więc nie jest współdzielony. Docs: „Singleton services must be thread safe”.
Skąd minimal API wie, że ITicketStore store to serwis, a nie ciało żądania?
Od .NET 7 binder najpierw pyta kontener DI. Zarejestrowany typ → wstrzyknięcie; niezarejestrowany typ złożony → próba deserializacji z body. Stąd „Unable to resolve service…” przy zapomnianej rejestracji.
Singleton potrzebuje danych bieżącego żądania. Właściwa reakcja:
Obniżenie lifetime'u usuwa wyjątek i przy okazji odbiera serwisowi sens — licznik zerowałby się co żądanie. Wstrzyknięcie przez konstruktor to deklaracja „potrzebuję tego przez całe życie”, a dane żądania takie nie są. Zostaje trzecia opcja: podać je w wywołaniu metody.
Czym różni się Transient od Scoped w jednym żądaniu HTTP?

Transient tworzy nową instancję przy każdym rozwiązaniu — dwa parametry tego samego typu w jednym handlerze dostają dwie różne instancje. Scoped tworzy jedną na całe żądanie i zwraca ją wszystkim.

Dlaczego singleton nie może przyjąć scoped w konstruktorze?

Bo przytrzymałby tę instancję na całe życie aplikacji. Obiekt stworzony dla jednego żądania obsługiwałby wszystkie następne — czyli np. DbContext z zamkniętą transakcją i nieaktualnym cache. To captive dependency; odwrotny kierunek (scoped bierze singleton) jest bezpieczny.

Co robi builder.Services.AddScoped<ITicketStore, InMemoryTicketStore>()?

Nic nie tworzy. Zapisuje w kolekcji deskryptor: „typ usługi ITicketStore, implementacja InMemoryTicketStore, lifetime Scoped”. Instancja powstanie dopiero, gdy ktoś o nią poprosi.
