Lekcja 0008 · ~25 min · projekt Helpdesk

Walidacja: FluentValidation i jedno miejsce, przez które przechodzi każdy command

Cel: wyprowadzić if (string.IsNullOrWhiteSpace(...)) z handlera do osobnego walidatora, wpiąć walidację w dispatcher tak, żeby niepoprawny request nie dotarł do handlera, i zwrócić frontendowi komplet błędów w jednej odpowiedzi.

Wymaga: lekcji 0006 (ISender) i 0007 (ProblemDetails). Ściągi: FluentValidation, curl.

Uwaga: projekt poszedł dalej. Od lekcji 0010 Helpdesk używa MediatR — Sender, ISender, Unit i ValidationSender zostały skasowane, a HandleAsync nazywa się Handle. Ta lekcja jest migawką stanu sprzed migracji i celowo jej nie zmieniamy: bez ręcznego dispatchera nie da się zrozumieć, co robi biblioteka.

Problem: walidacja rozlana po handlerach

Po lekcji 0007 handler wygląda tak:

{
    if (string.IsNullOrWhiteSpace(command.Title))
    {
        throw new DomainException(TicketErrors.EmptyTitle);
    }

    var ticket = store.Add(command.Title);

}

Trzy rzeczy są tu nie tak:

ObjawKonsekwencja
ten sam if jest w CreateTicketHandler i w UpdateTicketHandlertrzecia komenda z tytułem = trzecia kopia; jedna zapomniana = dziura
handler zatrzymuje się na pierwszym błędzieformularz z pięcioma złymi polami poprawiasz pięć razy, klikając „zapisz” po każdym
reguła „tytuł niepusty” jest wymieszana z logiką zapisunie da się jej odczytać ani przetestować bez uruchamiania handlera
We frontendzie masz to samo rozróżnienie: zod/vee-validate sprawdza kształt formularza przed wysłaniem, a store dopiero wykonuje akcję. Walidator na backendzie to ten sam pomysł — z tą różnicą, że backendowi nie wolno zakładać, że frontend już sprawdził.

Krok 2: walidator jako osobny plik w slice’ie

project/Helpdesk/Features/Tickets/Commands/CreateTicket/CreateTicketValidator.cs

using FluentValidation;

namespace Helpdesk.Features.Tickets.Commands.CreateTicket;

public class CreateTicketValidator : AbstractValidator<CreateTicketCommand>
{
    public CreateTicketValidator()
    {
        RuleFor(command => command.Title)
            .NotEmpty().WithMessage("Tytuł zgłoszenia nie może być pusty.")
            .MaximumLength(100).WithMessage("Tytuł zgłoszenia może mieć najwyżej 100 znaków.");

        RuleFor(command => command.Priority)
            .NotEmpty().WithMessage("Priorytet jest wymagany.")
            .Must(TicketPriority.IsAllowed).WithMessage("Priorytet musi być jedną z wartości: low, normal, high.");
    }
}
ElementCo robi
AbstractValidator<T>klasa bazowa; T to typ walidowanej wiadomości — tu command, nie request
RuleFor(c => c.Title)lambda wskazuje pole; z niej FluentValidation wyciąga nazwę "Title" do odpowiedzi
.NotEmpty(), .MaximumLength(n)gotowe reguły — jest ich kilkadziesiąt (EmailAddress, InclusiveBetween, Matches…)
.Must(predykat)furtka na własną regułę: dowolna funkcja zwracająca bool
.WithMessage(...)komunikat dla człowieka; bez tego dostajesz angielski tekst domyślny
Walidujemy command, nie request. Request to kształt JSON-a z sieci, command to intencja, którą rozumie domena — i to command trafia do dispatchera. Reguła powieszona na commandzie zadziała dla wszystkich wywołań, także tych spoza HTTP (job w tle, test, inny endpoint).
Reguły w jednym łańcuchu domyślnie nie zatrzymują się na pierwszym niepowodzeniu. Pusty priorytet łamie NotEmpty i Must — dostaniesz dwa komunikaty dla jednego pola (sprawdzone niżej, w tabeli weryfikacyjnej). Jeśli chcesz przerwać po pierwszym: .Cascade(CascadeMode.Stop).

Krok 3: pipeline behavior, czyli dekorator dispatchera

Walidator sam się nie uruchomi — ktoś musi go zawołać. Chcemy jednego takiego miejsca dla wszystkich komend. To miejsce już mamy: ISender z lekcji 0006.

project/Helpdesk/Common/Validation/ValidationSender.cs

using FluentValidation;
using FluentValidation.Results;

namespace Helpdesk.Common.Validation;

/// <summary>Dekorator ISender: uruchamia walidatory wiadomości przed przekazaniem jej do handlera.</summary>
public class ValidationSender(Sender inner, IServiceProvider provider) : ISender
{
    public async Task<TResult> Send<TResult>(ICommand<TResult> command, CancellationToken ct = default)
    {
        await ValidateAsync(command, ct);

        return await inner.Send(command, ct);
    }

    public async Task<TResult> Send<TResult>(IQuery<TResult> query, CancellationToken ct = default)
    {
        await ValidateAsync(query, ct);

        return await inner.Send(query, ct);
    }

    private async Task ValidateAsync(object message, CancellationToken ct)
    {
        var validatorType = typeof(IValidator<>).MakeGenericType(message.GetType());
        var validators = provider.GetServices(validatorType).Cast<IValidator>();
        var context = new ValidationContext<object>(message);

        var failures = new List<ValidationFailure>();

        foreach (var validator in validators)
        {
            var result = await validator.ValidateAsync(context, ct);
            failures.AddRange(result.Errors);
        }

        if (failures.Count > 0)
        {
            throw new ValidationException(failures);
        }
    }
}
FragmentPo co
(Sender inner, ...)dekorator: klasa implementuje ISender i opakowuje prawdziwy Sender. Endpointy nadal wstrzykują ISender i o niczym nie wiedzą.
MakeGenericType(message.GetType())z IValidator<> robi IValidator<CreateTicketCommand> — typ znany dopiero w czasie działania (ten sam trik co w Sender)
GetServices(...)liczba mnoga: jedna komenda może mieć kilka walidatorów. Brak walidatora = pusta lista, nie wyjątek.
Cast<IValidator>()niegeneryczny IValidator ma ValidateAsync(IValidationContext, ct) — dzięki temu nie potrzeba tu dynamic
throw new ValidationException(failures)wyjątek z pakietu FluentValidation, niosący komplet błędów, nie pierwszy z brzegu
To jest „pipeline behavior”. W MediatR ta sama rzecz nazywa się IPipelineBehavior<TRequest, TResponse> i ma metodę Handle(request, next, ct), gdzie next() to nasze inner.Send(...). Zespół, który mówi „walidacja jest w behaviorze”, ma dokładnie ten kod. Obok zobaczysz behaviory do logowania, transakcji i pomiaru czasu — wszystkie w tym samym miejscu, jedno owinięcie na drugim.
To ten sam pomysł, co middleware w Express albo interceptor w Axiosie: warstwa, przez którą przechodzi każde żądanie, zanim dojdzie do właściwej obsługi.

Krok 4: ValidationException → jedna odpowiedź z kompletem błędów

Rzucony wyjątek trzeba zamienić na JSON. Robimy to dokładnie tak jak w lekcji 0007 — drugim IExceptionHandler.

project/Helpdesk/Common/Errors/ValidationExceptionHandler.cs

public class ValidationExceptionHandler(IProblemDetailsService problemDetailsService) : IExceptionHandler
{
    public async ValueTask<bool> TryHandleAsync(HttpContext httpContext, Exception exception, CancellationToken ct)
    {
        if (exception is not ValidationException validationException)
        {
            return false;
        }

        httpContext.Response.StatusCode = StatusCodes.Status400BadRequest;

        return await problemDetailsService.TryWriteAsync(new ProblemDetailsContext
        {
            HttpContext = httpContext,
            Exception = exception,
            ProblemDetails =
            {
                Title = "Nieprawidłowe żądanie",
                Detail = "Popraw zaznaczone pola i wyślij formularz ponownie.",
                Status = StatusCodes.Status400BadRequest,
                Extensions =
                {
                    ["code"] = "validation_failed",
                    ["errors"] = ToErrorsByField(validationException)
                }
            }
        });
    }

    private static Dictionary<string, string[]> ToErrorsByField(ValidationException exception) =>
        exception.Errors
            .GroupBy(failure => JsonNamingPolicy.CamelCase.ConvertName(failure.PropertyName))
            .ToDictionary(group => group.Key, group => group.Select(failure => failure.ErrorMessage).ToArray());
}

Walidacja czy reguła domenowa?

Pytanie rozstrzygające: czy da się to stwierdzić, patrząc wyłącznie na treść żądania?

WalidacjaReguła domenowa
Skąd wiadomoz samego requestuze stanu systemu (baza, inne zgłoszenia)
Gdzie mieszkaAbstractValidator, przed handleremwewnątrz handlera
Ile błędów narazkomplet, w errorsjeden — pierwszy, który wystąpił
Status400404 / 409 / 403
Kształt ciałacode: validation_failed + errorspojedynczy code, bez errors
Przykładpusty tytuł, priorytet spoza listyzgłoszenie nie istnieje, e-mail zajęty, zamknięte zgłoszenie nie przyjmuje zmian
Dlatego w formularzu rejestracji „hasła się nie zgadzają” i „zły format e-maila” wracają razem w jednym 400, a „ten e-mail jest już zajęty” przychodzi osobno jako 409 — do bazy w ogóle nie doszło, dopóki pięć pól było zepsutych.

Uwaga bezpieczeństwa: przy publicznej rejestracji odpowiedź „e-mail zajęty” pozwala sprawdzać, kto ma konto (user enumeration). Wtedy zwraca się to samo niezależnie od wyniku i rozstrzyga mailem. Ta sama zasada co Forbidden → 404 z lekcji 0007.

Dwa błędy, które warto wywołać celowo

1. Zapomniane AddValidation() — cisza zamiast błędu

Usuń builder.Services.AddValidation(); z Program.cs i wyślij pusty tytuł:

Dlatego walidacja musi mieć test — brak walidatora nie objawia się niczym poza przyjętym śmieciem.

Po co walidować CreateTicketCommand, a nie CreateTicketRequest?
Walidacja siedzi w dekoratorze ISender, a przez ISender przechodzą komendy. Gdyby regułę powiesić na requeście, każde wywołanie spoza HTTP (job w tle, test, inny endpoint) ominęłoby ją bez śladu.
Czemu w errors pod jednym polem jest tablica, a nie jeden tekst?
Pusty priorytet łamie naraz NotEmpty i Must — sprawdzone: dwa komunikaty pod kluczem priority. Łańcuch reguł domyślnie nie zatrzymuje się na pierwszym błędzie.
„E-mail jest już zajęty” — walidator czy handler?
Walidator dostaje wyłącznie treść żądania. Wszystko, co wymaga stanu systemu, to reguła domenowa — DomainException z lekcji 0007, status 409 albo 404, jeden kod błędu.
Co się dzieje, gdy komenda nie ma żadnego walidatora?
GetServices (liczba mnoga) na brak rejestracji zwraca pustą listę, nie wyjątek. To wygodne — nie każda komenda potrzebuje walidatora — ale oznacza, że zapomniany walidator jest niewidoczny aż do produkcji.

Zapamiętaj bez zaglądania

Gdzie odpala się walidacja i skąd wie, który walidator wziąć?

W ValidationSender — dekoratorze ISender, przed inner.Send(...). Typ walidatora składany jest w czasie działania: typeof(IValidator<>).MakeGenericType(message.GetType()), potem provider.GetServices(...). Same walidatory rejestruje skan assembly (AddValidatorsFromAssemblyContaining<Program>()).

Czym różni się odpowiedź na walidację od odpowiedzi na regułę domenową?

Walidacja: 400, code: "validation_failed", słownik errors z kompletem pól. Reguła domenowa: 404/409/403, jeden code (np. ticket.not_found), bez errors. Kryterium podziału: czy do rozstrzygnięcia potrzebny jest stan systemu.

Kiedy ciało żądania musi iść z pliku, a nie z -d '...'?

Gdy zawiera polskie znaki. Git Bash konwertuje argumenty na windowsową stronę kodową i UTF-8 się psuje — API zwraca 500 z Cannot transcode invalid UTF-8 JSON text. Wtedy: cat > body.json <<'JSON' i --data-binary @body.json. Spacje w wartościach są w porządku.
