Lekcja 0005 · ~20 min · projekt Helpdesk

Command vs Query: pierwszy własny handler

Cel: wyjąć logikę z lambdy endpointu do osobnej klasy — CreateTicketHandler — i nazwać rzecz po imieniu: command zmienia stan, query tylko czyta. Po drodze pierwszy raz w tym kursie pojawia się async/await. To jest lekcja, po której zaczniesz rozpoznawać kształt firmowego kodu.

Wymaga: lekcji 0004 (Features/Tickets/). Ściąga: Command / Query — handlery.

Problem: lambda, która puchnie

Twój POST wygląda dziś tak:

tickets.MapPost("/", (CreateTicketRequest request, ITicketStore store,
                     TicketMetrics metrics, ICurrentUser user) =>
{
    var ticket = store.Add(request.Title);
    metrics.RecordCreated(user);
    return TypedResults.Created($"/tickets/{ticket.Id}", ticket);
});

Dwie linie logiki — jeszcze czytelne. Ale „utwórz zgłoszenie" w prawdziwym systemie znaczy: zwaliduj tytuł, sprawdź czy użytkownik ma uprawnienia, zapisz, zwiększ metrykę, wyślij powiadomienie na maila, dopisz wpis do audytu. Sześć kroków w lambdzie zarejestrowanej wewnątrz metody rozszerzającej. Nie da się tego przetestować bez podnoszenia serwera, nie da się wywołać z innego miejsca, a MapTickets rośnie do 200 linii.

Rozwiązanie jest banalne w opisie: logika idzie do klasy, endpoint tylko ją woła. Cała lekcja jest o tym, jak ta klasa wygląda w .NET-cie i dlaczego akurat tak.

Command i Query — dwa słowa, jedna reguła

CommandQuery
Co robizmienia stanczyta stan
Twoje endpointyPOST, PUT, DELETEGET
Niezmienniki domenytak — walidacja, reguły przejść stanunie ma czego chronić
Autoryzacjatak — po obu stronach, zawsze
Zwracaminimum (id, potwierdzenie)dane w kształcie wygodnym dla UI
Można powtórzyć bezkarnienietak

To jest CQRS — Command Query Responsibility Segregation. Nazwa brzmi ciężko, a w wersji, którą dziś napiszesz, to po prostu dwa interfejsy i konwencja nazewnicza. Wersje ciężkie (osobne bazy do zapisu i odczytu, event sourcing) istnieją, ale nie zaczyna się od nich i twój zespół najpewniej też ich nie ma.

„Commands should represent specific business tasks instead of low-level data updates. For example, in a hotel-booking app, use the command Book hotel room instead of Set ReservationStatus to Reserved.” — Microsoft, CQRS Pattern. Stąd nazwy: CreateTicketCommand, AssignTicketCommand, CloseTicketCommand — nie UpdateTicketStatusCommand.

Krok 1: dwa interfejsy

project/Helpdesk/Common/Cqrs.cs

namespace Helpdesk.Common;

/// <summary>Obsługuje jedną operację zmieniającą stan.</summary>
public interface ICommandHandler<in TCommand, TResult>
{
    Task<TResult> HandleAsync(TCommand command, CancellationToken cancellationToken = default);
}

/// <summary>Obsługuje jedno zapytanie o dane, bez zmiany stanu.</summary>
public interface IQueryHandler<in TQuery, TResult>
{
    Task<TResult> HandleAsync(TQuery query, CancellationToken cancellationToken = default);
}

Cztery rzeczy w tych sześciu linijkach:

  • <TCommand, TResult> — generyki. Jak Ref<T> w Vue: klasa parametryzowana typem. Zapis ICommandHandler<CreateTicketCommand, Ticket> czyta się „handler, który przyjmuje CreateTicketCommand i zwraca Ticket”.
  • in przed TCommand. Kontrawariancja — mówi, że typ wchodzi do środka i nigdy nie wychodzi. Na razie nic ci nie daje; wpisz i zapomnij, wróci przy pipeline'ach w lekcji 0008.
  • Task<T>. Odpowiednik Promise<T>. Twój handler jest dziś w pełni synchroniczny, ale interfejs musi być asynchroniczny od początku — w lekcji 0009 wejdzie EF Core i każde `SaveChangesAsync` będzie prawdziwym await. Zmiana sygnatury interfejsu później to przepisanie wszystkich handlerów naraz.
  • CancellationToken. Sygnał „klient rozłączył się, przestań pracować”. Framework wstrzykuje go sam. Odpowiednik AbortSignal z fetch.

Krok 2: command i jego handler

Konwencja vertical slices: jeden plik na przypadek użycia, a w nim wszystko, co ten przypadek opisuje.

project/Helpdesk/Features/Tickets/CreateTicket.cs

using Helpdesk.Common;

namespace Helpdesk.Features.Tickets;

public record CreateTicketCommand(string Title);

public class CreateTicketHandler(ITicketStore store, TicketMetrics metrics, ICurrentUser user)
    : ICommandHandler<CreateTicketCommand, Ticket>
{
    public Task<Ticket> HandleAsync(CreateTicketCommand command, CancellationToken cancellationToken = default)
    {
        var ticket = store.Add(command.Title);
        metrics.RecordCreated(user);
        return Task.FromResult(ticket);
    }
}

Task.FromResult(x) to „gotowy Task z wartością w środku”, czyli Promise.resolve(x). Używasz go, bo nic tu jeszcze nie jest asynchroniczne — nie ma na co czekać. Metoda nie jest oznaczona async, bo nie ma w niej await.

Nie rób async bez await. Kompilator zaakceptuje public async Task<Ticket> HandleAsync(…) { return ticket; }, ale rzuci ostrzeżenie CS1998 i wygeneruje maszynę stanów, która nic nie robi. Dopóki nie masz na co czekać — Task.FromResult.

Dlaczego handler może wstrzyknąć ICurrentUser

W lekcji 0002 wstrzyknięcie Scoped ICurrentUser do Singletona wysadziło aplikację przy starcie. Tutaj jest dokładnie odwrotnie — i to jest w porządku, bo handler zarejestrujesz jako Scoped. Scoped wolno zależeć od Scoped i od Singletona; zakazany jest tylko kierunek „długowieczny sięga po krótkowiecznego”.

Spróbuj zarejestrować handler jako Singleton, a dostaniesz to (sprawdzone):

System.InvalidOperationException: Cannot consume scoped service
'Helpdesk.Common.ICurrentUser' from singleton
'Helpdesk.Common.ICommandHandler`2[CreateTicketCommand,Ticket]'.

Ten sam wyjątek co w lekcji 0002, tylko z twoim własnym typem w środku. Handlery są Scoped — zawsze. Żyją tyle, co jedno żądanie, i tyle mają żyć.

Krok 3: query

project/Helpdesk/Features/Tickets/GetTicket.cs

using Helpdesk.Common;

namespace Helpdesk.Features.Tickets;

public record GetTicketQuery(int Id);

public class GetTicketHandler(ITicketStore store) : IQueryHandler<GetTicketQuery, Ticket?>
{
    public Task<Ticket?> HandleAsync(GetTicketQuery query, CancellationToken cancellationToken = default)
        => Task.FromResult(store.GetById(query.Id));
}

Query nie ma TicketMetrics — i to jest reguła, nie oszczędność: odczyt nie zmienia stanu, więc nie sięga po nic, co coś zmienia. Jeśli zobaczysz query, które zapisuje, nazwa kłamie.

Nie ma też ICurrentUser, ale to wyłącznie dlatego, że w tym projekcie zgłoszenia nie mają jeszcze właściciela. Gdy go dostaną, query będzie go potrzebowało — patrz sekcja niżej.

Ticket? jako TResult jest celowe: „może nie być takiego zgłoszenia” jest częścią kontraktu handlera, a nie czymś, co endpoint sobie dopowiada.

Autoryzacja dotyczy też query

Powyższa tabela mówi, że query nie ma reguł biznesowych — i to jest prawda tylko o niezmiennikach. Autoryzacja to osobna sprawa i obowiązuje po obu stronach. Twoje dzisiejsze API ma tu dziurę: GET /tickets/42 odda zgłoszenie każdemu, kto zgadnie liczbę. Ta podatność nazywa się IDOR (Insecure Direct Object Reference) i siedzi w OWASP Top 10 jako Broken Access Control.

Rodzaj autoryzacjiPytanieGdzie w kodzie
deklaratywnaczy to zalogowany serwisant?na trasie: .RequireAuthorization("Agent") na grupie
zasobowaczy to zgłoszenie należy do tego użytkownika?w handlerze — wymaga wczytania danych

Drugiej nie da się rozstrzygnąć na poziomie trasy, bo odpowiedź zależy od tego, co leży w bazie pod tym id.

Filtruj u źródła, nie po fakcie

Odruch jest taki:

var ticket = store.GetById(query.Id);
if (ticket.OwnerId != user.Id) return null;   // sprawdzenie po fakcie

Lepszy wzorzec: zapytanie od początku zawężone do tego, co użytkownik ma prawo widzieć.

public class GetTicketHandler(ITicketStore store, ICurrentUser user)
    : IQueryHandler<GetTicketQuery, Ticket?>
{
    public Task<Ticket?> HandleAsync(GetTicketQuery query, CancellationToken ct = default)
        => Task.FromResult(store.GetVisibleTo(query.Id, user.Name));
}

Różnica nie jest kosmetyczna. Przy sprawdzaniu po fakcie każde nowe query to osobna szansa, żeby zapomnieć o if-ie — a zapomniany if nie wywala testu, tylko cicho oddaje cudze dane. Przy filtrowaniu u źródła nie ma czego zapomnieć, bo nie istnieje metoda zwracająca niezawężone dane. Przy EF Core (lekcja 0009) robi to global query filter: jedna linia w DbContext, po której każde zapytanie w aplikacji jest zawężone automatycznie.

404 czy 403? Gdy ktoś prosi o cudze zgłoszenie, 403 Forbidden jest uczciwe, ale potwierdza istnienie zasobu — wystarczy przelecieć id od 1 do 10000, żeby poznać rozmiar systemu i zajęte identyfikatory. Dla danych wrażliwych standardem jest 404. Przy filtrowaniu u źródła dostajesz to za darmo: handler zwraca null, endpoint robi TypedResults.NotFound() i w ogóle nie wie, że autoryzacja istnieje.

Mechanika autoryzacji w ASP.NET Core — [Authorize], polityki, IAuthorizationHandler, resource-based authorization — to osobny temat, poza zakresem kursu na tym etapie. Tutaj chodzi o samo umiejscowienie: gdzie ta decyzja zapada, nie czym się ją zapisuje.

Aktualizacja struktury. Po tej lekcji projekt rozrósł się do sześciu przypadków użycia i płaskie pliki w Features/Tickets/ przestały wystarczać. Docelowy układ (obowiązujący od lekcji 0006) to folder na przypadek użycia: Features/Tickets/Commands/CreateTicket/ z CreateTicketCommand.cs, CreateTicketHandler.cs i CreateTicketEndpoint.cs, oraz analogicznie Queries/GetTicket/. Endpoint przestaje być lambdą — to public static class XEndpoint z metodą Map i prywatną HandleAsync.

Krok 4: rejestracja i endpointy

Handler to zwykły serwis — rejestruje się tak jak wszystko inne. W TicketsFeature.AddTickets:

services.AddScoped<ICommandHandler<CreateTicketCommand, Ticket>, CreateTicketHandler>();
services.AddScoped<IQueryHandler<GetTicketQuery, Ticket?>, GetTicketHandler>();

I endpointy, które teraz nie wiedzą już nic o ITicketStore:

tickets.MapPost("/",
    async (CreateTicketRequest request,
           ICommandHandler<CreateTicketCommand, Ticket> handler,
           CancellationToken cancellationToken) =>
    {
        var ticket = await handler.HandleAsync(new CreateTicketCommand(request.Title), cancellationToken);
        return TypedResults.Created($"/tickets/{ticket.Id}", ticket);
    });

tickets.MapGet("/{id:int}",
    async Task<Results<Ok<Ticket>, NotFound>> (
        int id,
        IQueryHandler<GetTicketQuery, Ticket?> handler,
        CancellationToken cancellationToken) =>
    {
        var ticket = await handler.HandleAsync(new GetTicketQuery(id), cancellationToken);
        if (ticket is { } found)
        {
            return TypedResults.Ok(found);
        }
        return TypedResults.NotFound();
    });

Zwróć uwagę na typ przy GET: async Task<Results<Ok<Ticket>, NotFound>>. Do unii z lekcji 0003 doszło opakowanie w Task — dokładnie tak, jak w TS Ticket | null staje się Promise<Ticket | null>. Kolejność słów jest sztywna: async, typ, lista parametrów, =>.

Przy POST nie musisz pisać typu jawnie, bo jest tylko jedna gałąź wyniku i kompilator sam go wywnioskuje.

Co dostajesz w zamian

  • Testowalność. new CreateTicketHandler(store, metrics, user).HandleAsync(cmd) — zwykłe wywołanie metody, bez serwera HTTP. To będzie połowa lekcji 0011.
  • Jedno miejsce na regułę. Walidacja tytułu doda się w handlerze i zadziała niezależnie od tego, ile endpointów go woła.
  • Nazwa zamiast opisu. CreateTicketCommand w liście plików mówi, co system potrafi. Lambda w środku MapTickets nie mówi nic.

Diagnostyka: jeden błąd, który zobaczysz na pewno

Zapomnisz zarejestrować handler w AddTickets — kod się zbuduje, a POST zwróci 500 z tym w konsoli (sprawdzone):

System.InvalidOperationException: Failure to infer one or more parameters.
Below is the list of parameters that we found:

Parameter           | Source
--------------------------------------------------
request             | Body (Inferred)
handler             | UNKNOWN

Ten komunikat jest lepszy, niż się wydaje: pokazuje tabelkę bindera z lekcji 0003 i mówi wprost, którego parametru nie umiał przypisać do żadnego źródła. UNKNOWN przy typie, który miał przyjść z DI, znaczy zawsze jedno — brak rejestracji.

Zauważ różnicę w momencie wykrycia: captive dependency wysadza aplikację przy starcie (walidacja kontenera w Build()), a brak rejestracji dopiero przy pierwszym żądaniu na ten endpoint. Dlatego literówka w rejestracji rzadkiego endpointu potrafi dojechać na produkcję. Test integracyjny, który dotyka każdej trasy, wyłapuje to za darmo — kolejny argument z lekcji 0011.

Sprawdź się

Odpowiedz zanim klikniesz. Zła odpowiedź nie zdradza dobrej — spróbuj jeszcze raz.

Dlaczego handlery rejestruje się jako Scoped, a nie Singleton?
Handler sięga po ICurrentUser, a docelowo po DbContext — oba Scoped. Singleton nie może konsumować Scoped; kontener wysadza aplikację przy Build() komunikatem „Cannot consume scoped service”. Koszt tworzenia jest tu bez znaczenia.
Handler nic nie awaituje. Jak zwrócić Task<Ticket>?
Task.FromResult to gotowy Task z wartością — Promise.resolve. async bez await daje ostrzeżenie CS1998 i niepotrzebną maszynę stanów, a Task.Run dokłada skok na inny wątek puli, żeby wykonać dwie linie synchronicznego kodu.
Konsola: „Failure to infer one or more parameters”, przy handlerze UNKNOWN. Co to znaczy?
Binder szuka źródła dla każdego parametru. Typ złożony spoza kontenera trafiłby do body, ale body jest już zajęte przez pierwszy parametr — zostaje UNKNOWN. Praktycznie zawsze znaczy to brakującą linię AddScoped.
Które z tych to command, a nie query?
Command zmienia stan systemu; dwa pozostałe tylko czytają, choćby wymagały skomplikowanego zapytania. Kryterium to skutek uboczny, nie złożoność. Nazwa dobrego commanda opisuje zadanie biznesowe („przypisz”), nie operację na danych („ustaw pole AssignedTo”).
Użytkownik prosi o cudze zgłoszenie po id. Co zwrócić?
403 potwierdza istnienie zasobu — wystarczy przelecieć kolejne id, żeby poznać rozmiar systemu. 404 nie wycieka nic i wychodzi naturalnie, gdy query jest zawężone u źródła: handler nic nie znalazł, więc endpoint zwraca „nie ma”. Okrojony zestaw pól to nadal wyciek: potwierdza istnienie.
Czym różni się command od query — w jednym zdaniu?

Command zmienia stan i niesie reguły biznesowe; query tylko czyta i nie ma prawa niczego zmienić. Stąd reszta różnic: query wolno powtórzyć bezkarnie, command nie.

Po co interfejs handlera jest asynchroniczny, skoro implementacja nie jest?

Bo przy EF Core (lekcja 0009) każdy zapis stanie się prawdziwym await. Zmiana sygnatury interfejsu później oznacza przepisanie wszystkich handlerów i wszystkich endpointów naraz. Task.FromResult to koszt jednej linii dzisiaj zamiast refactoru jutro.

Query nie ma reguł biznesowych — czy to znaczy, że nie sprawdza uprawnień?

Nie. Bez reguł jest tylko wobec niezmienników — odczyt niczego nie psuje, więc nie ma czego chronić. Autoryzacja obowiązuje tak samo po stronie odczytu; jej brak to IDOR. Wzorzec: zawężaj zapytanie u źródła, nie sprawdzaj własności po wczytaniu, i zwracaj 404 zamiast 403, żeby nie potwierdzać istnienia zasobu.

Kiedy kontener wykrywa captive dependency, a kiedy brak rejestracji?

Captive dependency — przy starcie, w builder.Build(), bo walidacja przechodzi po wszystkich deskryptorach. Brak rejestracji — dopiero przy pierwszym żądaniu na dany endpoint, bo dopiero wtedy binder próbuje wypełnić parametry.

Co dalej

Masz handlery, ale wołasz je ręcznie: endpoint wstrzykuje konkretny ICommandHandler<CreateTicketCommand, Ticket> i sam składa command. Przy dwudziestu przypadkach użycia to dwadzieścia różnych typów wstrzykiwanych w dwudziestu miejscach — i nie ma gdzie wpiąć czegoś, co ma się dziać przy każdym commandzie: logowania, walidacji, transakcji. Lekcja 0006: dispatcher — jeden ISender, któremu podajesz command, a on znajduje właściwy handler. Napiszesz go sam, żeby zobaczyć, że to trzydzieści linii refleksji, a dopiero potem podmienimy go na MediatR — bibliotekę, którą czytasz w firmowym repo.
