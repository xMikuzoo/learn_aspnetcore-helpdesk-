Lekcja 0009 · ~25 min · projekt Helpdesk

Prawdziwa baza: EF Core, SQLite i migracje

Cel: wymienić InMemoryTicketStore na bazę na dysku, wygenerować i zaaplikować pierwszą migrację, zobaczyć SQL, który EF wysyła w twoim imieniu — i wreszcie napisać handler, w którym async naprawdę na coś czeka.

Wymaga: lekcji 0002 (lifetimes), 0005 (handlery), 0007 (DomainException). Ściągi: EF Core + migracje, curl.

Jak czytać tę lekcję. Kod C# jest już w repo — przeczytasz go i zrozumiesz. Migracji nie ma i aplikacja bez niej nie wystartuje poprawnie. To twoja część: dwie komendy z kroku 4 i sprawdzenie, co po nich powstało.

Dlaczego to jest ważna lekcja

Do tej pory zgłoszenia żyły w List<Ticket> wewnątrz singletona. Wyłączasz aplikację — dane znikają. To wystarczało, żeby uczyć się DI i CQRS, ale ma trzy konsekwencje, które teraz naprawiamy:

In-memory (0003–0008)Baza (0009)
dane w RAM, giną przy restarciedane w pliku helpdesk.db, przeżywają restart
ręczny lock, bo singleton dzielony między wątkamibrak lock — jeden DbContext na żądanie
Task.FromResult(...) — async na nibyawait na prawdziwym I/O
Analogia z frontendu. InMemoryTicketStore to był Pinia store — stan w pamięci karty przeglądarki. EF Core to Prisma albo Drizzle: opisujesz model w kodzie, generator produkuje migracje SQL, a ty piszesz zapytania w języku hosta zamiast w stringach. Nawet komendy się rymują: prisma migrate dev ≈ dotnet ef migrations add + database update.

Krok 0 — sprawdź narzędzie

Migracje generuje osobny program CLI, instalowany globalnie, nie pakietem projektu:

dotnet ef --version
dotnet tool update --global dotnet-ef

Jeśli narzędzie jest starsze niż biblioteka, zobaczysz przy każdej komendzie ostrzeżenie — ostrzeżenie, nie błąd, wszystko zadziała:

The Entity Framework tools version '10.0.7' is older than that of the runtime '10.0.11'.

Krok 1 — pakiety i connection string

dotnet add package Microsoft.EntityFrameworkCore.Sqlite
dotnet add package Microsoft.EntityFrameworkCore.Design

Sqlite to provider — kawałek EF-a, który wie, jak zamienić LINQ na SQL akurat tego dialektu. W pracy w tym miejscu będzie .SqlServer albo Npgsql.EntityFrameworkCore.PostgreSQL; reszta kodu z tej lekcji zostaje bez zmian. Design jest potrzebny tylko do generowania migracji, dlatego NuGet dopisał mu PrivateAssets="all" — nie pojedzie na produkcję.

appsettings.json

"ConnectionStrings": {
  "Helpdesk": "Data Source=helpdesk.db"
}

Cały connection string SQLite to ścieżka do pliku. W firmie będzie tam host, baza, użytkownik i hasło — i dlatego nie będzie w appsettings.json, tylko w zmiennych środowiskowych albo user secrets.

Krok 2 — Ticket przestaje być record-em

Features/Tickets/Ticket.cs — przed i po

public record Ticket(int Id, string Title, string Priority);

public class Ticket
{
    private Ticket(string title, string priority)
    {
        Title = title;
        Priority = priority;
    }

    public int Id { get; private set; }
    public string Title { get; private set; }
    public string Priority { get; private set; }

    public static Ticket Create(string title, string priority) => new(title, priority);

    public void Rename(string title) => Title = title;

    public void ChangePriority(string priority) => Priority = priority;
}

Zmieniły się dwie niezależne rzeczy. Pierwsza jest wymuszona przez EF, druga to styl twojego zespołu — i dobrze, żeby kod kursu wyglądał jak kod, który czytasz w pracy.

Dlaczego class, a nie record — wymóg EF

EF Core działa na change trackingu: wczytuje wiersz, zapamiętuje jego wartości, a przy SaveChangesAsync porównuje i wysyła UPDATE tylko dla zmienionych kolumn. Żeby to miało sens, EF musi zobaczyć zmianę na tym samym obiekcie:

ticket.Rename(command.Title);
await db.SaveChangesAsync(cancellationToken);

Z niemutowalnym record-em pisałbyś ticket with { Title = ... }, co tworzy nowy obiekt — a EF nadal śledzi stary i nie ma o czym pisać UPDATE-a. Stąd reguła:

Encja to class. DTO i command to record. TicketDto i CreateTicketCommand zostały bez zmian — to dobrze. Encja mówi „jak to leży w bazie”, DTO mówi „co widzi frontend”. Rozdzielone, bo dodanie kolumny InternalNotes nie ma prawa wyciec do JSON-a, a zmiana kontraktu API nie ma prawa wymagać migracji.

Dlaczego prywatny konstruktor i Create() — decyzja projektowa

Konstruktor jest prywatny, settery są prywatne, więc spoza klasy nie da się utworzyć ani zmienić zgłoszenia inaczej niż przez metodę o konkretnej nazwie. Te dwie linie się już nie kompilują:

var t = new Ticket { Title = "x" };   // niedostępny konstruktor
ticket.Title = "cokolwiek";           // niedostępny setter

Co to kupuje: Create() jest jedynym wejściem, więc gdy pojawi się reguła „nowe zgłoszenie zawsze startuje ze statusem open”, jest dokładnie jedno miejsce, gdzie ją dopisać — i żadnego sposobu, żeby ją ominąć. Tak samo Rename(): jeśli kiedyś tytułu nie będzie wolno zmieniać w zamkniętym zgłoszeniu, if ląduje w metodzie, a nie w każdym handlerze, który akurat coś zapisuje.

Dziś Create() nic nie sprawdza i wygląda na ceremonię. To normalne — sens tego układu widać dopiero przy przejściach statusów (Close(), Assign()), do których dojdziemy. Ważne jest, że miejsce na regułę już istnieje.

To jest ten sam ruch co z ITicketStore. Zwężasz to, co da się wywołać, żeby nie dało się wywołać czegoś złego. Interfejs ukrywa bazę przed handlerem; prywatny setter ukrywa pole przed wszystkim poza encją.

Dwa haczyki, na które trafisz

1. Nazwy parametrów konstruktora muszą się zgadzać z nazwami właściwości. EF materializuje encję refleksją — modyfikatory dostępu go nie obowiązują, ale wiązanie parametrów idzie po nazwie, nie po pozycji. Przemianuj title na ticketTitle, a projekt zbuduje się z zerem ostrzeżeń, aplikacja wstanie, i dopiero pierwszy GET da 500:

System.InvalidOperationException: No suitable constructor was found for the type 'Ticket'.
The following constructors had parameters that could not be bound to properties of the type:
    Cannot bind 'ticketTitle' in 'Ticket(string ticketTitle, string priority)'

Jeśli chcesz mieć wolne nazwy parametrów, dołóż prywatny bezparametrowy konstruktor — EF użyje jego i wypełni właściwości setterami.

2. HasData przestaje przyjmować encję, bo new Ticket { Id = 1, ... } już się nie skompiluje. Idzie tam typ anonimowy — to rozwiązanie z dokumentacji, nie obejście, bo seed i tak trafia do migracji jako InsertData, a nie jako tworzenie obiektu:

ticket.HasData(
    new { Id = 1, Title = "Pierwsze zgłoszenie", Priority = "normal" },
    new { Id = 2, Title = "Drugie zgłoszenie!", Priority = "high" });

Krok 3 — DbContext i konfiguracja per encja

DbContext jest celowo chudy — nie wie nic o kolumnach ani o kluczach:

Common/Persistence/HelpdeskDbContext.cs

public class HelpdeskDbContext(DbContextOptions<HelpdeskDbContext> options) : DbContext(options)
{
    public DbSet<Ticket> Tickets => Set<Ticket>();

    protected override void OnModelCreating(ModelBuilder modelBuilder) =>
        modelBuilder.ApplyConfigurationsFromAssembly(typeof(HelpdeskDbContext).Assembly);
}

Cały opis tabeli mieszka obok encji, w osobnej klasie implementującej IEntityTypeConfiguration<T>:

Features/Tickets/TicketConfiguration.cs

public class TicketConfiguration : IEntityTypeConfiguration<Ticket>
{
    public void Configure(EntityTypeBuilder<Ticket> builder)
    {
        builder.HasKey(t => t.Id);
        builder.Property(t => t.Title).IsRequired().HasMaxLength(100);
        builder.Property(t => t.Priority).IsRequired().HasMaxLength(20);

        builder.HasData(
            new { Id = 1, Title = "Pierwsze zgłoszenie", Priority = "normal" },
            new { Id = 2, Title = "Drugie zgłoszenie!", Priority = "high" });
    }
}

Trzy rzeczy warte nazwania:

  • DbSet<Ticket> Tickets — tabela. db.Tickets.Where(...) to nie filtrowanie listy, tylko budowanie SELECT-a.
  • Configure — miejsce, gdzie dopowiadasz to, czego EF nie wywnioskuje z samych typów: klucz, wymagalność, długość kolumny, indeksy, relacje.
  • HasData — dane startowe (seed) wpisane do migracji, nie do kodu startowego. Zaraz zobaczysz je jako INSERT w wygenerowanym pliku.

Dlaczego osobna klasa, a nie wszystko w OnModelCreating

Da się wpisać to samo wprost w OnModelCreating — dla jednej encji różnicy nie widać. Widać przy dziesiątej: OnModelCreating puchnie do kilkuset linii, w których każdy feature grzebie przy każdym merge'u. IEntityTypeConfiguration<T> to po prostu jedna encja = jeden plik, a ApplyConfigurationsFromAssembly skanuje assembly refleksją i podpina wszystkie znalezione.

Znasz to już z tego kursu. To dokładnie ten sam ruch, co AddValidatorsFromAssemblyContaining<Program>() w lekcji 0008 i co metody rozszerzające AddTickets() / MapTickets() z lekcji 0004: jeden plik na feature, jedna linia skanująca w centrum. Konwencja zamiast rejestru, który trzeba pamiętać.

Gdzie ten plik położyć — to pytanie o architekturę, nie o EF:

UmiejscowienieKiedy
Features/Tickets/TicketConfiguration.cs (u nas)vertical slices — slice trzyma wszystko swoje razem: encję, konfigurację, handlery, walidatory
Infrastructure/Persistence/Configurations/Clean Architecture — warstwa domeny nie ma prawa znać EF-a, więc IEntityTypeConfiguration nie może leżeć obok encji

ApplyConfigurationsFromAssembly znajdzie ją tak czy inaczej — byle była w skanowanym assembly. Wracamy do tego w lekcji 0011.

Co jeszcze wchodzi do Configure: relacje

Nasz Ticket nie ma jeszcze relacji, ale w firmowym kodzie zobaczysz je głównie tutaj i warto umieć to przeczytać:

builder
    .HasOne(t => t.Manufacturer)
    .WithMany()
    .HasForeignKey(t => t.ManufacturerId)
    .OnDelete(DeleteBehavior.Cascade);
FragmentZnaczenie
HasOne(t => t.Manufacturer)ta encja ma jednego producenta
WithMany()producent ma wiele takich encji, ale kolekcji po jego stronie nie modelujemy
HasForeignKey(t => t.ManufacturerId)która kolumna trzyma klucz obcy
OnDelete(DeleteBehavior.Cascade)skasowanie producenta kasuje wszystkie jego wiersze
Cascade to decyzja, nie domyślność. Przy wymaganym kluczu obcym EF faktycznie przyjmuje Cascade jako domyślne, ale to znaczy, że jedno DELETE może po cichu zabrać ze sobą pół tabeli. Alternatywy: Restrict (zablokuj kasowanie, dopóki są dzieci) i SetNull (osieroć je). Przy encjach, które mają wartość historyczną — zgłoszenia, faktury, logi — Restrict jest zwykle tym, czego chcesz.
Uwaga na HasIndex(x => x.Id). Jeśli Id jest kluczem głównym, ma już unikalny indeks (PK_Tickets). Dopisanie HasIndex na tej samej kolumnie tworzy drugi, tym razem nieunikalny — sprawdziłem, migracja generuje wtedy dodatkowe CreateIndex(name: "IX_Tickets_Id", …). Kosztuje przy każdym zapisie i nie daje nic. HasIndex jest dla kolumn, po których szukasz: Title, Status, ManufacturerId.

Common/Persistence/PersistenceServices.cs

services.AddDbContext<HelpdeskDbContext>(options =>
    options.UseSqlite(configuration.GetConnectionString("Helpdesk")));

W Program.cs ta linia idzie przed AddTickets() — kolejność rejestracji nie ma znaczenia dla kontenera, ale ma dla czytelnika: infrastruktura, potem feature'y.

HasMaxLength(100) celowo powtarza limit z CreateTicketValidator z lekcji 0008. To nie duplikat przez niedopatrzenie: walidator zwraca ładne 400 z komunikatem po polsku, kolumna to ostatnia linia obrony przed czymkolwiek, co ominie API.

Krok 4 — twoja część: pierwsza migracja

Z katalogu project/Helpdesk:

dotnet ef migrations add InitialCreate
dotnet ef database update

Pierwsza komenda nie dotyka bazy. Porównuje twój model z zapisaną migawką (na razie pustą) i pisze kod różnicy. Powstają trzy pliki:

PlikCo w nim jest
Migrations/2026…_InitialCreate.csUp() — zmiana w przód, Down() — jej wycofanie
…_InitialCreate.Designer.csmigawka modelu na moment tej migracji
HelpdeskDbContextModelSnapshot.csmigawka aktualnego modelu — punkt odniesienia dla następnej migracji

Otwórz pierwszy z nich — to zwykły C#, nie magia

migrationBuilder.CreateTable(
    name: "Tickets",
    columns: table => new
    {
        Id = table.Column<int>(type: "INTEGER", nullable: false)
            .Annotation("Sqlite:Autoincrement", true),
        Title = table.Column<string>(type: "TEXT", maxLength: 100, nullable: false),
        Priority = table.Column<string>(type: "TEXT", maxLength: 20, nullable: false)
    },
    constraints: table => { table.PrimaryKey("PK_Tickets", x => x.Id); });

migrationBuilder.InsertData(
    table: "Tickets",
    columns: new[] { "Id", "Priority", "Title" },
    values: new object[,]
    {
        { 1, "normal", "Pierwsze zgłoszenie" },
        { 2, "high", "Drugie zgłoszenie!" }
    });

Widać wszystko, co ustawiłeś w TicketConfiguration: maxLength: 100, nullable: false, klucz główny, seed. I jedną rzecz, której nie ustawiałeś: Sqlite:Autoincrement. Id generuje teraz baza — twój GenerateId() z lekcji 0003 zniknął razem z problemem recyklingu numerów po skasowaniu ostatniego zgłoszenia.

Dopiero dotnet ef database update wykonuje ten kod na bazie. Powstaje plik helpdesk.db i tabela __EFMigrationsHistory z jednym wierszem — to po niej EF poznaje, których migracji jeszcze nie zaaplikował.

Migracje idą do gita, plik .db nie. Migracje to historia schematu — bez nich kolega po git clone nie odtworzy bazy. Plik .db jest binarny i konfliktuje przy każdym merge'u; dopisałem *.db do project/.gitignore.

Krok 5 — EfTicketStore i pierwszy prawdziwy await

Interfejs zmienił kształt: każda metoda jest teraz asynchroniczna i przyjmuje CancellationToken.

Features/Tickets/ITicketStore.cs

Task<IReadOnlyList<Ticket>> GetAllAsync(CancellationToken cancellationToken = default);
Task<Ticket?>             GetByIdAsync(int id, CancellationToken cancellationToken = default);
Task<bool>                TitleExistsAsync(string title, CancellationToken cancellationToken = default);
Task<Ticket>              AddAsync(string title, string priority, CancellationToken cancellationToken = default);
Task<bool>                UpdateAsync(int id, string title, string priority, CancellationToken cancellationToken = default);
Task<bool>                DeleteAsync(int id, CancellationToken cancellationToken = default);

To jest ta zmiana, na którą czekaliśmy od lekcji 0005. Wtedy handlery zwracały Task.FromResult(...) — deklarowały asynchroniczność, ale nic nie czekało. Teraz:

Features/Tickets/Queries/ListTickets/ListTicketsHandler.cs

public async Task<IReadOnlyList<TicketDto>> HandleAsync(ListTicketsQuery query, CancellationToken cancellationToken = default)
{
    var tickets = await store.GetAllAsync(cancellationToken);

    return [.. tickets.Select(TicketDto.From)];
}

Wątek, który obsługiwał to żądanie, na czas zapytania do bazy wraca do puli i obsługuje inne żądania. Przy jednym pliku SQLite to niewidoczne; przy bazie po sieci to różnica między setką a tysiącami równoczesnych żądań na tej samej maszynie. CancellationToken jedzie aż do sterownika: klient zamyka kartę, żądanie jest anulowane, zapytanie przestaje mielić bazę.

Features/Tickets/EfTicketStore.cs — odczyt

public async Task<IReadOnlyList<Ticket>> GetAllAsync(CancellationToken cancellationToken = default) =>
    await db.Tickets.AsNoTracking().OrderBy(t => t.Id).ToListAsync(cancellationToken);

public Task<bool> TitleExistsAsync(string title, CancellationToken cancellationToken = default) =>
    db.Tickets.AnyAsync(t => t.Title == title, cancellationToken);

EfTicketStore.cs — zapis

public async Task<bool> UpdateAsync(int id, string title, string priority, CancellationToken cancellationToken = default)
{
    var ticket = await db.Tickets.FirstOrDefaultAsync(t => t.Id == id, cancellationToken);
    if (ticket is null)
    {
        return false;
    }

    ticket.Rename(title);
    ticket.ChangePriority(priority);
    await db.SaveChangesAsync(cancellationToken);

    return true;
}

Zwróć uwagę: nie ma tu żadnego db.Tickets.Update(...). Wywołanie Rename() zmienia właściwość i to wystarczy, bo encja jest śledzona — wczytana bez AsNoTracking(). Stąd reguła kciuka:

Query → AsNoTracking(). Command → bez. Tracking to kopia każdego wczytanego wiersza trzymana w pamięci po to, żeby wykryć zmiany. Przy GET, gdzie nic nie zapisujesz, to czysty koszt. Przy PUT to cały mechanizm.

Ten sam kod widziany od strony bazy

Uruchom API z ASPNETCORE_ENVIRONMENT=Development i patrz na konsolę — EF loguje każde zapytanie. Poniżej realny log z tej sesji:

SELECT "t"."Id", "t"."Priority", "t"."Title"
FROM "Tickets" AS "t"
ORDER BY "t"."Id"

SELECT EXISTS (
    SELECT 1
    FROM "Tickets" AS "t"
    WHERE "t"."Title" = @title)

Dwie obserwacje na przyszłość. Po pierwsze, wartości lecą jako parametry (@p0), nie sklejone w string — SQL injection nie ma tędy drogi. Po drugie, AnyAsync nie ściąga wierszy, tylko pyta SELECT EXISTS. Gdybyś napisał store.GetAllAsync() i potem .Any(...) w C#, ściągnąłbyś całą tabelę, żeby sprawdzić jeden warunek. To jest ta klasa błędów, która na dev-ie nie boli, a na produkcji kładzie serwis.

Krok 6 — lifetime, czyli powrót lekcji 0002

W TicketsFeature zmieniła się jedna linia:

services.AddSingleton<ITicketStore, InMemoryTicketStore>();
services.AddScoped<ITicketStore, EfTicketStore>();

AddDbContext rejestruje HelpdeskDbContext jako Scoped, bo DbContext nie jest thread-safe i nie ma być długowieczny. Cokolwiek go wstrzykuje, musi mieć lifetime nie dłuższy. Zostaw AddSingleton, a aplikacja nie wstanie:

Cannot consume scoped service 'Helpdesk.Common.Persistence.HelpdeskDbContext'
from singleton 'Helpdesk.Features.Tickets.ITicketStore'.

To dokładnie ta sama captive dependency, którą wywoływaliśmy celowo w lekcji 0002 — tym razem nie na sztucznym przykładzie, tylko na czymś, co naprawdę byś napisał.

I konsekwencja, która wygląda jak usunięcie kodu: zniknął lock z lekcji 0003. Nie dlatego, że przestał być potrzebny — dlatego, że problem przestał istnieć. Singleton był jeden dla wszystkich wątków, więc trzeba było ręcznie pilnować listy. Scope to jedno żądanie HTTP, więc każde żądanie dostaje własny DbContext i nikt niczego nie współdzieli. O równoczesne zapisy dba baza — transakcjami, nie lock-iem w C#.

Krok 7 — reguła, której walidator nie sprawdzi

Obiecana na końcu lekcji 0008: unikalność tytułu. Walidator dostaje wyłącznie treść żądania, a na pytanie „czy taki tytuł już jest?” nie da się odpowiedzieć bez zajrzenia do bazy. To reguła domenowa, więc trafia do handlera i leci przez DomainException z lekcji 0007:

Features/Tickets/Commands/CreateTicket/CreateTicketHandler.cs

public async Task<TicketDto> HandleAsync(CreateTicketCommand command, CancellationToken cancellationToken = default)
{
    if (await store.TitleExistsAsync(command.Title, cancellationToken))
    {
        throw new DomainException(TicketErrors.DuplicateTitle(command.Title));
    }

    var ticket = await store.AddAsync(command.Title, command.Priority, cancellationToken);
    metrics.RecordCreated(user);

    return TicketDto.From(ticket);
}

Features/Tickets/TicketErrors.cs

public static Error DuplicateTitle(string title) =>
    new("ticket.duplicate_title", $"Zgłoszenie o tytule „{title}” już istnieje.", ErrorType.Conflict);

ErrorType.Conflict mapuje się na 409 — to twoja własna decyzja ze StatusFor w DomainExceptionHandler, podjęta w lekcji 0007, kiedy jeszcze nic nie zwracało konfliktu. Teraz coś zwraca.

throw w implementacji czy w miejscu użycia?

GetByIdAsync zwraca Ticket?, a wyjątek leci dopiero w handlerze:

public Task<Ticket?> GetByIdAsync(int id, CancellationToken ct = default) =>
    db.Tickets.AsNoTracking().FirstOrDefaultAsync(t => t.Id == id, ct);

var ticket = await store.GetByIdAsync(query.Id, cancellationToken)
    ?? throw new DomainException(TicketErrors.NotFound(query.Id));

Reguła: throw idzie tam, gdzie zna się znaczenie braku. Store wie tylko, że wiersza nie ma. Czy to błąd, zależy od tego, kto pyta:

Kto pytaBrak znaczyOdpowiedź

Gdyby GetByIdAsync rzucało samo, dwa ostatnie przypadki musiałyby łapać wyjątek, żeby stwierdzić normalną sytuację. Drugi powód, ważniejszy przy większym repo: store zaczyna wtedy zależeć od katalogu błędów feature'u. Jeden store używany przez trzy feature'y narzucałby wszystkim ten sam komunikat i ten sam status.

Ale to nie znaczy „nigdy nie rzucaj w implementacji”. Rozstrzyga nazwa metody — dokładnie tak robi sam EF Core:

Zwraca nullRzuca wyjątek
FirstOrDefaultAsyncFirstAsync
SingleOrDefaultAsyncSingleAsync

Jeśli ?? throw powtórzy ci się w czterech handlerach, nie przenoś go do GetByIdAsync — dołóż drugą metodę obok, której nazwa i typ zwracany obiecują co innego:

Task<Ticket?> GetByIdAsync(int id, CancellationToken ct = default);
Task<Ticket>  GetRequiredAsync(int id, CancellationToken ct = default);

Ticket? zmusza wołającego do decyzji, Ticket obiecuje, że decyzja już zapadła. Przy jednym użyciu ?? throw w handlerze jest tańsze — dlatego u nas jest tak, jak jest.

Czego nie robić: store rzuca KeyNotFoundException, handler łapie i zamienia na DomainException. To try/catch w roli if-a, przez granicę, którą sam kontrolujesz — droższe i gubiące kontekst.

Ta sama zasada, tylko wyrażona inaczej, siedzi w UpdateAsync i DeleteAsync: zwracają bool, a throw jest w handlerze.

Zepsuj celowo (cztery błędy, które i tak zobaczysz w pracy)

1. Migracja wygenerowana, ale nie zaaplikowana

Zajrzyj do katalogu: helpdesk.db istnieje i ma 0 bajtów. SQLite tworzy plik przy pierwszym połączeniu, ale schematu w nim nie ma. „Plik jest, więc baza jest” to fałszywy trop — źródłem prawdy jest tabela __EFMigrationsHistory. Naprawa: dotnet ef database update.

2. Store jako Singleton

W TicketsFeature zamień AddScoped na AddSingleton i uruchom. Aplikacja nie wstaje — wyjątek leci z builder.Build(), zanim obsłuży pierwsze żądanie:

System.AggregateException: Some services are not able to be constructed

Lifetime: Singleton ImplementationType: Helpdesk.Features.Tickets.EfTicketStore':
Cannot consume scoped service 'Helpdesk.Common.Persistence.HelpdeskDbContext'
from singleton 'Helpdesk.Features.Tickets.ITicketStore'.)

Sześć takich bloków, po jednym na każdy handler w łańcuchu. Przywróć AddScoped.

3. Pole w encji bez migracji

Dopisz do Ticket jedną linię i uruchom, bez generowania migracji:

public string? AssignedTo { get; private set; }
SQLite Error 1: 'no such column: t.AssignedTo'

Kompiluje się, startuje, wywala się przy pierwszym zapytaniu. To najczęstszy błąd początkującego z EF: model w kodzie i schemat w bazie to dwie osobne rzeczy, a migracja jest jedynym mostem między nimi. Usuń linię (albo zrób z niej migrację — patrz zadanie).

4. Zapomniane ApplyConfigurationsFromAssembly

Usuń tę jedną linię z OnModelCreating, skasuj katalog Migrations i wygeneruj migrację jeszcze raz. Nie ma błędu. Nie ma ostrzeżenia. Jest za to inna tabela:

Title = table.Column<string>(type: "TEXT", nullable: false),
Priority = table.Column<string>(type: "TEXT", nullable: false)

Zniknęło maxLength: 100, zniknął cały InsertData z danymi startowymi. TicketConfiguration nadal istnieje, kompiluje się i nikt go nigdy nie wywołuje. To ta sama klasa cichej awarii co zapomniane AddValidation() z lekcji 0008: konfiguracja przez skanowanie assembly jest wygodna dokładnie do momentu, w którym ktoś usunie linię skanującą.

Przywróć linię, skasuj Migrations i wygeneruj migrację ponownie — sprawdź, że maxLength: 100 wróciło.

Rozmowa, którą usłyszysz w zespole: repozytorium nad DbContext?

Zostawiliśmy ITicketStore, choć DbContext sam w sobie jest już abstrakcją nad bazą, a DbSet<T> to w zasadzie repozytorium. Argumenty z obu stron, bo obie usłyszysz:

Za własnym interfejsemZa DbContext wprost w handlerze
handler nie wie nic o EF — da się podmienić bazę i testować bez niejmniej warstw, mniej plików, mniej ceremonii
zapytania w jednym miejscu, nie rozsypane po slice'achslice widzi całe LINQ i może zoptymalizować własne zapytanie
wymusza granicę, którą Clean Architecture i tak narzucirepozytorium nad ORM-em zwykle degeneruje się do GetByXAndYAndZ

Szkoła vertical slices (Milan Jovanović, którego zna wasz zespół) częściej wybiera drugą kolumnę: DbContext prosto w handlerze, bo slice ma być samowystarczalny. Szkoła Clean Architecture wybiera pierwszą, bo warstwa domeny nie ma prawa znać EF-a. Wracamy do tego w lekcji 0011 — i to jest pytanie, które warto zadać na code review w pracy, bo odpowiedź mówi więcej o architekturze repo niż nazwy folderów.

Sprawdź się

Dlaczego Ticket przestał być record-em?
EF mapuje rekordy bez problemu. Problem jest w zapisie: with { } tworzy nowy obiekt, a śledzony jest stary — SaveChangesAsync nie miałby o czym pisać UPDATE-a.
Co robi dotnet ef migrations add z bazą danych?
Migracja powstaje wyłącznie z porównania modelu ze snapshotem, offline. Bazy dotyka dopiero database update. Dlatego migrację można wygenerować bez dostępu do serwera bazy.
Kiedy nie używać AsNoTracking()?
Bez trackingu EF nie zauważy przypisania ticket.Title = … i SaveChangesAsync nie wyśle UPDATE-a. Przy odczytach — odwrotnie: tracking to zbędny koszt.
Zgłoszenie o tym tytule już istnieje. Walidator czy handler?
Walidator widzi wyłącznie treść żądania. Wszystko, co wymaga stanu systemu, jest regułą domenową: DomainException, jeden code, status 409.
Czemu z EfTicketStore zniknął lock z lekcji 0003?
DbContext jest Scoped, a scope to jedno żądanie HTTP — nie ma współdzielonego stanu, więc nie ma czego blokować. O równoczesne zapisy dba baza, transakcjami.
Usuwasz ApplyConfigurationsFromAssembly. Co się dzieje?
EF wywnioskuje z samych typów tyle, ile umie: tabelę, kolumny i Id jako klucz. Wszystko, co dopisałeś w Configure — długości, seed, indeksy, relacje — po prostu nie istnieje. Cicha awaria, jak zapomniane AddValidation().
Gdzie powinien być throw przy braku zgłoszenia?
Store zna fakt, handler zna znaczenie: dla GET /tickets/99 brak to 404, przy sprawdzaniu duplikatu to sytuacja normalna. Wyjątek w implementacji jest w porządku tylko wtedy, gdy obiecuje go nazwa — jak FirstAsync obok FirstOrDefaultAsync.

Zapamiętaj bez zaglądania

Dwie komendy i co dokładnie robi każda z nich?

dotnet ef migrations add Nazwa — porównuje model ze snapshotem i generuje kod; bazy nie dotyka. dotnet ef database update — wykonuje na bazie migracje, których nie ma w tabeli __EFMigrationsHistory. Migracje idą do gita, plik .db nie.

Jakiego lifetime'u wymaga DbContext i dlaczego?

Scoped — rejestruje go tak samo AddDbContext. Nie jest thread-safe, więc jeden na żądanie. Wszystko, co go wstrzykuje, musi być Scoped albo Transient; Singleton = Cannot consume scoped service … from singleton … przy Build().

Jak zapisać zmianę w istniejącym wierszu?

Wczytać encję bez AsNoTracking(), przypisać nowe wartości do właściwości, wywołać await db.SaveChangesAsync(ct). Żadnego .Update(...) — change tracker sam wykryje różnicę i wygeneruje UPDATE tylko dla zmienionych kolumn.

Reguła wymaga zajrzenia do bazy — gdzie ją umieścić?

W handlerze, nie w walidatorze. Walidator widzi tylko treść żądania. Reguła domenowa leci przez DomainException z katalogu błędów: ticket.duplicate_title, ErrorType.Conflict, HTTP 409.

Gdzie opisujesz kolumny, indeksy i relacje — i jak to trafia do DbContext?

W klasie …Configuration : IEntityTypeConfiguration<T>, jedna encja = jeden plik, obok encji (slices) albo w Infrastructure/Persistence/Configurations (Clean Architecture). DbContext podpina wszystkie jedną linią: modelBuilder.ApplyConfigurationsFromAssembly(typeof(HelpdeskDbContext).Assembly). Bez tej linii konfiguracja jest ignorowana bez żadnego błędu.

Prywatny konstruktor i Create() — co na to EF i gdzie jest pułapka?

EF materializuje encję refleksją, więc prywatny konstruktor i prywatne settery mu nie przeszkadzają. Pułapka: parametry konstruktora są wiązane po nazwie z właściwościami — niezgodność daje No suitable constructor was found for the type 'Ticket' dopiero w czasie działania. Druga: HasData przyjmuje wtedy typ anonimowy, nie encję.

Metoda nie znalazła rekordu — zwrócić null czy rzucić?

Rozstrzyga nazwa. GetByIdAsync → null, a znaczenie braku nadaje wołający (?? throw new DomainException(...) w handlerze). GetRequiredAsync → rzuca, bo tak obiecuje. Wzór: FirstOrDefaultAsync vs FirstAsync w EF Core.
