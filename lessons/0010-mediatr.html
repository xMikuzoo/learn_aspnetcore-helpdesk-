Lekcja 0010 · ~20 min · projekt Helpdesk

Wymiana własnego dispatchera na MediatR

Cel: skasować Sender, ISender, Unit i ValidationSender, a na ich miejsce wstawić bibliotekę — i zbudować dokładnie tę warstwę interfejsów, którą masz w firmowym repo.

Wymaga: lekcji 0006 (własny dispatcher) i 0008 (walidacja w pipelinie). Ściągi: MediatR, dispatcher.

Skąd ta lekcja. Pokazałeś kod z pracy — wasze ICommand / IQuery / ICommandHandler to cienka warstwa nad MediatR. Przepisujemy Helpdesk na dokładnie ten sam układ, żeby firmowe repo przestało wymagać tłumaczenia.

Krok 2 — warstwa nazw nad IRequest

MediatR zna tylko request. Nie zna pojęć „command” i „query” — te dokładamy sami, i to jest ta warstwa, którą masz w pracy:

Common/Cqrs.cs — cały plik po migracji

public interface ICommandBase;

public interface ICommand : IRequest, ICommandBase;

public interface ICommand<out TResponse> : IRequest<TResponse>, ICommandBase;

public interface IQuery<out TResponse> : IRequest<TResponse>, ICommandBase;

public interface ICommandHandler<in TCommand> : IRequestHandler<TCommand>
    where TCommand : ICommand;

public interface ICommandHandler<in TCommand, TResponse> : IRequestHandler<TCommand, TResponse>
    where TCommand : ICommand<TResponse>;

public interface IQueryHandler<in TQuery, TResponse> : IRequestHandler<TQuery, TResponse>
    where TQuery : IQuery<TResponse>;

Siedem linii, zero logiki. Co za nie kupujesz:

  • Intencję w nazwie. IQuery<TicketDto> i ICommand<TicketDto> są technicznie identyczne — oba to IRequest<TicketDto>. Różni je tylko słowo, ale to słowo jest całym CQRS z lekcji 0005.
  • Constraint, którego MediatR nie ma. where TCommand : ICommand<TResponse> sprawia, że handler komendy nie skompiluje się z zapytaniem w środku. Goły IRequestHandler na to pozwala.
  • Punkt zaczepienia dla pipeline'u. ICommandBase nie ma żadnej składowej — istnieje po to, żeby behavior mógł napisać where TRequest : ICommandBase i nie odpalać się na cudzych requestach.

out w <out TResponse> to kowariancja — dziedziczona po IRequest<out TResponse>. Pozwala potraktować IQuery<TicketDto> jako IQuery<object>. Przy bezwynikowym ICommand nie ma czego wariować, stąd brak out.

Uwaga na ICommandBase — to jest pytanie na code review. W tym układzie IQuery też implementuje ICommandBase, więc marker mimo nazwy obejmuje zapytania. Każdy behavior ograniczony where TRequest : ICommandBase odpali się także na GET. Dla walidacji to dobrze (chcemy walidować i komendy, i zapytania). Dla behaviora otwierającego transakcję albo piszącego wpis audytowy — katastrofa. Nazwa IApplicationRequest mówiłaby prawdę; ICommandBase kłamie. Zapytaj u siebie, czy to świadome.

Krok 3 — Unit odchodzi

Do MediatR 11 bezwynikowy request był w rzeczywistości IRequest<Unit> i handler zwracał Task<Unit> — dokładnie to, co napisaliśmy sami w lekcji 0007. Od wersji 12 jest osobna ścieżka: IRequest : IBaseRequest, a IRequestHandler<in TRequest> zwraca zwykłe Task. Dlatego dwie komendy chudną:

public record UpdateTicketCommand(int Id, string Title, string Priority) : ICommand<Unit>;
public record UpdateTicketCommand(int Id, string Title, string Priority) : ICommand;

Features/Tickets/Commands/UpdateTicket/UpdateTicketHandler.cs

public class UpdateTicketHandler(ITicketStore store) : ICommandHandler<UpdateTicketCommand>
{
    public async Task Handle(UpdateTicketCommand command, CancellationToken cancellationToken)
    {
        if (!await store.UpdateAsync(command.Id, command.Title, command.Priority, cancellationToken))
        {
            throw new DomainException(TicketErrors.NotFound(command.Id));
        }
    }
}

Zniknęło Task<Unit>, zniknęło return Unit.Value;, zniknął plik Common/Unit.cs. To jest ta różnica, o którą pytałeś przy własnym ISender: przeciążenia bez wyniku nie dało się dołożyć w kilku linijkach, bo wymagało drugiej hierarchii — markera, handlera, gałęzi w dispatcherze, metody w dekoratorze. Biblioteka zrobiła to raz u siebie.

Dwie zmiany w sygnaturze handlera, obie wymuszone. HandleAsync → Handle, bo tak nazywa się metoda w IRequestHandler. I znika = default przy CancellationToken — interfejs deklaruje parametr bez wartości domyślnej.

Krok 4 — dekorator staje się behaviorem

Common/Validation/ValidationBehavior.cs

public class ValidationBehavior<TRequest, TResponse>(IEnumerable<IValidator<TRequest>> validators)
    : IPipelineBehavior<TRequest, TResponse>
    where TRequest : ICommandBase
{
    public async Task<TResponse> Handle(
        TRequest request,
        RequestHandlerDelegate<TResponse> next,
        CancellationToken cancellationToken)
    {
        var context = new ValidationContext<TRequest>(request);
        var failures = new List<ValidationFailure>();

        foreach (var validator in validators)
        {
            var result = await validator.ValidateAsync(context, cancellationToken);
            failures.AddRange(result.Errors);
        }

        if (failures.Count > 0)
        {
            throw new ValidationException(failures);
        }

        return await next(cancellationToken);
    }
}

Porównaj z ValidationSender z lekcji 0008 — logika jest ta sama, ale trzy rzeczy zrobiły się prostsze:

Dekorator (0008)Behavior (0010)
dwie metody Send (command i query), obie wołające ValidateAsyncjedna metoda Handle
typeof(IValidator<>).MakeGenericType(...) + GetServicesIEnumerable<IValidator<TRequest>> wstrzyknięte przez konstruktor — bez refleksji
ValidationContext<object>ValidationContext<TRequest> — typ znany
opakowanie ISender, więc kolejność = kolejność rejestracji dekoratorównext(ct) = następne ogniwo; kolejność = kolejność AddOpenBehavior

IPipelineBehavior jest generyczny po obu parametrach, więc jedna klasa obsługuje wszystkie requesty. Constraint where TRequest : ICommandBase zawęża to do naszych.

To jest middleware, tylko w innym miejscu. app.UseXxx() opakowuje żądanie HTTP; IPipelineBehavior opakowuje command. Ten sam kształt (next w środku), inny poziom: middleware widzi ścieżkę i nagłówki, behavior widzi typ komendy i jej pola.

Krok 5 — rejestracja

Common/CommonServices.cs

public static IServiceCollection AddDispatcher(this IServiceCollection services)
{
    services.AddMediatR(configuration =>
    {
        configuration.RegisterServicesFromAssemblyContaining<Program>();
        configuration.AddOpenBehavior(typeof(ValidationBehavior<,>));
    });

    return services;
}

I w TicketsFeature.AddTickets znika sześć linii — po jednej na handler:

services.AddScoped<ICommandHandler<CreateTicketCommand, TicketDto>, CreateTicketHandler>();
services.AddScoped<IQueryHandler<GetTicketQuery, TicketDto>, GetTicketHandler>();

Zostaje tylko to, czego MediatR nie zna: ITicketStore i TicketMetrics. To jest ta „cena”, o której mówiła lekcja 0006 — zapomniana rejestracja handlera dawała 500 przy pierwszym żądaniu. Skan assembly płaci ją za ciebie: nowy handler działa od razu po zapisaniu pliku.

typeof(ValidationBehavior<,>) to otwarty typ generyczny z lekcji 0006 — piszesz klasę raz, MediatR domyka parametry osobno dla każdego requestu.

Błędy, które zobaczysz po drodze

Migracja nie kompiluje się w połowie — to normalne. Trzy komunikaty, każdy mówi dokładnie, co zrobić:

KomunikatZnaczenie

Sprawdź się

Po co własne ICommand, skoro MediatR ma IRequest?
MediatR działa bez tej warstwy. Kupujesz nią rozróżnienie command/query (którego biblioteka nie zna) oraz where TCommand : ICommand<TResponse> — kompilator nie pozwoli wtedy pomylić handlera komendy z handlerem zapytania.
Dlaczego z projektu zniknął Unit?
Do wersji 11 IRequest był IRequest<Unit>. Od 12 jest IRequest : IBaseRequest i IRequestHandler<in TRequest> z Task. Wewnątrz biblioteki Unit nadal istnieje — po prostu nie dotyka już twojego kodu.
Co zmienia where TRequest : ICommandBase w behaviorze?
Nazwa myli. IQuery też dziedziczy po ICommandBase, więc constraint mówi „nasze requesty”, nie „komendy”. Dla walidacji to pożądane; dla behaviora transakcyjnego byłoby błędem.
Co zastąpiło sześć linii AddScoped dla handlerów?
AddOpenBehavior rejestruje pipeline, nie handlery. Handlery znajduje skan assembly — ten sam wzorzec co AddValidatorsFromAssemblyContaining i ApplyConfigurationsFromAssembly.

  3. git log -p -- project/Helpdesk/Common — zobacz, że skasowaliśmy ISender.cs, Sender.cs i Unit.cs, a endpointy zmieniły tylko using.

Zapamiętaj bez zaglądania

Jak nazywa się handler w MediatR i czym różni się od naszego z lekcji 0006?

IRequestHandler<TRequest, TResponse> z metodą Handle(request, cancellationToken) — bez = default. Wersja bezwynikowa: IRequestHandler<in TRequest> z Task Handle(...). Nasze ICommandHandler / IQueryHandler tylko po nich dziedziczą i dokładają constraint.

Gdzie wpina się walidację i jak przekazać sterowanie dalej?

IPipelineBehavior<TRequest, TResponse>, rejestrowany przez cfg.AddOpenBehavior(typeof(ValidationBehavior<,>)). Dalej: return await next(cancellationToken);. Nic nie wołasz — brak next oznacza przerwanie łańcucha.

Co dokładnie robi RegisterServicesFromAssemblyContaining<Program>()?

Skanuje assembly i rejestruje w DI każdą klasę implementującą IRequestHandler (oraz INotificationHandler). Zastępuje ręczne AddScoped per handler. Ten sam wzorzec co AddValidatorsFromAssemblyContaining z 0008 i ApplyConfigurationsFromAssembly z 0009 — i ta sama cena: usunięcie jednej linii wyłącza wszystko, bez błędu.
