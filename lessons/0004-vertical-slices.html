Lekcja 0004 · ~20 min · projekt Helpdesk

Vertical slices: jeden folder na feature

Cel: wyprowadzić wszystko, co dotyczy zgłoszeń, z Program.cs do folderu Features/Tickets/ — tak, żeby Program.cs wrócił do dziesięciu linii, a dodanie nowego zasobu nie wymagało dotykania żadnego istniejącego pliku. Po drodze poznasz metody rozszerzające, czyli mechanizm, na którym stoi połowa API .NET-a.

Wymaga: lekcji 0003 (CRUD w grupie tras). Ściąga: Vertical slices i metody rozszerzające.

Problem: dwunasty endpoint

Twój Program.cs ma teraz około 70 linii i robi cztery niepowiązane rzeczy: rejestruje serwisy, definiuje CRUD zgłoszeń, wystawia metryki i trzyma eksperyment z lifetime'ami. Póki to jeden zasób, da się żyć. Dołóż komentarze do zgłoszeń, załączniki i użytkowników, a dostaniesz 300 linii, w których rejestracja ICommentStore jest 200 linii od endpointów, które z niej korzystają.

W świecie frontu przerabiałeś dokładnie ten sam ruch. Kiedyś struktura Vue wyglądała tak:

src/
  components/    // wszystkie komponenty świata
  stores/        // wszystkie store'y świata
  composables/   // wszystkie composable świata

Dodanie jednego widoku znaczyło otwarcie czterech folderów i dopisanie po pliku w każdym. Dlatego przeszliście na src/features/checkout/ z komponentem, store'em i typami obok siebie. Vertical slices to ta sama decyzja po stronie backendu — i to jest architektura, którą stosuje twój zespół.

„Minimize coupling between slices, and maximize coupling in a slice.” — Milan Jovanović, Vertical Slice Architecture. Sedno: wewnątrz jednego feature'u pliki mogą wiedzieć o sobie wszystko; między feature'ami — jak najmniej.

Krok 1: metoda rozszerzająca

Zanim przeniesiesz pliki, potrzebujesz mechanizmu, którym feature „podłączy się" do Program.cs. W .NET robi się to metodą rozszerzającą (extension method).

Ty już ich używasz cały czas. builder.Services.AddSingleton<…>() nie jest metodą klasy ServiceCollection — to metoda statyczna z zupełnie innego pliku, doklejona do interfejsu IServiceCollection z zewnątrz. Tak samo app.MapGet i app.UseHttpsRedirection.

Składnia to jedno słowo — this przed pierwszym parametrem:

public static class TicketsFeature
{
    public static RouteGroupBuilder MapTickets(this IEndpointRouteBuilder app)
    {
        // …
    }
}

Od tej chwili app.MapTickets() działa tak, jakby MapTickets było metodą app. Kompilator zamienia to na TicketsFeature.MapTickets(app) — to czysty cukier składniowy, żadnej magii w runtime.

Frontendowo: to jest to, co w JS robiłbyś przez Array.prototype.myThing = …, tylko bez modyfikowania cudzego obiektu. Nic nie jest podmieniane globalnie — metoda istnieje wyłącznie w plikach, które zaimportują jej namespace.

Trzy warunki i trzy błędy kompilatora

Wszystkie trzy sprawdzone na .NET 10.0.400 — jeśli któryś zobaczysz, wiesz już, co znaczy:

ZapomniałeśKomunikat
klasa musi być staticerror CS1106: Metoda rozszerzenia musi być zdefiniowana w nieogólnej klasie statycznej.
this przy parametrzeerror CS1061: Element „WebApplication" nie zawiera definicji „MapTickets"…
using w Program.csten sam CS1061, z dopiskiem „czy nie brakuje dyrektywy using…"
Ostatni wiersz to najczęstsza pułapka. Metoda rozszerzająca jest niewidoczna, dopóki nie masz using jej namespace'u. Kompilator mówi „nie ma takiej metody", choć plik leży dwa foldery obok. Dlatego w firmowym kodzie zobaczysz czasem namespace Microsoft.Extensions.DependencyInjection; nad własną klasą rozszerzeń — sztuczka, żeby metoda była widoczna wszędzie tam, gdzie już jest AddSingleton. Legalne i powszechne, ale mylące dla czytającego; my tego nie robimy.

Krok 2: namespace, czyli import w C#

Do tej pory wszystkie twoje pliki były w globalnym namespace i widziały się nawzajem bez żadnego import. To działa tylko dlatego, że projekt jest malutki. Przy folderach na feature'y potrzebujesz nazw:

namespace Helpdesk.Features.Tickets;   // pierwsza linia pliku, ze średnikiem

To file-scoped namespace (C# 10+): obejmuje cały plik, bez klamer i bez dodatkowego wcięcia. Starszy kod ma wersję z { … } — to samo, tylko wszystko przesunięte o cztery spacje.

Dwie rzeczy, które zaskakują przy przejściu z TS:

  • Namespace nie wynika z folderu. Nikt go nie generuje z układu katalogów — wpisujesz go ręcznie. Konwencja mówi „ma odpowiadać ścieżce", ale kompilator tego nie sprawdza. VS Code z rozszerzeniem C# podpowie właściwy przy tworzeniu pliku.
  • Importujesz namespace, nie plik. W TS piszesz import { Ticket } from './ticket' — konkretna ścieżka. W C# piszesz using Helpdesk.Features.Tickets; i dostajesz wszystkie publiczne typy z tego namespace'u, niezależnie od tego, w ilu plikach siedzą.

Krok 4: TicketsFeature.cs

Dwie metody rozszerzające: jedna dokłada serwisy do kontenera, druga mapuje endpointy. Obie zwracają to, co dostały — dzięki temu da się je łańcuchować, dokładnie jak wbudowane Add*.

project/Helpdesk/Features/Tickets/TicketsFeature.cs

using Helpdesk.Common;
using Microsoft.AspNetCore.Http.HttpResults;

namespace Helpdesk.Features.Tickets;

public static class TicketsFeature
{
    public static IServiceCollection AddTickets(this IServiceCollection services)
    {
        services.AddSingleton<ITicketStore, InMemoryTicketStore>();
        services.AddSingleton<TicketMetrics>();
        return services;
    }

    public static RouteGroupBuilder MapTickets(this IEndpointRouteBuilder app)
    {
        var tickets = app.MapGroup("/tickets").WithTags("Tickets");

        tickets.MapGet("/", (ITicketStore store) => store.GetAll());

        // … reszta endpointów bez zmian, przeklejona z Program.cs

        tickets.MapGet("/metrics", (TicketMetrics metrics) => new { created = metrics.Created });

        return tickets;
    }
}
Dlaczego IEndpointRouteBuilder, a nie WebApplication? Bo MapGroup zwraca RouteGroupBuilder, który też implementuje IEndpointRouteBuilder. Pisząc na interfejsie, tę samą metodę wywołasz zarówno na app, jak i wewnątrz innej grupy — np. var api = app.MapGroup("/api"); api.MapTickets(); przeniesie cały feature pod /api/tickets jedną linią. Gdybyś zadeklarował this WebApplication app, ta możliwość by nie istniała.

/tickets/metrics obok /tickets/{id:int}

Metryki przeniosły się z /metrics pod /tickets/metrics — bo dotyczą zgłoszeń, więc należą do slice'u. Można by się bać kolizji z /tickets/{id:int}, ale zweryfikowane: GET /tickets/metrics zwraca {"created":1}, nie 404. Ograniczenie :int z lekcji 0003 wyklucza "metrics" z dopasowania, więc routing spokojnie idzie do trasy dosłownej. Bez :int ten adres by nie działał.

Krok 5: Program.cs po refactorze

project/Helpdesk/Program.cs

using Helpdesk.Common;
using Helpdesk.Features.Diagnostics;
using Helpdesk.Features.Tickets;

var builder = WebApplication.CreateBuilder(args);

builder.Services.AddCurrentUser();
builder.Services.AddTickets();
builder.Services.AddDiagnostics();

var app = builder.Build();

app.MapGet("/", () => "Hello World!");

app.MapTickets();
app.MapDiagnostics();

app.Run();

Trzynaście linii i czytelny spis treści aplikacji. Ale ważniejsza jest inna właściwość: dodanie feature'u „komentarze" to jeden nowy folder i dwie nowe linie tutaj. Zero zmian w istniejących plikach. To jest cała obietnica vertical slices — nowy kod dopisujesz, starego nie ruszasz, więc nie ma czego zepsuć.

Uwaga na kolejność: Add* muszą być przed builder.Build(), Map* po. Kontener jest zamykany w momencie Build() — to ta sama granica, o którą rozbiła się captive dependency w lekcji 0002.

Czym to nie jest

Warto od razu odróżnić dwie rzeczy, które w rozmowie w pracy padają obok siebie:

Vertical slicesClean Architecture
Kryterium podziałufeature (Tickets, Comments)warstwa (Domain, Application, Infrastructure)
Nowy featurejeden folderplik w każdej warstwie
Reguła zależnościslice nie zna slice'uwszystko wskazuje do środka
Cenaduplikacja między slice'amiabstrakcje i przeskakiwanie między projektami

Nie są sprzeczne — da się mieć slices wewnątrz warstwy Application. Do Clean Architecture wracamy w lekcji 0010; na razie zapamiętaj samo kryterium podziału, bo to ono pada w pytaniu „czemu u nas jest tyle folderów".

Sprawdź się

Odpowiedz zanim klikniesz. Zła odpowiedź nie zdradza dobrej — spróbuj jeszcze raz.

Co czyni metodę statyczną metodą rozszerzającą?
this przed typem pierwszego parametru mówi kompilatorowi, że wywołanie app.MapTickets() ma się przełożyć na TicketsFeature.MapTickets(app). Dodatkowo klasa musi być static i nieogólna — inaczej CS1106.
Kompilator: „WebApplication nie zawiera definicji MapTickets”. Co sprawdzasz najpierw?
Metoda rozszerzająca jest niewidoczna bez using jej namespace'u — kompilator zgłasza to jako brak metody, nie jako brak importu. Drugi kandydat to zgubione this. Rejestracja w DI nie ma tu nic do rzeczy: to błąd kompilacji, a DI rozstrzyga się w runtime.
Po co MapTickets przyjmuje IEndpointRouteBuilder zamiast WebApplication?
RouteGroupBuilder również implementuje IEndpointRouteBuilder, więc ten sam feature podłączysz pod app albo pod app.MapGroup("/api"). Programowanie na interfejsie kupuje ci tu konkretną elastyczność, nie samą czystość.
Kiedy klasa powinna trafić do folderu Common?
Kryterium to faktyczne użycie, nie przewidywanie. Przenoszenie tam kodu „bo się przyda” kończy się folderem, w którym leży połowa aplikacji i który zależy od wszystkiego — czyli dokładnie tym, przed czym slices mają chronić.
Na co kompilator zamienia app.MapTickets()?

Na zwykłe wywołanie statyczne TicketsFeature.MapTickets(app). Metody rozszerzające to cukier składniowy rozwijany w czasie kompilacji — w runtime nie istnieje żadne „doklejanie” metod do typu.

Czym różni się using w C# od import w TypeScript?

import wskazuje plik i wybrane symbole. using wskazuje namespace i wciąga wszystkie jego publiczne typy, niezależnie od liczby plików. Namespace nie jest wyprowadzany z układu folderów — wpisujesz go ręcznie.

Jaka jest jednozdaniowa różnica między vertical slices a Clean Architecture?

Kryterium podziału: slices tną kod po feature'ach, Clean Architecture po warstwach. Stąd „nowy feature = jeden folder” kontra „nowy feature = plik w każdej warstwie”.

Źródło pierwotne

Milan Jovanović — Vertical Slice Architecture (ok. 8 min). Czytaj po to, żeby zapamiętać jedno zdanie: „Minimize coupling between slices, and maximize coupling in a slice” — to autor, którego zna twój zespół, więc to jest dosłownie ich słownik. Do samych metod rozszerzających: Extension Methods (C# Programming Guide) — sekcje Definition i Binding at compile time.
Coś nie wchodzi — CS1061 mimo using, konflikt tras, plik nie widzi typu z sąsiedniego folderu? Wklej to nauczycielowi w terminalu (Claude Code w C:\PLAYGROUND\asp). Pytanie do zespołu: „czy slice'y u nas mogą się nawzajem wołać, czy tylko przez coś wspólnego?” — odpowiedź powie ci, jak rygorystycznie traktują izolację feature'ów.

Co dalej

Masz folder na feature, ale w środku wszystko dalej siedzi w jednej metodzie MapTickets: lambda pobiera dane, woła store i buduje odpowiedź. Póki to jest store.Add(title), jest dobrze. Ale „utwórz zgłoszenie” zaraz zacznie znaczyć: zwaliduj, sprawdź uprawnienia, zapisz, zwiększ metrykę, wyślij powiadomienie. Tego nie chcesz mieć w lambdzie endpointu. Lekcja 0005: command vs query — rozdzielenie „zmień stan” od „przeczytaj stan” i pierwszy własny ICommandHandler. To jest ten fragment, który w twoim firmowym repo nazywa się CQRS.
